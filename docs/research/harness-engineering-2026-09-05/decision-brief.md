The next useful investment is a trustworthy account of inputs, evidence and total work. The investigation found concrete defects in that account. It did not establish that a new model loop, shared board or storage backend would improve ordinary sessions.

## My view on the agent message board

It is useful enough to test for **discovery and late corrections**. A worker may learn something relevant to another task without knowing its recipient. A small shared notice lets that other worker discover it. Known dependencies are already well served by direct handoffs and a coordinator's concise context packet.

For example, one worker discovers that document v2 changes a paragraph another worker cited from v1. A notice can identify both versions, the affected claim and the uncertainty. Another useful notice says exactly which sections failed to answer a question. Neither notice establishes truth or completion; the reader still follows the evidence.

The [message-board research](message-board.md) assesses [Collusion](https://collusion.wiki/) and related primary literature. That evidence motivates the pilot; it does not establish benefit for this harness.

Start with three benign document packets and three arrangements: a single worker with complete sources; complementary workers with directed handoffs and a curated packet; the identical parallel arrangement with a small board added. Keep source access, model, total budget, correction timing and grading constant. Count posting, reading, curation and correction work. Necessary independent verification is not wasted duplication.

A stored message is not evidence of delivery, use, correctness or benefit. Keep those observations separate. Preserve independent initial assessments, source versions and correction history. Fix the reference assessment before grading anonymized final outputs; exclude treatment labels, peer discussion, self-grades and other cases' answers. Scheduled observations must reach each arrangement at the same release point.

**Recommendation:** no board service or general shared memory now. Prepare the pilot. Expand it only if a validated notice explains an improvement over a capable direct-handoff baseline within the same budget and without new correctness, provenance or isolation failures. Three packets can show a mechanism; adoption needs repeated paired evidence and a practical benefit threshold selected before the adoption study.

## Runtime ownership remains an open choice

The inspected SDKs support some of the capabilities previously treated as reasons to own the loop. Source inspection also revealed boundaries that matter: a request observed before normalization can differ from adapter input; cancellation and process loss are different events; serializable state is not an atomic record of artifact work.

The [foundation investigation](foundations.md) pins the source versions and names the inspected tests. Those upstream tests were read, not run here. Its strongest reason to compare deeper ownership is a concrete compound requirement: one recoverable account of prepared input, context boundary and unfinished benign artifact work. A supported extensible runtime, narrow host change and owned loop should compete on that requirement, not on a feature checklist.

The first protocol should test client-managed input at the scripted adapter boundary, a late document correction, cooperative pause, and uncertainty after an artifact write without a receipt. Persisted no-summary rollover is a separately selectable diagnostic. Do not penalize a candidate for lacking it unless it becomes a required behavior. Model quality and real-provider behavior need a later, separately authorized comparison.
