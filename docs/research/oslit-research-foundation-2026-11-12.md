## Engineering goal

Build a target-neutral workflow for authorized security research. A person supplies the target, a signed scope, a goal, and resources. The agent owns the whole internal engagement: it learns the target, prepares a usable environment, writes its threat model, maps reachable surfaces, chooses and revises experiments, asks for independent checks, decides when the search is covered or blocked, produces the result, and verifies cleanup. It makes and checks a patch when the goal and evidence call for one. It must carry material work across interruptions. No person supplies a flaw, test sequence, next research step, or patch hint during the run. Current human authority and review gates still apply, but the agent owns their handoff and resumes the run after they are settled. These decisions are recorded separately from research steering.

The workflow must not depend on a prior issue database, a known defect, a fixed twin, a prewritten target command, or a hand-built target adapter. An agent can create target-specific scripts and setup files in the disposable run. The durable harness must enforce authority, resource limits, evidence capture, replay, review, and cleanup without knowing the target's flaw. Some targets need hardware, accounts, or observation methods outside the approved environment. The system must report these as blocked with exact reasons. No finite test can prove it works on every target or prove that a dry target has no vulnerability.

The repository already states this direction in its [product and engineering guide](../wiki/product-and-engineering-direction.md). Its research method is target neutral, but the automated path is incomplete. The native agent can read and edit source, search files, use a shell, retain a workspace, and resume. The host can run captured source in clean copies and start fresh review. A person still prepares runtime images, dependencies, and build commands; invokes independent execution and review; and checks the patch link. Service effect capture is pinned to Kanboard cases. The continuation controller runs research turns, but it does not dispatch these host evidence steps. The current model route is also fixed to two OpenCode DeepSeek pairs. This readback found no complete live native workflow result with a real provider and target. See [native status](../wiki/native-research-status.md), [source mode](../agents/native-source-sdk.md), [controller](../../tools/native_continuation.py), and [runner](../../tools/native_research.py).

A new source target currently needs a runtime in both pinned images, offline dependencies, a build command, a signed scope, a fresh plan approval, and an observer. The runner does not install target tools at start. Its source review can return a candidate for operator review. It does not accept a patch or file a confirmed finding. A matching replay proves repeatable output, not a security claim or a fix. These are integration gaps in the general workflow. They do not call for target-specific wrappers. Its current 24-hour ceiling also provides no multi-day proof.

A first patch check can use the current source commands. Run the same effect and normal-function probes before and after the researcher's patch. Give a fresh reviewer the pinned diff, original source, and receipts. The reviewer can test an original copy and a patched copy. The operator must still check that the patched bytes come only from the proposed diff and that the probes test the same behavior. The runner does not bind these steps or issue a patch verdict. This manual link is part of final review, and its time belongs in the human-touch record. For the full autonomous workflow, the runner must bind the proposed diff, original bytes, patched bytes, and checks before it asks for review.

The 9 November local Kanboard pilot reproduced two bounded historical effects. Both researchers used Codex chats and knew facts about the case. Neither product runner executed. One arm crossed its signed effect limit. This is method evidence and a scope failure, not proof that the autonomous pipeline works. Kanboard is not an input or special case required by the proposed workflow. The local record is `kanboard-paired-comparison-20261109/engagements/paired-harness-kanboard-2026-11-09/pilot-report.md`.

## Be-ambitious method

**Field:** Security systems engineering.

- **Expert move:** Prove transfer to new targets. Check that an effect came from the claimed flaw and that a patch fixes the cause without breaking normal work. Count every human research hint, setup repair, reviewer action, and provider charge.
- **Raw material:** Use fresh authorized source or target access, policy, build files, runtime state, and raw execution receipts. Do not start from a known writeup, issue answer, or a feature list.
- **Method:** Let the agent prepare its environment, map reachable paths, choose tests, revise from observations, and request independent replay and review. Use unseen targets from more than one stack. Keep a hidden known case in the evaluator only, then test an unknown target.
- **External check:** Another operator can start an eligible target without research steering. An independent reviewer can repeat the reported effect and patch check from saved inputs. Failures, false claims, blocked cases, cost, and human help remain in the result set.

**Rewritten working objective:**

```text
Build one target-neutral workflow in which the agent owns an internal engagement from setup to closeout. Its required inputs are an authorized target, a signed scope, a goal, and resources. The agent prepares the target, writes and corrects its threat model, maps attacker-reachable paths, chooses and revises experiments, and requests independent checks. It tests impact under the same attacker role when evidence supports that step. It proposes and checks a patch when the goal calls for one. It resumes from saved work, obtains required reviews, closes the run with supported claims or exact limits, and verifies cleanup. Keep human authority decisions visible. Test transfer on unseen targets without giving the researcher a flaw, fixed twin, issue answer, target-specific command, or manual research hint. Measure useful results, false claims, patch regressions, cost, and human work. Add tools only when a run shows a gap or measured gain.
```

## The general run, not a target script

The workflow has one stable contract. Its inputs are target identity or source, signed scope, research goal, accounts or access that the scope permits, and a resource limit. The agent may create target-local scripts, build instructions, tests, and notes. It can choose the order of work and revisit earlier ideas. The host pins what ran and records effects. A target may be source code, a local service, or another permitted surface. Each class needs a safe way to run and observe it; a generic shell alone does not establish every claim.

The agent owns these decisions during the run:

1. **Setup:** Inspect the source and policy. Determine how to build or start the target in a disposable environment. Create the target-specific commands and check that normal behavior works. If required access or a safe runtime is missing, report a blocked state with the missing item.
2. **Research:** Draft the threat model. Map entry paths, trusted roles, assets, and reachable states. Choose a test that can separate an explanation from a serious alternative. Run it, compare the result with the prediction, and revise or backtrack. A held path does not end another live lead.
3. **Evidence:** Submit a concrete experiment to an independent executor or observer. Preserve exact inputs, source version, actor, target state, output, and contrary evidence. Replay the effect on a clean copy. Test a control that removes the claimed cause. A successful outcome through a different flaw fails causal attribution.
4. **Impact and optional patch:** If a supported effect may lead further, test that claim under the same attacker rights and scope. If the goal calls for a patch, produce a small diff and check the effect, normal behavior, and nearby variants on original and patched copies. Send the exact claim, controls, diff when present, and limits to a fresh reviewer.
5. **Continuity and closeout:** Keep useful leads, failed tests, pending effects, allowance, and cleanup state across context loss. Decide when the work is supported, unresolved, blocked, or covered dry. Request the review that a material claim or strong-lead dismissal needs. Reconcile pending effects, state exact coverage and uncertainty, record human help, verify cleanup, and close the internal run. External filing, deployment, or merge remains a separate action under current policy.

These are evidence states and responsibilities, not a fixed order of workers. A stronger model must be free to find a better test or method. The stable code enforces the signed boundary and evidence rules. It does not encode a Linux, EVM, Kanboard, or issue-search recipe as the workflow itself.

## Smallest engineering path from the current code

Keep the current research method, native workspace, clean source executor, and reviewer. The first missing step is a way to start **before** the target runtime is known. Today `prepare` needs an image and command that a person has prepared. A generic setup session must be able to inspect the authorized source and build files without target-effect rights. It can propose a runtime image, dependency closure, and commands. The host then checks the signed scope, builds or selects that image under allowed network and resource rules, and pins it before research starts. Setup failure becomes a clear blocked result, not a request for a human to choose the next research method.

Make the remaining handoffs agent-driven under the host's existing authority checks:

1. Let the setup agent create a target profile, threat model, and build plan from the new target. The host returns a ready or blocked receipt with exact input hashes. Do not require an operator to write the target build command. Keep secrets and unapproved network access out of the run. Use the same shared allowance and human-touch record across setup and research.
2. Let the agent request bounded execution and fresh review through a structured file in its workspace. The host validates each request against the plan, runs the existing executor, and returns a receipt. Extend the continuation controller beyond research turns so it can complete this loop. Use the current source executor first. Generalize service capture before claiming the same evidence quality for service targets; the present capture path is pinned to Kanboard.
3. Bind the agent's proposed patch diff to exact original and patched bytes. Use the same effect, normal-function, and variant checks on clean copies. The fresh reviewer challenges the causal link. Do not add a separate patch service if the existing executor and reviewer can support this contract.
4. Let the controller carry the run through review and internal closeout. Today `continue` can request a closure review, but a person supplies the review decision. The agent must arrange an independent check, act on a reopen decision, reconcile pending effects, verify cleanup, and report the terminal state without manual research steering. Record all human touches and charged cost. Test interruption and uncertain-effect recovery. Raise time limits only with matching approval and operational proof. Keep model and provider adapters behind the same research and evidence contract; qualify a new adapter on the same unseen evaluation set.

The agent may improve a target-local script during a run. A reusable harness change is a separate candidate. Test it against the prior version with the evaluator held fixed before it becomes the default. This preserves the user's model-upgrade goal: a stronger model can choose better work without inheriting a large fixed script of yesterday's tactics.

The prompt-seed idea applies to the research goal and rules. Keep the scope, evidence standard, tool meanings, and stop rules as versioned inputs. Let a stronger model choose better tests and build better target-local scripts. Do not regenerate the authority or evidence control code from a prompt at each model change. That code must stay pinned and must pass the same checks. Run new models on unseen cases before claiming that an upgrade improved the system.

## Threat model in each engagement

The user has settled its placement: `engagements/<id>/THREAT_MODEL.md` belongs beside the target-local `scope.md` during setup. The agent writes it from pinned source and facts in the scope, with no review before the run. It states assets, attacker starting position, trusted roles, deployment conditions, attacker-reachable entry paths, and security properties. It cites evidence and marks unknowns. It helps the researcher decide which claims are reachable. It does not name the flaw or grant permission. Only the signed scope grants authority. If the two files conflict, the run must follow the scope. A claim that depends on an unverified threat-model fact stays unresolved until an independent check supports it.

The newer route has **no native scaffold directory**. Its [source bootstrap](../../skills/source-engagement-bootstrap/SKILL.md) creates a target-local scope and separate brief; the shared `_TEMPLATE` is for legacy queue work. Native `prepare` currently freezes the source, scope, and brief, then mounts the brief and workflow read-only. It has no separate threat-model input. The smallest robust implementation is to freeze the target-local threat model as one more read-only input, hash it in the plan, and show it on first research and resume. Keep it outside the source export. Putting it into the copied source changes target identity and the hard-pinned T01 case. New native setups can require the file while old sealed plans retain their original meaning. If evidence contradicts an assumption, the agent records the correction during the run and rechecks affected claims. The frozen file stays as the run's original input. A later run uses a new pinned version. A correction cannot widen the signed scope. See [prepare and plan](../../tools/native_research.py).

## What the new sources add

| Proposal | Useful part | Limit and first decision |
| --- | --- | --- |
| Target threat model | Name assets, starting actor, trusted roles, deployment conditions, and security properties before judging a claim. | Create it for each engagement from target facts. Test both a trusted-role false lead and a reachable path in evaluation. |
| Narrow agent assignments | A bounded responsibility can reduce missed code in a large audit. Agents must follow calls across files. | Let the agent split work when the target needs it. Measure whether this improves valid coverage and total cost. Do not make one file-per-agent a rule. |
| Several models on one scope | Independent searches may find different leads. | Test this after a baseline. Count unique replayed results, false claims, cost, and human work. Model agreement is not an oracle. |
| Escalate a validated result | Test whether a supported effect reaches more impact under the same actor and permissions. | Use a new observed effect and control for each stronger claim. Do this when the expected value and signed ceiling justify it; do not require an escalation attempt for every low-impact result. |
| Track code read | A read trace can show files or lines an agent did not open. | Treat it as a gap signal only. It cannot show understanding, reachability, or absence of flaws. Review source disclosure before sharing traces. |
| Local GitHub issue search | Issues can suggest intended behavior, prior failures, affected versions, and duplicates. | Call this **issue context**, not an oracle. The agent must work without it. Trial a small, pinned snapshot only when a run shows a useful retrieval or duplicate problem. |

The five audit techniques are from [nisedo's 11 November article](https://x.com/nisedo/status/2120508560182325500). They are experience-based recommendations, not controlled OSLit results. That article recommends human review of an agent-drafted threat model. The [OpenAI threat-model skill](https://github.com/openai/codex-security/blob/main/plugins/codex-security/skills/threat-model/SKILL.md) requires checks against actual runtime boundaries and source evidence. The user chose an agent draft without a pre-run human review. [agentcov](https://github.com/trailofbits/agentcov) records what an agent read; it does not qualify the reasoning or result. The current native workflow already calls for controls, disconfirming tests, connected effects, clean replay, and fresh challenge. A new document or tool must improve the observed work, not duplicate those rules.

[OpenAI's November pipeline report](https://openai.com/index/a-thousand-fewer-paths-to-root/) gives two checks that matter here. First, 20 of 200 early reported root exploits used a different flaw from the one assigned. The result alone did not prove the claimed path. The team added an independent causal check. Second, the report says that stronger models needed less technique orchestration: a library of 103 techniques helped the earlier model, but added only 1.5 percentage points with the later model. These are OpenAI's reported results, not OSLit results. They argue for observing the full causal path and measuring any new tool against the current model. The report also describes patch review for attack variants and normal function, and a stopping rule for attempts that make no progress. This is a reason to define useful progress, not to stop at the first failed test.

[FORGE's three-month Linux kernel lookback](https://forge-blog.github.io/posts/linux-kernel-3-month-lookback/) reports 26,502 raw scan results, 621 cases with proof evidence, 59 public reports, and 38 mainline fixes at publication. These are author-reported counts. The same article reports more than four person-months of human review and patch work. Its long calendar span is a program result, not proof that one agent worked alone for days. It credits NebuSec with one independent discovery and severity analysis; it does not by itself prove a broad partnership or unattended delivery. The transferable measure is accepted results and total human effort after validation, not scan volume. Of the proof-backed cases, 133 were already reported or fixed upstream by submission time. An issue snapshot might help with duplicate work, but it can miss mailing lists, commits, and private reports.

## Tool contract and optional issue data

The user proposed five questions that every tool should answer. Keep the same contract for present and future commands: purpose, use condition, exact invocation, observed evidence, and the narrow conclusion that the evidence supports. Current native examples show why the last field matters:

| Command | Applies when and how to invoke it | Observed evidence | Supported conclusion |
| --- | --- | --- | --- |
| `continue` runs another bounded research turn. | An active run has a valid approval and `NEXT.json`. Use `python3 tools/native_research.py continue --run-root RUN`. | The dispatch journal, receipts, and remaining allowance. | A turn ran or needs reconciliation. This does not prove useful research progress. |
| `source-execute` runs a captured source batch on three offline copies. | A source experiment is ready. Use `python3 tools/native_research.py source-execute --run-root RUN --command-file COMMAND.json`. | Input and output manifests, exit status, and hashes. | The observed output is repeatable under those inputs. This does not prove a security flaw. |
| `review` runs a fresh review on clean copies. | An observer freezes a packet. Use `python3 tools/native_research.py review --run-root RUN --observer-root OBSERVER --selection FILE --selection-sha256 HASH --role reviewer-1`. | Reviewer trace and separate effect/control receipts. | At most a candidate for operator review. This is not a confirmed filing or patch verdict. |

Past GitHub issues can supply leads, intended behavior, and duplicate evidence. They cannot confirm current reachability or impact. The agent must work without them. A later issue tool would search a version-pinned snapshot with the native file tools and return issue IDs, dates, relevant statements, the snapshot hash, and corpus-health status. Its conclusion is only a lead or duplicate hypothesis. The supplied example reports a timeline mismatch (`104` stored, `162` expected), so even its retrieval coverage is uncertain. The native runner disables web search, MCP, and plugins. Today an optional reference file enters the frozen **source** tree and changes its hash. A separate pinned, read-only reference input would make a fair issue-assisted trial possible without changing target bytes. No bulk ingestion is needed for the general workflow. See the [native entry](../agents/native-local-research.md) and [runtime configuration](../../tools/native_research.py).

## Falsifiable proof lanes

1. **Unseen end-to-end cases.** Give the runner only a new authorized target, signed scope, goal, and resources. The agent prepares the runtime, chooses tests, requests review, and closes the internal run. The evaluator may hold a known flaw and fixed state, but these never enter the agent's inputs. One case should require an observed effect, causal control, clean replay, and, when patching is part of its goal, a diff with effect and normal-function checks on clean copies. Include a hard negative that can end covered dry without a patch. Force an interruption. Count setup failures, false confirmations, cost, human touches, and cleanup. A research hint fails research independence even if the effect is real. A blocked or dry run can be correct if it gives exact limits. One pass proves that exact run, not target independence.
2. **Transfer and new work.** Repeat the same operating contract on unseen targets from different technical classes. Do not add a target-specific branch to the harness before the run. The agent may write scripts and setup files in its own workspace. Follow with an unknown target, where a finding needs independent reproduction and affected-party review before a novelty or external-credit claim. Record every start, including misses, invalid claims, patch regressions, and operator rescue. Report a result by target class and resource limit. A finite cohort cannot prove that every target is supported.
3. **Long work and tool value.** Set time and resources from each case. The current 24-hour plan and approval ceiling must change together if a case needs more; a raised timer alone proves nothing. Force context loss and check that hypotheses, effects, authority, and allowance survive. Challenge premature stopping. Count useful experiments, changed explanations, repeated no-progress turns, and leads resolved with evidence. A genuine multi-day run is required for a multi-day reliability claim. Compare each new tool with the same baseline, including cost and human work.
4. **Optional issue trial.** The core run works without past issues. If an observed retrieval or duplicate problem earns an issue tool, compare the same model, target class, access, and allowance with and without a frozen issue snapshot. Include stale and misleading issues. Measure better experiments and duplicate detection, not just more retrieved text.

Company proof is downstream of this engineering work. An affected-party check, research credit, and paid repeat are separate evidence. For OSLit's initial autonomy claim, the accepted population is ordinary supported EVM/Solidity work under company decision DEC-0060. Other targets can prove engineering transfer, but they do not enter that denominator. Research independence and non-founder product operation have separate passes under DEC-0061. The repository's current authority gates still apply. A full future autonomy claim needs evidence that replaces those gates; a plan cannot waive them.

## Grilling decisions

- **Decided:** When a run includes patching, the first patch result is a pinned, independently reviewed local diff with the original effect and normal-function checks. A pull request or merge is a later external step. A dry or blocked run needs no patch.
- **Decided:** The agent drafts the threat model without a pre-run human review. The signed scope stays authoritative. Material claims that depend on an unverified assumption need an independent check before confirmation.
- **Decided:** The first discovery run is blind to prior issues. A separate trial may test an issue snapshot.
- **Decided:** A hidden known flaw can be used to evaluate the complete workflow. It is never a required input to a production run. An unknown-target run tests new discovery separately.
- **Decided:** The run time limit depends on the case and allowed resources. Multi-day capability is still a later proof need, not a fixed time rule for the first case.
- **Decided:** If evidence contradicts the threat model, the agent records a correction in the run and rechecks affected claims. The original input stays frozen; a later run uses a new version.
- **Decided:** A negative run reports covered paths, limits, and unresolved paths. It does not claim the target has no RCE.
- **Decided:** Start with the current tools. Add a focused tool when a run shows a missing experiment or a measured gain. Each tool must state its purpose, use condition, invocation, observed evidence, and supported conclusion.
- **Corrected direction:** The agent owns the internal engagement from setup through hypotheses, experiments, review handoffs, result, cleanup, and closeout. Patch work applies when the goal calls for it. No human research steering is assumed. A target-specific script is created inside the run; it is not a permanent branch in the harness.
- **Pending input for evaluation:** The user will provide a fresh target. Its facts select an environment and signed scope. They do not define the general architecture.

For the first source-only review, the host can enumerate protected [source execution receipts](../../tools/native_research.py). The current per-turn snapshots do not preserve prior post-turn checkpoints or raw native tool output. If a material claim depends only on that missing data, review stays incomplete. Copying the whole raw tool stream into durable evidence would risk storing target data or secrets; the existing [review text filters](../../experiments/native-review-qualification/fresh_review.py) cannot prove safe redaction.

No target was run and no issue corpus was imported for this draft. The central risk is that operator setup, host-only evidence commands, or target-specific capture make an assisted result look autonomous. The next engineering work must remove those handoffs under the existing authority and evidence controls.
