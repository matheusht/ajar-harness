## Triples

### T1 — [STRONG] Private-asset double-spend → `throw` in async completion path → full-node process crash (uncaught)
- **mechanism:** `validation.js:2129–2131`
  ```js
  function onDone(err){
      if (err && objAsset && objAsset.is_private && !conf.bLight)
          throw Error("spend proof didn't help: "+err);
      cb2(err);
  }
  ```
  The throw fires in the *completion callback* of `checkForDoublespends` (which runs inside
  `conn.query`'s async callback → `async.eachSeries` final callback → `checkInputDoubleSpend`'s
  `onDone`), i.e. NOT inside an async iterator. **Verified by micro-test:** async 2.6.4 catches
  throws inside iterators/tasks but a throw in the nested completion callback invoked from a
  db-query callback escapes as `uncaughtException` (reproduced the exact nesting: `forEachOfSeries`
  iterator → `setImmediate` (db callback) → nested `eachSeries` finalCb throws → process exits).
  Call stack: ws message → `onWebsocketMessage` (`network.js:4112`, no try/catch) →
  `handleJoint` 1057 → `validation.validate` 117 → `validateMessages` → `validatePayment` 2054 →
  `validatePaymentInputsAndOutputs` 2122 → `checkInputDoubleSpend` → `checkForDoublespends` 1655 →
  conflict record found (included in ancestry, sequence 'good' or too-young) → `cb2(error)` chain →
  `onDone` → **throw → process crash**.
- **reachability to the throw:** the private path (broadcast units with private-asset payments are
  rejected earlier via `validatePayment` "asset privacy mismatch" at 2078 because `bPrivate` is
  unset). The reachable entry is the private-payment-chain flow:
  `network.js:2269/2333` → `private_payment.js:23` → `divisible_asset.js:17/171` or
  `indivisible_asset.js:239` → `validation.validatePayment` with `bPrivate: true` (set by
  `initPrivatePaymentValidationState` 2665). No try/catch wrapper in that chain.
- **concrete input construction:** locally (lab): (1) define a private asset (auto-destroy,
  non-transferrable, fixed denominations per `validateAssetDefinition`), (2) create private chain A
  that spends private output X and gets recorded; (3) create private chain B whose ancestry
  *includes* A and which re-spends the same hidden output X (self-contradictory double spend, spend
  proof cannot "help" because the conflict is genuine); (4) submit B to a full node. Expected: node
  crashes with `Error: spend proof didn't help`. Negative control: identical double spend on a
  PUBLIC asset must produce a clean nonserial rejection (`ifUnitError`, no crash); and the same
  private double-spend on a LIGHT node must cleanly reject (the `!conf.bLight` gate — this is the
  05f291d8 fix boundary, confirming the asymmetry is deliberate for light, accidental for full).
- **expected outcome:** full-node crash (uncaughtException), repeated on each re-delivery of B
  (crash-loop until peers stop sending B or node is patched). All full nodes processing B crash
  deterministically.
- **DoS-coordination note (for orchestrator):** B is an *invalid/nonserial* unit; the network does
  not include it; recovery is a node-side catch (no network coordination) → per program-policy this
  is likely OUT of scope as a pure node-crash DoS — but it is a genuine robustness defect
  (validation must never crash the process on attacker input) and worth reporting as defensive/Medium
  context, and the crash-loop property deserves the operator's judgement. This is the f1→f8
  (private payments) hand-off lead.
- **status:** candidate (suspected_signal — mechanism + construction complete; needs lab
  verification in round 1+).

### T2 — [MEDIUM] `validateAATrigger` `count_primary_aa_triggers > 1` rule lacks the 277fad7 disjunct (old-DAG bypass sibling)
- **mechanism:** `validation.js:1025–1028`
  ```js
  if (objValidationState.count_primary_aa_triggers > 1) {
      if (objValidationState.last_ball_mci >= constants.pemCurvesFixMci)
          return callback(`more than 1 primary AA trigger`);
      if (storage.getMinRetrievableMci() > constants.pemCurvesFixMci)
          return callback(createTransientError(`more than 1 primary AA trigger`));
  }
  ```
  The permanent rejection is gated ONLY on `last_ball_mci >= pemCurvesFixMci` — no
  `|| !hasBall && getMinRetrievableMci() >= pemCurvesFixMci` disjunct, unlike the sibling rules the
  team just fixed in `277fad7` (max_aa_responses=0 at 996; one-output-per-asset at 1030) and the
  other `pemCurvesFixMci` gates that carry the disjunct (vote 1813, attestors 2735, private-asset
  conditions 2784, formula/validation.js ×17).
- **bypass:** attach a unit with 2+ AA-trigger outputs to an old part of the DAG
  (`last_ball_mci < pemCurvesFixMci`) on a node whose `getMinRetrievableMci() <= pemCurvesFixMci`
  (fresh/syncing node, or during the migration window) — the permanent branch doesn't fire and the
  transient branch doesn't fire either. On a caught-up node the transient branch eventually sticks
  (unit stays unhandled until purged) — so the bypass is node-state-dependent: it matters for nodes
  behind, and as a divergence between two nodes at different sync states (one accepts, one defers).
- **concrete input construction:** a unit with two payment outputs to two different AA addresses,
  attached to parents whose last ball is below `pemCurvesFixMci`. Expected: accepted on a node with
  `minRetrievableMci <= pemCurvesFixMci`; deferred (transient) on a caught-up node.
- **impact:** cross-node acceptance divergence (consensus-relevant if the AA engine processes
  multi-trigger units differently) + tps-fee computation (validateTpsFee keys on
  `count_primary_aa_triggers`). Needs the F11 (AA engine) + F2 (tps fee) cross-check to size.
- **negative control:** the same unit attached at/after `pemCurvesFixMci` is rejected permanently;
  a single-trigger unit below the MCI is accepted on both node states.
- **status:** candidate (suspected_signal — needs AA-engine confirmation of what multi-trigger
  acceptance changes).

### T3 — [MEDIUM] `validateAATrigger` early-return below `v4UpgradeMci` — complete old-DAG AA-trigger validation gap
- **mechanism:** `validation.js:986–992`
  ```js
  if (objValidationState.last_ball_mci < constants.v4UpgradeMci || objValidationState.bAA || !objValidationState.last_ball_mci) {
      if ("max_aa_responses" in objUnit)
  ```

  For any non-AA unit attached below `v4UpgradeMci`, ALL AA-trigger validation is skipped

- **concrete input construction:** unit with 5 outputs to 5 different AA addresses, parents attached
  below `v4UpgradeMci`. Expected: passes `validateAATrigger`; the AA engine then decides what a
  multi-trigger unit does.
- **impact:** depends on F11 — does the AA engine process such units' triggers? If yes, the
  trigger-count protections are meaningless for old-DAG attachments. Cross-family hand-off.
- **negative control:** same unit above `v4UpgradeMci` → trigger rules enforced.
- **status:** candidate (weak–medium; needs AA engine cross-check).

### T5 — [HELD / NEGATIVE] Money arithmetic is precision-safe by design (MAX_CAP = 9e15 < 2^53)

  validation path.** Residual surfaces: formula/ (F5) and fee math (F16).

## Held or refuted observations (with the decisive control)

  fixed in 277fad7/048fbdb carries the `!hasBall && getMinRetrievableMci() >= X` disjunct
  (996, 1030, 1813, 2735, 2784, formula/validation.js 17 sites). T2 (`count>1`) is the one
  remaining non-disjunct sibling in the permanent branch — the hunt found exactly one, not a family.
  *Decisive control:* grep of all `last_ball_mci >= constants.` sites + per-site disjunct check.
- **H2 — check-order consistency (Q4):** all entry paths converge on `validation.validate`:
  `handleJoint` (network), `handlePostedJoint`→`handleJoint`, `handleSavedJoint`→`handleJoint`
  (unhandled joints re-validated, not trusted), and catchup (`catchup.js` validates hashes+ball
  chain first, then full validation on write via `handleSavedJoint`). No path found that stores a
  unit without the full pipeline.
- **H3 — fail-open (Q3):** none found on the main path. Validation errors route to
  `ifUnitError`/`ifJointError`/`ifTransientError`; the writer is invoked only from `ifOk`
  (`network.js:1165`). `joint_storage` persists *unhandled* (missing-parent) joints, and those are
  re-validated when parents arrive — not a fail-open.
- **H4 — fields trusted without validation (Q2):** the structural whitelists (`hasFieldsExcept`) are
  tight; all consensus-bearing fields (unit hash, payload hashes, parent list vs hash-tree,
  last_ball vs ball, commissions vs `objectLength`, signatures via `validateAuthors`) are
  independently re-derived. Residual trust points are the era-consistency rules (T2/T3/T4/T6) and
  the AA-definition guard gap (T7).
- **H5 — `max_aa_responses=0` on ball-less units is refused early** (`validation.js:277–278`),
  independent of the 277fad7 gate — defense in depth exists.
- **H6 — unsigned joints refused on network paths** (`network.js:1210`, `handlePostedJoint`
  "unsigned unit"; `network.js:1082` ifOkUnsigned path) and `60850f6` added the network-level
  refusal. Held.
- **H7 — the `"no src_coin"`/`"no src_output"` throws (2444–2447) are inside the input iterator,**
  i.e. caught by async → clean error, NOT crashes (contrast T1, which is in the completion path).
