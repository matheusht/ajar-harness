## Triples

### T1 — `is_valid_merkle_proof` formula construct is vacuously satisfiable (merkle root self-chosen)

- **mechanism:** `is_valid_merkle_proof(element, proof)` (formula/evaluation.js:1763) calls
  `merkle.verifyMerkleProof(element, objProof)` (merkle.js:84). `verifyMerkleProof` returns
  `the_other_sibling === proof.root` — the **root is read from the attacker-supplied proof itself**
  (merkle.js:100). With `siblings: []` and `index: 0`, the loop never runs, `the_other_sibling =
  hash(element)`, so the check passes iff `proof.root === hash(element)` — which the caller
  (attacker) can always arrange. The proof deserialization path accepts attacker strings
  (`deserializeMerkleProof`, merkle.js:75; `proof.length > 1024` cap only bounds size).
- **source→sink→path:** attacker-crafted AA trigger/response formula `['is_valid_merkle_proof', X,
  proof]` → formula/evaluation.js:1763 → merkle.deserializeMerkleProof (1789) →
  merkle.verifyMerkleProof (1794) → `cb(res)` with res=true for any X when
  `proof = "0-" + base64(hash(X))` (single-element "tree").
- **concrete input construction:** in an AA formula: `is_valid_merkle_proof("evil_value",
  "0-" + sha256_base64("evil_value"))` → returns `true` for ANY string, no tree membership required.
- **expected outcome:** the predicate returns true for an element that is not in any real merkle
  tree — the "proof" proves only self-consistency.
- **negative control:** the language's OTHER merkle primitive, `['in merkle', ...]`
  (definition.js:1006-1016), binds the root to ground truth: `dataFeeds.dataFeedExists(..., '=',
  proof.root, ...)` requires the root to be an on-chain published feed value, and the proof comes
  from the authentifier set. That construct is sound; the formula construct lacks the root-binding
  step — the difference is the flaw.
- **impact assessment (honest):** any AA logic that uses `is_valid_merkle_proof` WITHOUT separately
  pinning `proof.root` against a trusted value is bypassable. Individual AA logic is out of scope;
  the construct is part of the in-scope AA engine (SF-9/SF-10). Impact is conditional on AA usage →
  needs_review, engine-level footgun, likely informational/medium depending on usage. Also gated:
  the sibling-string checks apply only `mci >= pemCurvesFixMci` (all new units post-fix).

### T2 — unbounded catchup chain / hash tree responses bypass the depth+nodes guard (DoS while syncing)

- **mechanism:** `handleCatchupChain` (network.js:2112-2114) passes the peer's response straight to
  `catchup.processCatchupChain` with **no** `isTooDeeplyNestedOrHasTooManyNodes` check and **no array
  length caps** on `unstable_mc_joints`, `stable_last_ball_joints`,
  `witness_change_and_definition_joints`, `proofchain_balls` (catchup.js:147-170 — only
  type/shape checks). `processHashTree` (catchup.js:461) likewise accepts an unbounded `arrBalls`
  and performs per-ball `getBallHash` + multiple DB queries inside one transaction under
  `mutex.lock(["hash_tree"])`. Per-joint work in `processWitnessProof` includes
  `hasValidHashes` (SHA256) plus ECDSA authentifier verification per witness author
  (`validateAuthorSignaturesWithoutReferences` → `Definition.validateAuthentifiers`, validation.js:2854).
- **source→sink→path:** malicious peer → `handleCatchupChain` (network.js:2112) → unbounded
  `unstable_mc_joints` (catchup.js:152) → `witnessProof.processWitnessProof` (catchup.js:180) →
  per-joint hash + signature verification. Contrast: joint downloads ARE guarded
  (network.js:975, `isTooDeeplyNestedOrHasTooManyNodes`), and the server-side chain length is capped
  (`MAX_CATCHUP_CHAIN_LENGTH = 100000`, catchup.js:13) — the client accepts unbounded input from the
  same message family.
- **concrete input construction:** peer responds to `catchup` request with
  `{unstable_mc_joints: [100000 well-formed witness joints], stable_last_ball_joints: [...], ...}`
  → CPU spent on 100k hash + ECDSA verifies; or `get_hash_tree` response with a huge `arrBalls`.
- **expected outcome:** prolonged CPU/DB churn on the syncing node; possible stalls of the
  `catchup_chain`/`hash_tree` mutexes.
- **negative control:** the same message with a bounded chain (normal sync) completes; the guard
  exists on the sibling joint path.
- **scope verdict (per DoS coordination rule):** a node-side cap resolves this without network
  coordination → **out of scope** for the bounty (temporary single-node disruption). Recorded as a
  hardening note; not a finding candidate unless it escalates to a deterministic crash that requires
  coordination (see Gaps — crash path not yet proven).

### T3 (held/negative) — catchup trust chain is cryptographically anchored at every layer

- **mechanism (why it holds):** the sync trust chain is layered and each layer's verification is
  named: (1) witness signatures verified per witness author — `processWitnessProof` →
  `validateUnit` → `validateAuthorSignaturesWithoutReferences` (witness_proof.js:252-300) → ECDSA
  via the definition language; (2) majority-of-witnesses required to anchor the last-ball
  (witness_proof.js:117-122, `MAJORITY_OF_WITNESSES`); (3) proof-chain balls hash-verified against
  `getBallHash(unit, parent_balls, skiplist_balls, is_nonserial)` AND each ball must chain to the
  witness-anchored set (catchup.js:197-220); (4) hash tree: root must equal the next
  `catchup_chain_balls` element, every ball's hash verified, ancestry completeness enforced via the
  `childlessBalls` check (catchup.js:494-543); (5) downloaded joints: ball↔unit bound to the
  verified hash tree via `storage.assocHashTreeUnitsByBall` (`validateHashTreeBall`, validation.js:516-528)
  and the `bCatchingUp && !objJoint.ball` refusal (network.js:1277, the a7eb776 fix); (6) stable
  joints chain by `current.ball === previous.last_ball` with unit hashes verified (catchup.js:235-250),
  anchored to the witness-signed last ball.
- **decisive control per layer:** listed above with file:line. No layer accepts a value it cannot
  verify against a previously-anchored value. This family is where the recent hardening
  (a7eb776, 615e258, e01ba3e, 6fe2938) concentrated, and the design is coherent.
- **verdict:** held (negative). No "accept a false proof" path found in the catchup chain, hash
  tree, or ball↔unit binding.

### T4 (weak, note) — unstable-joint ancestry check is not an MC-membership check

- **mechanism:** `processWitnessProof` requires each unstable MC joint to be an ancestor of the
  previous one (`arrParentUnits.indexOf(objUnit.unit) === -1` → error, witness_proof.js:96-100) and
  majority of witnesses to have authored units in the presented chain — but nothing verifies the
  joints are actually ON the main chain (no `is_on_main_chain` requirement in the catchup path; the
  receiving node does not yet know these units).
- **source→sink→path:** malicious peer → fabricated-but-real-signature witness segment (a stale
  branch) → the syncing node anchors last_ball to it. Requires the peer to possess real
  witness-signed units (stale history is publicly available, so feasible for an eclipse-style
  attacker).
- **expected outcome:** syncing node builds a stale/alternate view until it connects to honest peers
  (standard sync attack).
- **negative control:** for balls the receiving node already knows, the "first chain ball must be
  stable and on mc" check uses the node's OWN DB (catchup.js:262-280); genesis fallback accepts a
  full chain to genesis only with witness signatures (can't be forged).
- **verdict:** weak; not a code-level acceptance bug, requires network-level position (eclipse);
  no direct fund loss; likely out of scope. Recorded for the orchestrator's network family.

### T5 (note) — `readHashTree` range amplification (both directions)

- **mechanism:** `readHashTree` (catchup.js:391-431) serves every unit in `[from_mci, to_mci]` with
  no cap; a requesting peer can ask for a huge range and the serving node builds an unbounded
  response; the requesting node's `processHashTree` does unbounded per-ball DB work (T2).
- **verdict:** DoS, node-side fix resolves → out of scope per the coordination rule. Hardening note.

## Held or refuted observations (with the decisive control)

- **Held:** no false-proof acceptance in the catchup chain / hash tree / ball binding (T3 — the
  layered anchor controls above).
- **Held:** `in merkle` definition predicate binds proof.root to an on-chain data feed via
  `dataFeedExists` (definition.js:1018) — the secure pattern the formula construct (T1) lacks.
- **Held:** merkle tree construction duplicates trailing nodes for odd counts and `verifyMerkleProof`
  handles the duplicated-trailing-node case (merkle.js:34-36, comment at :88) — no odd-count
  membership gap found.
- **Held:** archiving reorg queries unspend outputs only when no OTHER unit spends the same output
  (`NOT EXISTS` guard in each unspend query, archiving.js:107-160) — double-spend reorg handling is
  careful; void-vs-remove keeps witnesses/authors (archiving.js:74-105).
- **Held:** the `throw Error("processWitnessProof: no last ball units")` (witness_proof.js:128) is
  unreachable — the joint that crosses `MAJORITY_OF_WITNESSES` also pushed its `last_ball_unit`
  (checked before the push at :119-122). No crash path.
