## Triples (candidate hypotheses)

### T11-1 — S12: JS Number precision in AA composer working-balance arithmetic beyond 2^53 (weak, needs lab)
- **Mechanism:** `aa_composer.js` keeps the AA's working balance in JS `Number`
  (`objValidationState.assocBalances[address][asset] = row.balance + trigger.outputs[row.asset]`
  at :504; `net_target_amount = payload.outputs.reduce((acc,o)=>acc+(o.amount||0), size)` at
  :1091; deltas in `updateFinalAABalances` :720-755). `MAX_BALANCE = 2**63-1 - 128*MAX_CAP`
  (:49) — far beyond `Number.MAX_SAFE_INTEGER` (2^53). Comment at :48 admits precision loss
  "inconsequential". `checkBalances` (:2015-2025) tolerates up to `1e-5` relative discrepancy
  for balances above 2^53.
- **Source→sink→path:** AA state `updateInitialAABalances` (SQL `aa_balances.balance` BIGINT)
  → JS Number addition → spend decisions (`not enough balance` checks :970, `issueAsset`
  :1160-1190) → response unit outputs. Precision loss at >2^53 balances can make the composer
  compute a balance slightly different from the real output sum.
- **Concrete input construction:** an AA holding >2^53 base units (9e15 MAX_CAP per output ×
  ≥2 outputs, or a whale AA), triggered to compute change/issue amounts near the boundary.
- **Expected outcome:** change_amount or available-balance comparison off by a few units
  (relative, ~1e-16). Direction matters: a computed balance HIGHER than real → spend attempt
  rejected at unit validation (bounce, harmless); LOWER → liveness only. Individual amounts are
  bounded by MAX_CAP=9e15 < 2^53, so no single-amount precision loss.
- **Negative control:** amounts ≤ 2^53 → exact arithmetic; and the real ledger (outputs/inputs)
  is integer-exact in SQL, so any composer overspend is refused by `validateAndSaveUnit`.
- **Verdict:** real precision-loss zone, but impact bounded by real-output validation. **Low
  severity; keep for a lab check** — the interesting sub-question is whether a crafted balance
  near a boundary lets an AA *issue* slightly more of its own asset than the cap (issue_amount
  math at :1180-1190 uses `objAsset.cap || (target_amount - total_amount)`).

### T11-2 — definition-change / nested-AA recursion disabled in AA validation (weak)
- **Mechanism:** `aa_validation.js` `validateMessage` case `'definition'` (:389-403) only
  shape-checks a nested AA definition (`['autonomous agent', non-empty-object]`); the recursive
  `validateAADefinition` call is **commented out** (:404-405, "interrupt the call stack to
  protect against deep nesting").
- **Path:** nested definition inside an AA's template messages → shape-checked only → the AA
  emits it as a real definition message → `validation.js` case `definition` (:1740-1790) runs
  full `validateAADefinition` on the concrete definition at execution time.
- **Concrete input:** AA template containing a nested definition with malformed inner messages.
- **Expected outcome:** accepted at AA-definition time (shape only); the malformed content never
  executes because only *definition messages* register AAs and those are fully validated.
- **Negative control:** a nested definition actually emitted as a definition message IS fully
  validated (validation.js:1765) → malformed content rejected → bounce.
- **Verdict:** defense-in-depth gap only, inert. **Held.**

### T11-3 — light-vendor AA definition inserted without validateAADefinition (weak, wallet-side)
- **Mechanism:** `aa_addresses.js` `readAADefinitions` (:66-107): unknown addresses are fetched
  from the light vendor (`light/get_definition`), chash is verified, but the definition is
  inserted into `aa_addresses` via `storage.insertAADefinitions(db, ..., mci=0, ...)` **without
  `validateAADefinition`** (validation.js's consensus path is bypassed in this wallet path).
- **Path:** wallet compose (`checkAAOutputs`) → `readAADefinitions` → insert with mci=0.
- **Concrete input:** a hub returns a syntactically-chash-valid AA definition whose template
  would fail validateAADefinition (e.g., a definition with getters referencing an unknown
  function).
- **Expected outcome:** wallet node treats the address as an active AA (mci=0) before its
  definition stabilizes; premature trigger activation. Impact: local wallet behavior, not
  consensus (the trigger handling is still full-node validation). Also `determineGetterProps`
  with validation_mci=0 could THROW in the wallet path for getters that are mci-gated.
- **Negative control:** for full nodes, the consensus path inserts the same definition at its
  stabilization mci with identical content, so no state divergence for honest definitions.
- **Verdict:** wallet-side, hub-trusted by design (light model). **Weak; flag for wallet
  surface review, not a consensus finding.**

### T11-4 — estimation (bAir) runs against the last unit, not the last stable unit (weak/UX)
- **Mechanism:** `estimatePrimaryAATrigger` → `readLastUnit` (`aa_composer.js:321-336`:
  `SELECT unit, main_chain_index FROM units ORDER BY main_chain_index DESC LIMIT 1`) — may
  include an unstable unit as the reference MC unit, while real execution uses the trigger's
  stable MC unit. Header comment :71-72 documents "not 100% accurate".
- **Verdict:** documented estimation inaccuracy; wallet UX/info only. **Held (not a finding).**

## Held or refuted observations (with the decisive control)

1. **Forged unsigned AA response injection — REFUTED (3 independent layers).** The classic
   attack (submit a unit authored by an AA address, which has no private key, to spend AA funds)
   is blocked: (a) `network.js:965` refuses any joint containing `"unsigned"` from peers;
   (b) `validation.js:146-148` transient-errors `"possible AA"` for single-author units with no
   authentifiers and no content_hash; (c) `validation.js:1197` returns
   `createTransientError("will not validate unit signed by AA")` for AA-authored external
   units; (d) `ifOk`/`ifOkUnsigned` throw if called on the wrong joint type (validation.js:483-486,
   network.js:1129/1135). AA units are only created locally via `validateAndSaveUnit` with
   `objJoint.aa=true` (aa_composer.js:1966-1995). **Decisive control: 60850f6 + the transient
   errors; a forged AA unit cannot reach `ifOk`.**
2. **S1 disjunct migration in the AA-trigger rules — COVERED-DRY for this rule family.**
   `validateAATrigger` gates at validation.js:996 (`max_aa_responses=0`),
   :1030 (single-trigger output-count rule), :1025/:1027 (multi-trigger), :1194
   (definition-not-found), :1896 (system param bounds) all carry the
   `!hasBall && getMinRetrievableMci() >= X` disjunct. No bare `last_ball_mci >= constants.X`
   gate found in the AA trigger/definition validation rules. **Cross-family flag:**
   `validation.js:741` (non-AA unit must have ≥1 non-AA parent) still lacks the disjunct — a
   unit attached to an old DAG part skips it; direction is "allows what the rule forbids" —
   hand to F1/F2 for parent-validation impact analysis.
3. **Getter-mci divergence (determineGetterProps throw at insert vs validation) — REFUTED.**
   Traced the mci sources: for AA-defined AAs both validation (validation.js:1761 `top_mci =
   aa_mci || last_ball_mci` with `aa_mci` = trigger mci) and insert (writer.js:622
   `initial_trigger_mci`) use the trigger mci; for regular AAs validation uses last_ball_mci and
   insert (main_chain.js:1539, `definer_last_ball_mci`) reads the same last-ball mci. The
   getter-to-getter read (`readAAGetterProps` at `to_mci`) is therefore consistent; a getter
   referencing a not-yet-defined getter fails at validation and the unit never reaches insert.
   The `throw` in `determineGetterProps` (aa_validation.js:798-800) is unreachable for
   validated definitions. **Decisive control: mci provenance trace.**
4. **`variableHasStringsOfAllowedLength` unbounded recursion — REFUTED.** Deeply nested
   parameterized-AA `params` cannot overflow the stack because the whole unit is depth/nodes
   capped first: `isTooDeeplyNestedOrHasTooManyNodes` (string_utils.js:260, depth 100 / nodes
   10000) runs at validation.js:153 before validateAADefinition.
5. **`app='state'` spoof — REFUTED.** `state` is in `aaApps` (aa_validation.js:31) so it passes
   the app-list check (validation.js:1619), but `validateInlinePayload` has no `state` case →
   `default: return callback("unknown app")` (validation.js:1825-1827) → any unit carrying
   app='state' is rejected. State updates only happen via the AA composer's evaluated state
   formula (aa_composer.js:1577-1597), never via a message.
6. **Trigger/response-count bounds — HELD.** `max_aa_responses` validated (validation.js:181-187
   ≤ MAX_RESPONSES_PER_PRIMARY_TRIGGER=10, =0 rejected for new units); composer bounces at
   `arrResponses >= MAX_RESPONSES_PER_PRIMARY_TRIGGER` (aa_composer.js:1835) and per-trigger
   `max_aa_responses` (:1838); a second primary trigger from the same unit is bounced (:1850).
7. **AA response structural controls — HELD.** Response units must be inline
   (validation.js:1622-1624), single author (validation.js:1128), no `tps_fee`
   (validation.js:1053-1056), deterministic output/input ordering (`readStableOutputs`
   aa_composer.js:1109-1118 ORDER BY main_chain_index/unit/output_index), deterministic
   secondary ordering (`ORDER BY address` :1723).
8. **Balance-vs-storage check — HELD.** `updateStorageSize` (:1517-1555) refuses state growth
   beyond byte balance when `mci >= aaStorageSizeUpgradeMci`, caps state var value length
   (MAX_STATE_VAR_VALUE_LENGTH=1024), and checkStorageSizes (:2070-2095) enforces the
   kvstore↔aa_addresses.storage_size invariant continuously.
9. **Trigger enqueue on stability only — HELD (note for F2).** Primary triggers are inserted
   only when the paying unit stabilizes on the MC (`main_chain.js:1660-1700`, sequence='good',
   `aa_definition_units.main_chain_index<=mci`), and AA-response→AA payments are handled
   in-transaction via `handleSecondaryTriggers` (aa_composer.js:1721-1765) with revert on
   failure (:1867-1890). The `storage.assocStableUnits[trigger.unit]` access (:1850) is safe
   because primary trigger units are stable by construction.

## Suspected_success candidates

**None at suspected_success level.** No mechanism was proven exploitable in static analysis.
Two leads are worth a round-1 deep-dive with the lab:

- **R1-A (T11-1, S12):** AA composer working-balance arithmetic beyond 2^53 — specifically the
  `issueAsset` self-issue amount math (`objAsset.cap || (target_amount - total_amount)` at
  aa_composer.js:1180-1190) near the cap boundary, and the `checkBalances` 1e-5 tolerance
  window. Requires a local node with an AA holding >2^53 units; the precision-loss zone is
  acknowledged in the code (:48, :2020-2023).
- **R1-B (T11-3):** the light-vendor definition insert without `validateAADefinition`
  (aa_addresses.js:66-107) — determine whether a full-node wallet can be made to run an
  unvalidated definition at mci=0 and whether the `determineGetterProps` throw there is
  reachable (would crash the wallet compose path).
