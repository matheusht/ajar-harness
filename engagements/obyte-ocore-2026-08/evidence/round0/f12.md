## Triples

### T-f12-1 (weak): `getJointHash` uses non-canonical `JSON.stringify` (insertion-order dependent)
- **mechanism:** joint identity hash for the known-bad-joints cache is `sha256(JSON.stringify(objJoint))`
  — key order = object insertion order, not sorted.
- **source→sink→path:** `object_hash.js:118-121` → consumers `joint_storage.js:47`
  (`assocKnownBadJoints[getJointHash(objJoint)]`) and `joint_storage.js:331`
  (`saveKnownBadJoint` — cache + `known_bad_joints` DB table).
- **concrete input:** the same logical joint `{unit: U, ball: B}` vs `{ball: B, unit: U}` — inbound
  joints are `sortObject`'d in `network.js:1219/1281`, locally-handled joints may not be — two encodings,
  two hashes.
- **expected outcome:** cache miss for an already-known-bad joint → duplicate validation work. A
  malicious peer can keep re-sending differently-ordered encodings of the same bad joint → repeated
  full validation (bounded by existing unit-size limits; CPU-amplification is modest).
- **negative control:** `sortObject`-normalized joint → stable hash. **Verdict: not consensus-critical**
  (joint identity is the unit hash, not this cache key). Keep as weak.

### T-f12-2 (medium, latent; cross-family F5): formula `sha256`/`chash160`/`number_from_seed` hash `res.toString()` whose string form is **type-dependent** — MEASURED
- **mechanism:** the formula functions convert Decimal→double-range *but then hash `res.toString()`*,
  and Decimal.toString() vs Number.toString() diverge on PRECISION (measured on pinned commit):
  - `Decimal("12345678901234567").toString() === "12345678901234567"` (exact, decimal.js stores the
    literal digits) but `parseFloat("12345678901234567").toString() === "12345678901234568"`
    (nearest double) — **different hash input for the same logical value**.
  - `Decimal("0.1234567890123456789")` → `"0.1234567890123456789"` vs Number → `"0.12345678901234568"`.
  - Exponent-boundary forms AGREE (decimal.js config `toExpNeg:-7`/`toExpPos:21` deliberately
    "same as for js number", `formula/common.js:11-17`) — my initial 1e-7 hypothesis was refuted by
    test; the divergence is precision, not notation.
  - `toDoubleRange` (`formula/common.js:40-44`): a Decimal below ~2.47e-324 (`val.toNumber() === 0`)
    becomes `new Decimal(0)` — measured: `Decimal("1e-330")` → toNumber 0 → `sha256(1e-330)` hashes `"0"`.
- **source→sink→path:** `formula/evaluation.js:1828` (`sha256`), `1834`, `1889`
  (`number_from_seed`: `seed.toString()`), `chash160` (~1848); helpers `formula/common.js:40-44`.
  Hash feeds AA state/randomness → consensus-bearing if used in state.
- **concrete input:** `sha256(12345678901234567)` with the operand arriving as a JS number (double
  literal, or a data-feed value read via `getFeedValue` → Number) vs as a Decimal (string literal
  converted by `createDecimal` in arithmetic, `formula/evaluation.js:195/254`) — same logical value,
  different hash.
- **expected outcome:** today **deterministic per node** (AA typing is on-chain-determined, same code,
  same inputs ⇒ same type). **NOT a live consensus split.** It IS a live AA-correctness trap (an AA
  comparing `sha256` of a feed-derived number against a literal-derived value never matches) and a
  **latent split**: any path that types the same logical value differently across nodes (a future data
  feed read, a future typing change, `number_from_seed` param typing) diverges consensus.
- **negative control (measured):** `sha256` of the same value with the same type → identical output on
  repeat evaluation.
- **Verdict: hazard, measured, hand to F5** (they own formula evaluation typing).

### T-f12-3 (weak): `'in merkle'` definition predicate lacks the sibling guards added in `e01ba3e`
- **mechanism:** the recent fix (`formula/evaluation.js:1771-1777`) validates merkle-proof siblings
  (non-empty strings, ≤50) for `is_valid_merkle_proof` at `mci >= pemCurvesFixMci`. The **definition
  language's** `['in merkle', ...]` path (`definition.js:1005-1031`) deserializes + verifies without
  any of those guards.
- **source→sink→path:** `definition.js:1016-1022` → `merkle.js:deserializeMerkleProof/verifyMerkleProof`.
  Proof comes from the unit's authentifiers (attacker-chosen, bounded by unit size limits).
- **concrete input:** a definition whose `in merkle` authentifier carries >50 siblings (or empty-string
  siblings via a crafted serialized proof `"0--<root>"`).
- **expected outcome:** longer verification loop (≤ unit-size bound) — bounded CPU DoS on the
  validating node; empty-sibling proofs verify `hash(element) === root` (the trivial case, sound
  because root must equal a posted feed value — see N6). Malformed proofs fail verification → unit
  rejected via `fatal_error`. **Impact: low; incomplete port of the sibling fix.**
- **negative control:** the same malformed proof is rejected by `is_valid_merkle_proof`
  (fixed path) but accepted-then-failed (or slow) on the definition path.
- **Verdict: record as an incomplete-fix sibling (S9 family); no exploit found.**

### T-f12-4 (low, historical): pre-`aa2UpgradeMci` numeric feed keying collapses distinct values within 1 ulp at ≥2^53
- **mechanism:** numeric feed keys are `encodeDoubleInLexicographicOrder(toNumber(value))`; two
  distinct decimal strings ≥ 2^53 that parse to the same double get the SAME `n`-key. A definition
  `in data feed = <value>` queries by the double → can match a feed whose literal value differs.
- **source→sink→path:** writer `main_chain.js:1566-1575` (n-key for ≤16-significant-digit strings when
  `mci < aa2UpgradeMci`), reader `data_feeds.js:dataFeedByAddressExists` (121-145), predicate entry
  `definition.js:926` / `data_feeds.js:dataFeedExists`.
- **concrete input:** pre-upgrade feed `"9007199254740993"` and query value `"9007199254740992"` — both
  double 9007199254740992.
- **expected outcome:** `in data feed = 9007199254740992` returns TRUE for the feed posted as
  `9007199254740993`. **Deterministic across nodes** (same double conversion) — semantic false-positive
  on the predicate, not a split. Post-upgrade, >15-digit mantissas are stored strings-only
  (`bLimitedPrecision=false` ⇒ `toNumber` null) — so the collision is **historical, not live**.
- **negative control:** post-upgrade exact-string `s`-key lookup for the same value.
- **Verdict: low; documented, not exploitable on current chain state.**

  binds `data`, so the hash is fine).
- **expected outcome:** underpaid fee if unreconciled. **Needs F1/F16 confirmation.**
- **Verdict: cross-family lead, transfer.**

## Held or refuted observations (with the decisive control)

- **N1 — lone-surrogate / U+FFFD hash-collision (refuted for units):** `getSourceString` hashes lone
  surrogates as their UTF-8 replacement bytes (Buffer.from utf8), so `"\uD800"` and `"\uFFFD"` produce
  the same hash input — a potential hash-collision on string content. **Decisive control:**
  `validation.js:156` rejects any joint containing lone surrogates or NUL bytes
  (`isObjectWellFormed`) before payload processing; `hasValidHashes` (line 130) runs earlier but only
  computes/compares, never accepts. Device messages (non-joint) aren't well-formed-checked, but the
  alterable envelope fields are E2E-encrypted payload + addresses; no practical tamper path found
  (device.js:150-180 verifies both v1/v2 hash modes, no fail-open).
- **N2 — data-feed delimiter injection (refuted):** feed names/values containing `\n` are rejected
  (`validation.js:1932-1937`, `1944-1946`); numeric feed values must be integers (`isInteger`);
  name/value length caps enforced. The `df`/`dfv` key structure is therefore safe from
  delimiter-injection at the validation boundary.
- **N3 — -0 divergence (not found):** every hashing serializer normalizes -0→0
  (`getSourceString`/`getJsonSourceString` via `toString()`, `JSON.stringify`, `sortObject`,
  `replaceNegativeZero`, `cloneDeep`, `encodeDoubleInLexicographicOrder`). The `22d8fb1` fix was
  formula-evaluation-internal (comparison semantics), not hashing; no hashing-path -0 divergence exists.
- **N4 — canonical serializers are total and deterministic (held, positive):**
  `getSourceString`/`getJsonSourceString` sort keys, throw on null/undefined/empty/NUL, and serialize
  numbers via value-deterministic `toString()`. `sortObject` descends into arrays with a type-stable
  comparator. Unit/payload/ball hashes are cross-node deterministic for valid units.
- **N5 — data feed s/n dual-keying is self-consistent:** writer (`main_chain.js:1566-1575`) and
  readers (`data_feeds.js`) agree on the numeric-vs-string key decision for on-chain MCIs;
  `getValueFromDataFeedKey`/`getFeedValue` round-trip canonical forms.
- **N6 — merkle proof soundness (held):** `verifyMerkleProof` takes an attacker-controlled index and
  sibling list, but the computed root must equal a **posted feed value** (`definition.js:1026-1028`
  queries `dataFeedExists(..., '=', proof.root, ...)`); no second-preimage on sha256 → no forgery.
- **N7 — device-message hash-mode duality (held):** verifier accepts v1 or v2 serialization for
  `message_hash` (`device.js:164-165`); signer computes v1. Compatibility surface only; `\x00` and
  null handling consistent; no fail-open.
