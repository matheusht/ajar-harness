## Triples (candidate hypotheses)

### T-A — CRASH: private divisible-asset double-spend (spend-proof replay) → uncaught throw → deterministic full-node crash
- **Mechanism:** In `checkForDoublespends`'s completion, the caller's `onDone` (validation.js:2276–2280):
  `if (err && objAsset && objAsset.is_private && !conf.bLight) throw Error("spend proof didn't help: "+err);`
  This throw is inside a `conn.query` callback, **outside** `async.series`'s synchronous try/catch. It propagates to the event loop → `network.js:4367` uncaughtException handler re-throws → **process crash**.
- **Source→sink→path:** attacker owns private divisible asset input I (output in their unit A). Attacker sends unit B spending I again (replaying the spend proof — shape S8, spend-proof uniqueness). B validation (validation.js `validateMessages` → divisible transfer step) → src-output query + ownership check passes (B authored by owner) → `checkInputDoubleSpend` (2252) → `doubleSpendQuery` finds A's spend record in `inputs` (2258) → `checkForDoublespends` (1655) → A's author == B's author (no "another address" throw) → not bLight → `graph.determineIfIncludedOrEqual` (A included in B's parents — attacker chains them) → A "too young" (`main_chain_index > last_ball_mci || null`) → `cb2(error)` → `cb(err)` → `onDone(err)` → **throw** → crash.
- **Concrete input construction:** on a local fork, create a private divisible asset; mint to self; send unit A spending it (valid); send unit B (same author, parents include A) spending the same input with the same spend proof; observe the full node crash (exit due to uncaught exception). Negative control: same double-spend with a PUBLIC divisible asset → accepted as nonserial (`acceptDoublespends` → `is_unique=NULL`), no crash.
- **Expected outcome:** full-node process crash on every node that validates B; B never saved; repeatable by the attacker (crash → reconnect → resend).
- **Impact assessment (per program rules):** availability-class; a node-side fix (make it non-throwing like the light path) resolves it **without** network coordination → likely **out of scope** as pure DoS per the DoS-coordination rule. **BUT** it is strong evidence for the S8 family: the full node's private-payment double-spend enforcement is *crash-based*, not refusal-based — and the input is a replayed spend proof, which is exactly the uniqueness gap the 2025 fix (05f291d8) addressed only on the light path. Cross-family feed for f8.

### T-B — CRASH (narrow window): stability lock proc `throw Error("earlier unit is no longer on main chain")` (main_chain.js:1213)
- **Mechanism:** `determineIfStableInLaterUnitsAndUpdateStableMcFlag` calls `handleResult(bStable, true)` to the caller BEFORE acquiring `['handleJoint']` (fire-and-forget, main_chain.js:1199–1201). The queued proc later re-reads the earlier unit; if it was reorged off the MC while queued → uncaught throw → crash. Window: between the determination (during validation U) and the proc running (after U's unlock) — the single-writer model makes genuine interleaving rare, but under handleJoint contention (queued jobs) the window widens.
- **Source→sink→path:** main_chain.js:1189 → 1199 (`handleResult(bStable,true)`) → 1201 `mutex.lock(['handleJoint'])` → 1213 `if (!objEarlierUnitProps.is_on_main_chain) throw Error(...)`.
- **Concrete input:** flood a local network so the handleJoint queue is deep, while sending units that change the MC tip such that the earlier last_ball unit is reorged between determination and lock acquisition. Uncertain reachability; recorded as weak-to-medium.
- **Negative control:** without contention the proc runs immediately after U's unlock (queue order), MC cannot change in between (single-threaded, serialized) → no crash in normal operation.

### T-C — DEAD CODE (not exploitable): the `SELECT ball FROM balls ... just became stable but ball not found` throw (validation.js:826)
- Both branches above it `return` (`if (bAdvancedLastStableMci) return callback(transient)`; `if (!bAdvancedLastStableMci) return checkNoSameAddressInDifferentParents()`), so the query + throw are unreachable. Recorded so nobody re-hunts it.

### T-D — WEAK: global `['handleJoint']` serialization + disabled deadlock checker + lock-leak-on-throw
- All joint validation and save is serialized through the single `['handleJoint']` lock (plus `['write']` in saveJoint). The deadlock checker (`checkForDeadlocks`, 30s) is commented out; if any lock proc never invokes its unlock (e.g., a throw swallowed by a library), the queue stalls silently with no timeout — permanent node-wide joint-processing halt until restart. This turns any single recoverable error into a full availability stall; mitigations: uncaughtException re-throw crashes first, and `lockOrSkip` exists for non-critical paths. Reported as a hardening gap, not a standalone finding.

### T-E — WEAK: `assocUnitsInWork[unit]` + `handleSavedJoint` 1s retry loop
- If validation crashes mid-processing (T-A/T-B), `assocUnitsInWork[unit]` is never deleted and the `['handleJoint']` lock never released — but the process is dead anyway (uncaught re-throw), so no in-process lock-leak persists across restarts. After restart the unit arrives fresh. Not independently exploitable; consequence of T-A/T-B.

### T-F — LOW: `notifyWatchersAboutStableJoints` acknowledged race
- The `mci_became_stable` event can fire before the stability commit is visible to a fresh query; the `['write']`-lock wait doesn't guarantee visibility (comment at network.js:1643 admits it). Impact: light clients may briefly miss stability notifications → delayed `have_updates`. Self-correcting on the next roundtrip. Not a finding.

## Held or refuted observations (with the decisive control)

- **H1 — no concurrent double-processing within a process:** `handleJoint` sets `assocUnitsInWork[unit]=true` synchronously at entry and every terminal callback deletes it; `checkIfNewJoint` → `checkIfNewUnit` dedups via memory cache + DB. Two simultaneous entries for the same unit → second gets `ifUnitInWork`. Control: verified all six terminal callbacks (ifOk, ifOkUnsigned, ifKnown, ifKnownBad, ifKnownUnverified, error paths) delete the flag; `handlePostedJoint`'s `ifUnitInWork` returns "already handling this unit". HELD.
- **H2 — lock-order consistency:** all writers acquire locks in the same order: `['handleJoint']` → `arrAuthorAddresses` → `['write']` → (nested `['private_write']`); the stability proc re-enters `['handleJoint']` fire-and-forget AFTER the caller's result callback (no deadlock — verified the caller is not blocked on the queued proc). `purgeUncoveredNonserialJointsUnderLock` and `readDependentJointsThatAreReady` dispatch only after their own locks release. No inversion found. HELD.
- **H3 — public-asset double-spend is refusal-based, not crash-based:** the non-private branch of `onDone` routes the error to `cb2(err)` → transient/unit error → `purgeJointAndDependencies` — no crash. Control: traced `checkForDoublespends` error path for non-private assets. HELD (this is the negative control for T-A).
- **H4 — ownership precedes double-spend check on the transfer path:** `if (arrAuthorAddresses.indexOf(owner_address) === -1) return cb("output owner is not among authors")` runs before `checkInputDoubleSpend` for both public and private (fixed-denomination + divisible) transfers → the `checkForDoublespends` "conflicting ... from another address?" throw is NOT trivially reachable by spending a stranger's output. HELD.
- **H5 — init/catchup overlap covered:** `cc0ba54` holds `['handleJoint','initial']` through `initCaches`/`initUnhandledAndKnownBad`; `a7eb776`/`615e258` gate online/posted joints during catchup (no ball / `bCatchingUp`). Siblings checked: `handleSavedJoint` (from storage) is only reached via `findAndHandleJointsThatAreReady`, which runs under `['handleJoint']`; no uncapped catchup entry found in this family. HELD.
