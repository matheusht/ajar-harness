## Triples (candidate hypotheses)

### T1 — MISSING `return` AFTER CATCH IN `handleSavedPrivatePayments` (network.js:2324–2331) — the one real fail-open candidate

- **Mechanism:** in `handleSavedPrivatePayments` (network.js:2301), each queued private payment
  chain's head payload is hashed:
  `network.js:2322-2323` `try { var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true); }`
  `network.js:2324-2331` `catch (e) { console.log(...); if (ws) sendResult(ws, {..., result:'error', error: e.toString()}); deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); }` — **no `return`**.
  `network.js:2332` `var key = 'private_payment_validated-'+...-+json_payload_hash+...;` (hash is `undefined` on the error path)
  `network.js:2333` `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` — **still executed**.
  `getBase64Hash(payload, true)` throws when the payload contains a `null` value
  (`string_utils.js:223-224` `if (variable === null) throw Error("null value in " + ...)`), a
  non-finite number (`string_utils.js:228-229`), or a string containing the 0x00 join char
  (`string_utils.js:18-19`). The payload is attacker/peer-controlled (queued from
  `handleOnlinePrivatePayment` at network.js:2230+ / wallet.js:1035).
- **Source → sink → path:** peer/wallet sends chat private payment → wallet.js:1035
  `handleOnlinePrivatePayment` → queued into `unhandled_private_payments` (network.js:2248) →
  `handleSavedPrivatePayments` (network.js:2301) → hash try/catch (2322–2331) → **fall-through**
  → `validateAndSavePrivatePaymentChain` (private_payment.js:29) → asset-module
  `validateAndSavePrivatePaymentChain` (divisible_asset.js:17 / indivisible_asset.js) →
  transaction COMMIT/ROLLBACK (private_payment.js:52–70).
- **Concrete input construction:** as a peer of a full node with a wallet, send a private payment
  chain whose head element payload contains a `null` field (e.g. `payload = {asset: <private
  asset>, denomination: 1, output_index: null}` — the wallet-side checks at wallet.js:1027 only
  require `isNonnegativeInteger(output_index)` consistency and `handleOnlinePrivatePayment`
  (network.js:2236-2242) reads `payload.denomination` and validates unit/message_index/output_index
  shapes, none of which reject a null INSIDE nested payload fields). Then observe the node's
  handling of the queued chain.
- **Expected outcome (two branches, both need lab proof):**
  - (a) The asset module's own hash path (`divisible_asset.js:75` catch → `ifError` → ROLLBACK)
    rejects the chain: the `unhandled_private_payments` row was already deleted in the catch →
    chain silently dropped, never retried; the sender was told `error` while validation still ran
    and then deleted the record again (no-op) and invoked `cb` a second time on the async.each
    iterator (second call ignored by async). State-machine inconsistency: error result + continued
    processing + double-cb.
  - (b) If the asset module does NOT re-hash the offending field, the chain is ACCEPTED
    (`ifOk` → sendResult 'accepted') despite the sender having received `result:'error'` — the
    sender may re-send, and the acceptance key contains `undefined` for the hash
    (`'private_payment_validated-<unit>-undefined-<idx>'`), so eventBus listeners keyed on the
    correct hash never fire and all malformed chains collide on one key.
- **Negative control:** a payload with no nulls/non-finite values hashes fine (no catch), key uses
  the real hash, single `deleteHandledPrivateChain`, single `cb` — clean single-path processing.
  Also the sibling in `wallet.js:1029-1031` DOES `return cb("head priv element hash failed " + e)` —
  the intended fail-closed pattern; the full-node path at network.js:2324 lacks it.
- **Assessment:** `suspected_signal` — the shape is definite (error path continues processing,
  double-cb, undefined-hash key, error-then-accept possible). Impact is NOT yet established:
  branch (a) is availability-of-one-chain (attacker-controlled anyway), branch (b) would need the
  asset module to accept a null-containing payload (its own hash checks likely reject). Needs
  dynamic verification (F8 private-payments family overlap; lab PoC with a null-bearing payload).

### T2 — CATCH → `cb()` SUCCESS IN `readAADefinitions` (aa_addresses.js:87–89) — fail-open in fee estimation

- **Mechanism:** `readAADefinitions` (aa_addresses.js:34, light path) fetches unknown address
  definitions from the light vendor; `try { var chash = objectHash.getChash160(arrDefinition); }
  catch (e) { ...; return cb(); }` — a definition whose chash computation throws is skipped as if
  the address were not an AA. Same for `response.error` (line 80) and `chash !== address` (line
  97-99): all three treat "can't verify" as "not an AA".
- **Source→sink→path:** wallet.js:2179 `aa_addresses.checkAAOutputs(arrPayments, ...)` →
  readAADefinitions → light-vendor fetch (network.requestFromLightVendor) → catch → cb() → address
  absent from rows → `checkAAOutputs` (aa_addresses.js:118–153) skips the bounce-fee requirement
  for that address → wallet composes a unit without the required bounce fees.
- **Concrete input:** send a payment to an AA address whose definition fetch fails or whose
  definition mismatches the address chash (light client). The wallet-side bounce-fee check is
  skipped.
- **Expected outcome:** wallet under-reports required bounce fees → the unit is rejected by the
  full node (which resolves the AA from its own `aa_addresses` table and enforces bounce fees at
  validation). Consequence is a failed transaction, not a bypass: the node-side enforcement is the
  control that caps this (negative control: full node with the definition in `aa_addresses`
  returns rows directly at aa_addresses.js:44-46, never entering the light path).
- **Assessment:** `suspected_signal` as a fail-open SHAPE (error → success), `held` as an impact —
  capped by node-side validation; wallet-side fee estimation only. Low severity if anything.

### T3 — `cb(found_address)` USED AS ERROR + ERROR-IGNORING FINAL CALLBACK (validation.js:688–706)

- **Mechanism:** `checkNoSameAddressInDifferentParents` passes a string to `cb(found_address)` to
  abort `async.eachSeries` early, and the final callback `function(){...}` ignores its `err`
  parameter, relying on the closure `found_address` instead. Works today; fragile (if the iterator
  aborted for any other reason the error would be silently dropped).
- **Assessment:** observation/fragility, not a bug — `found_address` is checked explicitly.
  Recorded so future refactors don't silently break it.

### T4 — OLD-DAG-GATED ARG CHECKS in validateDefinition (definition.js:601–605, 385–389) — cross-ref to S1 (route to f1/f4)

- **Mechanism:** `if (args.length > 10000 && (last_ball_mci >= pemCurvesFixMci || !hasBall && getMinRetrievableMci() >= pemCurvesFixMci))` and the mci/age/timestamp `isArrayOfLength(args,2) && (...)`
  gates skip the length checks for units attached below the upgrade MCI (with a ball, without the
  minRetrievableMci disjunct). Not a fail-open bug per se, but the S1 old-DAG-gating shape; belongs
  to families f1/f4. Recorded for routing.
