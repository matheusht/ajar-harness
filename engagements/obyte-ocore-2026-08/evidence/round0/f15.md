## Triples

### T1 — signed_message signing path: ZERO content validation before signature (weak-medium)
- **Mechanism:** In `handleMessageFromHub` case "sign" (`wallet.js:251`), if the request unit
  carries `signed_message` and only `{signed_message, authors, version}` (`wallet.js:340`), the
  wallet skips ALL validation — no `hasValidPayloadHashes`, no payment checks, no
  `handleOnlineJoint` — and goes straight to `eventBus.emit("signing_request", ...)` (344). The
  signature is `objectHash.getSignedPackageHashToSign(objUnit)` (`signed_message.js:93`), covering
  arbitrary `{app, payload}`.
- **Source→sink:** hub/cosigner "sign" message → `wallet.js:251-344` → `signing_request` (user
  confirmation) → `getSigner().sign` (`wallet.js:2008-2060`) → ECDSA signature over the
  signed_message hash. Contrast: the messages path runs full unsigned validation first
  (`wallet.js:346-357`, `network.handleOnlineJoint` at 361).
- **Concrete input:** attacker sends
  `{address: <victim>, signing_path: "r", unsigned_unit: {version, signed_message: {app: "attestation", payload: {address: <attacker>}}, authors: [{address: <victim>, authentifiers: {r: "..."}}]}}`
  to the victim wallet via hub (or as a cosigner).
- **Expected outcome:** wallet emits a signing request; on user confirmation, the wallet signs the
  attacker-chosen signed_message attributed to the victim's address. signed_message cannot move
  value directly (no payment), but anchors attestations / contract responses / profile claims.
- **Negative control:** same request as a messages-unit requires payment presence + payload-hash
  validation + full unsigned validation; the signed_message branch is the only one that skips all
  of it.
- **Assessment:** `suspected_signal` (weak-medium). Exploitability requires user confirmation AND a
  consumer of signed_message (arbiter contracts, attestations) where a forged-looking message
  matters. GUI display is the last gate (out of scope — GUI wallet).

### T2 — Light-mode composition trusts hub-supplied position + tps_fee (medium observation)
- **Mechanism:** In `conf.bLight`, `composeJoint` takes `parent_units`, `last_ball`,
  `last_ball_unit`, `last_ball_mci`, and `tps_fee` verbatim from the hub response
  (`composer.js:312-330, 341-352`) with presence-only checks. Meanwhile light-mode validation
  short-circuits after structural checks: `validation.js:340-344` returns
  `ifOkUnsigned(true)` / `ifOk({sequence:'good', arrDoubleSpendInputs:[]...})` with NO balance,
  signature, definition, or double-spend verification.
- **Source→sink:** hub `light/get_parents_and_last_ball_and_witness_list_unit` →
  `composer.js:312` → composed+post-signed unit attached at hub-chosen position → light wallet DB.
- **Concrete input:** attacker-controlled hub returns
  `{parent_units: [<pre-upgrade units>], last_stable_mc_ball: <old ball>, last_stable_mc_ball_mci: <0 or below upgrade MCIs>, tps_fee: <minimal>}`.
- **Expected outcome:** (a) the wallet signs a unit attached to an OLD DAG position —
  position-gated upgrade rules (shape S1: `last_ball_mci >= constants.X` gates) do not apply to
  that unit; (b) an undersized tps_fee is composed unverified; (c) the wallet can be kept composing
  units that fork off a stale position. Full nodes still validate the posted unit against THEIR
  state — so the direct impact is (a) for position-gated rules, plus transaction failure/stalling.
- **Negative control:** honest hub returns the current position; unit attaches to the tip.
- **Assessment:** `suspected_signal` (medium observation, low standalone exploitability). The S1
  interplay (upgrade-rule bypass via old-position attachment) is the interesting part and needs a
  concrete position-gated rule + a composed unit that would violate it. Cross-family with F9/F10
  (light trust model).

### T3 — JS Number change arithmetic on value amounts (note, S12 cross-family)
- **Mechanism:** `var change = total_input - total_amount - commissions` (`composer.js:538`) and
  `var change = total_input - target_amount` (`divisible_asset.js:260`) run on IEEE-754 doubles.
  Beyond 2^53 (9e15 base units ≈ 9e6 full GBYTE/asset units) integer precision is lost; the change
  output and fees can be off by base units.
- **Source→sink:** composed unit outputs → change output amount (`composer.js:538-543`) →
  `objPaymentMessage.payload.outputs[0].amount = change`.
- **Concrete input:** two huge inputs (> 2^53 base units) with arithmetic that drops a unit.
- **Expected outcome:** change output off-by-N base units vs Decimal reference.
- **Negative control:** amounts < 2^53 produce exact change.
- **Assessment:** `suspected_signal` (note). Feeds F12 (dag-js-numeric-value-arithmetic card).

### T4 — sortOutputs type assumptions (weak)
- **Mechanism:** `sortOutputs` (`composer.js:35-38`) does `a.address < b.address` then
  `a.amount - b.amount`; non-string address / non-number amount throws or mis-sorts. In the sign
  path outputs are pre-validated (`wallet.js:307-318`); in local compose and asset modules
  (`divisible_asset.js` arrOutputs from params) caller-controlled.
- **Assessment:** `suspected_signal` (weak). Local crash / invalid composed unit; network rejects.
  Self-harm only.

## Held or refuted observations (decisive control)

- **H1 — f5d8552 sibling hunt on the messages path: NOT FOUND (held).** The sign request path is
  comprehensively hardened: private payload structure + hash + output_hash (`wallet.js:264-303`),
  payload hashes (`wallet.js:348` → `validation.js:54 hasValidPayloadHashes`), payment message
  presence + inputs/outputs structural checks (`wallet.js:349-357`, the f5d8552 addition),
  full unsigned validation for full nodes (`wallet.js:361` → `validation.js` series at 362-492).
  The placeholder-signature acceptance (`definition.js:743`: `bUnsigned && signature[0] === "-"`)
  is only reachable in local unsigned validation — `network.js:965-966/1213-1214` refuse
  `unsigned` joints from peers, so the placeholder bypass cannot be driven remotely.
- **H2 — signature binding is sound.** `getUnitHashToSign` deletes authentifiers
  (`object_hash.js:89-96`); the signature covers content_hash, authors (addresses), witnesses,
  parents, last_ball, timestamp. No field a cosigner/hub could swap survives the hash; a "signature"
  response is bound to (device, address, path, text) via the eventBus key (`wallet.js:410-415`).
- **H3 — multisig order change (d724068) is benign:** sorting authors by authentifier count for
  signing (`composer.js:551-554`) only reorders requests; the unit hash is unchanged.
- **H4 — change output underflow guard:** `if (change <= 0)` throws/handles
  NOT_ENOUGH_FUNDS (`composer.js:539-544`) — no negative change output.

## Gaps not covered and why

- **aa_composer.js composition paths** (AA responses composed with attacker-influenced state):
  large (78KB) and F11-family; noted for the AA engine family. The AA response units still pass
  network validation, so the surface is "AA state → composed response" correctness, not signing.
- **payload_location 'uri' fetch** — the sign path allows uri messages (payload absent, uri ≤500
  chars, uri_hash checked at `validation.js:1581-1593`); the node-side fetch of uri payloads is an
  F9/SSRF-surface item, not signing.
- **GUI rendering of signing_request** — the confirmation dialog is the final gate for T1/T2; GUI
  wallet is out of scope for this audit (core library only).
- **receiveTextCoin full flow** — self-composed, mnemonic-local; no external input; skimmed only.

## Verdict

Family is well-hardened on the message-signing path (f5d8552 + full unsigned validation); the
notable residuals are the unvalidated signed_message signing branch (T1, low) and the light-mode
hub-position trust that interacts with old-DAG rule gating (T2, medium observation, cross-family).
