## Triples

### T-f2-01 (STRONG — verify Oracle MySQL semantics in round 2) — unary-plus on a string column breaks the double-spend competitor filter on MySQL

- **mechanism:** In `findStableConflictingUnits` (main_chain.js:1391, query at 1395–1416), the double-spend competitor query filters stable competitor units with the predicate `AND +competitor_units.sequence='good'` (line 1401/1415). `sequence` is a TEXT column with values `good | temp-bad | final-bad`. Operator precedence makes this `(+competitor_units.sequence) = 'good'`.
- **source→sink:** the WHERE clause (main_chain.js:1415) → `findStableConflictingUnits` → `handleNonserialUnits` (1252) assigns `sequence = 'final-bad'` when conflicts are found → `propagateFinalBad` (1320) marks spending units final-bad → `addBalls` calls `objectHash.getBallHash(unit, arrParentBalls, arrSkiplistBalls, objUnitProps.sequence === 'final-bad')` (main_chain.js:1511) — **the ball hash depends on the resolved sequence** → downstream units hash different balls → divergence.
- **verified behavior:** sqlite (repo default + tests): `+` is a no-op → filter correctly matches only `'good'` (tested live: `SELECT +sequence='good'` → good=1, final-bad=0, temp-bad=0). MariaDB 12.3.2 (local): identical correct result (tested live). **Oracle MySQL 8: unary plus applies numeric coercion (`+'good'` → 0), and `0 = 'good'` coerces the string to 0 → TRUE → the predicate matches ALL sequences** — competitors then include stable `final-bad` units, widening the competitor set and changing which units resolve `good` vs `final-bad`.
- **concrete input construction:** author A posts 2+ units in the same MCI where the earliest (by `ORDER BY unit`) resolves `final-bad` via a genuine input conflict; a later same-author unit has no real double-spend conflict. On sqlite/MariaDB the later unit resolves `good` (final-bad competitor excluded); on Oracle MySQL (if coercion applies) it resolves `final-bad` (final-bad competitor included). Opposite divergence: a unit that should be `final-bad` resolves `good` when its only competitor is a `final-bad` unit that the broken filter *should* have excluded — wait, the broken filter *includes* more → more final-bads on MySQL; a MySQL-only `good` is impossible here (filter widening only adds competitors) — so the divergence is: **MySQL marks more units final-bad than sqlite/MariaDB** → ball hashes diverge for those units → nodes disagree on downstream ball references → consensus divergence between DB backends.
- **expected outcome:** DB-backend-dependent `sequence` resolution → divergent ball hashes → cross-node disagreement (Critical-shaped if any MySQL node participates in consensus).
- **negative control:** (a) verified sqlite/MariaDB return only `good`; (b) the corrected predicate `sequence='good'` returns identical results on all three backends; (c) a single-unit-per-author MCI (no competitors) is unaffected on all backends.
- **round-2 verification:** run on Oracle MySQL 8: `CREATE TABLE t(sequence TEXT); INSERT ... ; SELECT +sequence='good' FROM t;` — if `final-bad`/`temp-bad` match, the divergence is real. Then confirm whether Obyte full nodes run Oracle MySQL in production (conf.storage supports mysql and sqlite; some deployments historically used MySQL). Note: this same `+` idiom appears harmlessly on numeric columns (`+is_on_main_chain=1` in witness_proof.js:206/countVotes) — the string column is what changes semantics.

### T-f2-02 (STRONG — race window, needs demonstration) — unhandled throw when the referenced last-ball unit leaves the MC during the lock wait → process crash / handleJoint lock leak

- **mechanism:** `determineIfStableInLaterUnitsAndUpdateStableMcFlag` (main_chain.js:1189) is called from validation (validation.js:802) when an incoming unit's `last_ball_unit` is not yet stable in the node's view. It computes `determineIfStableInLaterUnits` on the **validation transaction's snapshot** (`conn`), calls `handleResult(bStable, true)`, then — to advance the stability point — acquires the `handleJoint` lock (main_chain.js:1201) and re-reads `earlier_unit` on the **global** db:
  - line 1214: `if (!objEarlierUnitProps.is_on_main_chain) throw Error("earlier unit is no longer on main chain");`
  - The throw is inside a callback executed via `storage.readUnitProps(db, earlier_unit, async function(...){...})` (main_chain.js:1213) with **no try/catch and the `unlock()` never called**.
- **source→sink:** concurrent reorg removes an unstable MC unit (goDownAndUpdateMainChainIndex, main_chain.js:262) → validation path's queued stabilizeMci work reads it on the global db → throw → unhandled rejection (Node ≥15 default = process exit; Node 25.9.0 here) → **process crash, and if any handler catches the rejection instead, the `handleJoint` lock is never released → every subsequent joint validation queues forever (liveness stall)**.
- **concrete input construction:** a peer propagates unit U whose `last_ball_unit` LB is unstable-but-stable-in-parents (this path), while concurrently propagating a competing branch whose units overtake LB's branch (higher witnessed level) before this node acquires `handleJoint`; the validation transaction snapshot still shows LB on-MC, the post-lock re-read shows it off-MC.
- **expected outcome:** process exit (or permanent handleJoint queue stall) on the validating node; if the same race hits all honest nodes processing the same unit — network-wide crash with recovery requiring coordinated action (in-scope class: temporary freezing of network transactions).
- **negative control:** no concurrent reorg → `readUnitProps` returns on-MC → guard at 1216 (`new_last_stable_mci <= last_stable_mci || is_stable`) handles the moved-forward case (this is the 2afd965 fix) → no crash.
- **round-2 verification:** demonstrate the race in a two-process local lab (competing branch + delayed lock acquisition); also confirm no global `uncaughtException`/`unhandledRejection` handler exists (grep found none outside node_modules).

### T-f2-03 (WEAK — construction attempt needed) — stability-point stall by keeping an alt branch "included by later units"

- **mechanism:** `updateStableMcFlag` new path (main_chain.js:511–520) calls `determineIfStableInLaterUnits(conn, first_unstable_mc_unit, arrFreeUnits, ...)` where `arrFreeUnits` = **all free units, including attacker-authored ones** (getFreeUnits, main_chain.js:717). `determineIfStableInLaterUnits` treats an alt branch as live only if included by later units (`determineIfHasAltBranches`, main_chain.js:1040; `createListOfBestChildrenIncludedByLaterUnits`, 1060), then requires `min_mc_wl >= max_alt_level` (main_chain.js:1190) to advance stability.
- **source→sink:** attacker authors alt-branch units (children of an alt root of the current best parent) and keeps them included by their own free tip units → `bHasAltBranches=true`, `max_alt_level` raised → `min_mc_wl >= max_alt_level` fails → stability point does not advance → no new balls → all transactions below the stall point stay unfinalized (temporary freezing).
- **concrete input construction:** on a local lab, an attacker (non-witness, but able to author units) posts an alt-branch unit with high `level` (long chain) attached to the current best parent's alt root, and keeps referencing it; measure stability advancement with and without the alt branch.
- **expected outcome:** stability point frozen while valid MC units exist (if the WL-increasing constraint `bpunits.witnessed_level < units.witnessed_level` in determineMaxAltLevel (main_chain.js:763) can be satisfied cheaply — open question).
- **negative control:** remove the attacker's alt units (or stop referencing them) → stability resumes; the MC branch alone advances normally.
- **open questions (why it may not pan out):** the WL-increasing constraint may bound `max_alt_level` below `min_mc_wl` for cheap constructions; sustainability cost; whether the freeze self-heals when the attacker stops (it should — units stop being "included by later units" once superseded... but free units remain free unless children attach, so a one-shot posting may persist — needs the lab test). Impact class only if resolution requires network coordination; otherwise out-of-scope temporary disruption.

### T-f2-06 (held / out-of-scope) — emergency OP-list change + unstable votes (countVotes, is_emergency)

`applyEmergencyOpListChange` (main_chain.js:1940) can be triggered by anyone paying `SYSTEM_VOTE_COUNT_FEE` (1e9) via a `system_vote_count` message (writer.js:640, validation.js:1911), gated by `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days). `countVotes` with `is_emergency=1` folds in `getUnstableVotes` (main_chain.js:1906) — unstable 'good' units' `op_list` votes at least `EMERGENCY_COUNT_MIN_VOTE_AGE` (1h) old, sorted deterministically (timestamp, level). A balance-holding attacker can influence the OP list this way; the OP list drives best-parent tie-breaks (storage.js `determineBestParent`, `bestParentPrefersOpUpgradeMci`) and the witness set for stability. **This is an economic/governance attack — explicitly excluded by program-policy.md ("basic economic and governance attacks").** Held/out-of-scope; the vote-count balance query itself was recently fixed (final-bad spender undercount).

### T-f2-07 (weak — cross-family note for f1, S1 interplay) — validation-path stability advancement changes gating thresholds

`determineIfStableInLaterUnitsAndUpdateStableMcFlag` advances the node's stability point as a **side effect of validating a peer-supplied unit** (validation.js:802 → main_chain.js:1189→1201→`stabilizeMci(last_stable_mci+1)`), and returns a transient error ("last ball just advanced, try again", validation.js:810) so the unit is not written. Implications: (a) a peer can cause the node to advance stability + run AA triggers + update tps fees without the triggering unit itself being committed — an influence on validation gating thresholds (rules keyed on `last_ball_mci >= constants.X`, the S1 family) — but only *forward* (rules become *more* likely to apply, never less: no bypass); (b) liveness: repeated submissions in a loop force repeated transient rejections + stability work (CPU/DB cost, AA triggers) — a resource cost amplifier, not a consensus flaw. Weak; the transient-rejection loop deserves a cost measurement but no consensus impact.
