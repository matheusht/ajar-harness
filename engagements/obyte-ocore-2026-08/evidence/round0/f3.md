## Triples

### T1 — ECDSA malleability (high-S) — **REFUTED by experiment, held**
- mechanism: signature.js `verify()` → `secp256k1.ecdsaVerify` (signature.js:36). Hypothesis: the
  npm lib may accept high-S (malleated) signatures.
- path: unit authentifier → definition 'sig' case (definition.js:743) → `ecdsaSig.verify(
  unit_hash_to_sign, signature, pubkey)` → ecdsaVerify.
- concrete input: sign a unit hash with a fresh key, flip S to `n−s` (high-S), submit as the
  authentifier.
- expected outcome (before test): accepted (malleability).
- **actual (local test): low-S accepted=true; HIGH-S accepted=false.** This secp256k1 build enforces
  low-S in `ecdsaVerify`.
- negative control: high-S rejection is the negative control; low-S acceptance is the positive
  control. Both tested.
- residual: `verifyMessageWithSecp256k1PemPubKey` (signature.js:66) calls `signatureNormalize`
  BEFORE verify → high-S IS accepted on the PEM/formula path. Inconsistent but benign here
  (malleability is not usable for forgery; unit identity is the unit hash, which excludes
  authentifiers; device-message identity is message content). Record as held/benign inconsistency.

### T2 — pubkey parsing/type confusion in `verify()` — **HELD (fail-closed)**
- mechanism: `Buffer.from(b64_pub_key, "base64")` with malformed/overshort pubkey; `ecdsaVerify`
  requires exactly 33 or 65 bytes.
- path: definition 'sig' (definition.js:745) → verify() → ecdsaVerify.
- concrete input: definition with `pubkey` = 44-char base64 that decodes to ≠33/65 bytes (or
  non-base64 → lenient Buffer.from yields 0 bytes).
- expected: Node's lenient base64 could yield a weird-length key.
- **actual (tested): 64-byte pubkey → THROWS → caught (signature.js:38) → false; empty pubkey →
  THROWS → false; `Buffer.from("!!!!","base64")` → 0 bytes → throws → false.** Fail-closed.
- negative control: correct 33-byte compressed pubkey verifies true (test 1).
- note: PUBKEY_LENGTH=44 (constants.js:39) means definitions only ever carry compressed keys;
  uncompressed-confusion is structurally excluded.

### T3 — pre/post-MCI PEM verification divergence (OpenSSL vs npm secp256k1) — **HELD (weak)**
- mechanism: `verifyMessageWithPemPubKey` (signature.js:48) picks the npm secp256k1 path only when
  the PEM carries the secp256k1 OID AND `mci >= pemCurvesFixMci`; below the MCI it uses
  `crypto.createVerify('SHA256')` (OpenSSL). The two paths differ in signature encoding (DER vs
  compact-after-import) and curve support.
- path: formula `sign`/`vrf` opcodes (evaluation.js:1720, :1755) → verifyMessageWithPemPubKey.
- concrete input: an AA defined pre-MCI using a brainpool/binary curve (allowed then); a node on
  OpenSSL 3 (which dropped some binary curves) verifies differently from one on LibreSSL/1.1.
- expected: cross-*version* divergence, not attacker-controllable; new AAs are locked to
  `objSafePemTypes` post-MCI (signature.js: ~200–230). No unit can change its MCI; no split.
- verdict: held, liveness/ops concern only. Recorded for completeness; not pursued further in f3.

### T4 — `bUnsigned` placeholder signature ("-" accepted as valid) — **HELD — network-refused**
- mechanism: definition.js:743 — `if (objValidationState.bUnsigned && signature[0] === "-")
  return cb2(true)`. bUnsigned is set ONLY from `objJoint.unsigned` (validation.js:332).
- path: any joint delivered to `validate()` with `unsigned: true` → placeholder sigs pass.
- concrete input: send `{unit: {...no authentifiers...}, unsigned: true}` to a full node.
- **the fix (60850f6) refuses `"unsigned" in objJoint` at 3 delivery paths**: handleResponseToJointRequest
  (network.js:965), handlePostedJoint (network.js:1213), handleJustsaying 'joint' (network.js:2713).
  I enumerated joint-delivery paths: post_joint ✓, justsaying 'joint' ✓, get_joint response ✓,
  catchup (serves stored joints — no unsigned possible), hub commands (no joint delivery found),
  light-vendor (same justsaying path). No uncovered delivery path found.
- residual (pattern note for later rounds): ANY future joint-delivery path must add the same check;
  the local-composition path legitimately uses it. Cross-check with f9 (network) in round 1.

### T5 — nonserial (`content_hash`) units skip authentifier re-verification — **CANDIDATE (cross-family lead)**
- mechanism: validation.js:1184 — `if (objUnit.content_hash){ // nothing else to check
  objValidationState.sequence='final-bad'; return callback(); }` — a nonserial unit is validated
  only for unit-hash/structural integrity; signatures are NOT re-checked. Also :1154 — authors may
  lack authentifiers when `content_hash` is present; :176 — `content_hash` allowed only in finished
  balls.
- path: catchup/storage delivery of a ball-bearing nonserial unit → validate() → validateAuthors →
  no signature check.
- trust anchor: (a) the unit hash binds `content_hash`; (b) `content_hash` was validated when the
  serial form was processed; (c) the ball was produced by nodes that validated the serial unit.
- concrete input: cannot be forged without breaking (a)–(c) — requires a ball for unvalidated
  content. **Cross-family question for f2/f10: can a ball be accepted for content that was never
  serial-validated (ball forgery, catchup-only acceptance, "no ball via post_joint" siblings)?**
- expected: held IF ball integrity + serial validation are sound on every path; the Obyte team's
  recent catchup hardening (a7eb776, 615e258) suggests this area is where they expect abuse.
- verdict: suspected_signal (weak) — needs f2/f10 adjudication of the ball/stability anchor.

### T6 — post-MCI skip of pending-keychange guards (`checkSerialAddressUse`) — **CANDIDATE (cross-family lead)**
- mechanism: validation.js:1281 — `next = (last_ball_mci >= pemCurvesFixMci || !hasBall &&
  minRetrievableMci >= pemCurvesFixMci) ? validateDefinition : checkNoPendingChangeOfDefinitionChash`.
  Post-upgrade, `checkNoPendingChangeOfDefinitionChash` AND `checkNoPendingDefinition` are SKIPPED.
- path: unit from an address with a pending (unstable) definition change → validateAuthor →
  checkSerialAddressUse → validateDefinition directly (runtime still evaluates the definition at
  `last_ball_mci`, so a *not-yet-stable* change is not the active definition).
- concrete input: change definition, then immediately (before the change is stable/in last_ball)
  submit a spend signed per the NEW definition, attached so `last_ball_mci` still reflects the old
  definition.
- expected: the runtime read (readDefinitionByAddress at last_ball_mci) uses the OLD definition →
  the new-sig spend fails → the race the guards mitigated appears closed by the read-at-last_ball
  semantics; but the boundary case (change unit in the unit's OWN ancestry / definition included in
  the unit as co-author, validation.js:1186–1196) is exactly the "attacker changes his definition
  then quickly spends" case the code comments call unresolved (validation.js:1484 comment:
  "todo: investigate if this can split the nodes").
- verdict: suspected_signal (weak) — needs f4 (definition-change path) + f2 (stability/ball
  ordering) adjudication. High value if real (definition-change race → spend under old semantics).

### T7 — `payload_uri` not committed by unit hash — **HELD (covered)**
- mechanism: `getNakedUnit` (object_hash.js:26) deletes `payload_uri` and `payload`; unit hash and
  unit_hash_to_sign commit only to `payload_hash` + `payload_location`.
- path: external-payload message → fetch → must match `payload_hash` (validation.js:64, :224).
- concrete input: a unit whose URI serves content X but claims hash H; the fetch/verify path must
  compare hash.
- verdict: held for inline (payload_hash verified early); the uri-fetch verification is on the
  light/vendor path — cross-check f9/f10 that fetched payloads are hash-verified before use.

### T8 — cyclic/recursive `'address'` definition references → stack overflow — **HELD (bounded)**
- mechanism: runtime 'address' (definition.js:780) recurses into the referenced address's
  definition; a cycle A→B→A could recurse unboundedly.
- path: definition evaluation during authentifier verification.
- mitigation found: definition-time validation (definition.js:285–330) increments `complexity`/
  `count_ops` with MAX_COMPLEXITY=100 / MAX_OPS=2000, and cyclic/self-referential definitions fail
  validation at definition time (the recursion in the validation pass is guarded). Runtime recursion
  is via async callbacks (not synchronous stack growth). Cross-checked with the object-depth
  protection (6fe2938).
- verdict: held. Not a crash vector as built.

## Held or refuted observations (with the decisive control)

- **H1 — malleability (T1)**: high-S rejected by ecdsaVerify (test: false); low-S accepted (test:
  true). Refuted for the unit-authentifier path.
- **H2 — pubkey parsing (T2)**: wrong-length/empty pubkey → throw → verify() returns false
  (fail-closed). Refuted.
- **H3 — unsigned placeholder (T4)**: all 3 network delivery paths refuse `unsigned` joints
  (60850f6 verified in-tree at network.js:965/:1213/:2713); no sibling delivery path found.
- **H4 — cyclic definitions (T8)**: complexity guard (MAX_COMPLEXITY=100) bounds definition-time
  evaluation; runtime recursion is async. Refuted as a crash vector.
- **H5 — 'address' unresolved inner definition**: runtime ifDefinitionNotFound → cb2(false)
  (definition.js:795–805) — fail-closed (the definition-time pass is lenient, the runtime is not;
  no bypass).

## Suspected_success candidates

None at the `confirmed` bar — I found no signature/acquisition bypass that lets a unit pass without
the private key. Two cross-family leads (T5, T6) carry real potential but their decisive check lives
in other families (ball/stability anchor; definition-change race). Both are handed up with the exact
mechanism and file:line for round-1 allocation.

## Gaps not covered and why

- **Light-client wallet paths** (`light_wallet.js`, `light.js`): light clients trust vendor-provided
  data by design; whether a malicious vendor can serve forged units to a light client is a
  trust-model question, out of the core-lib signature scope — flagged for f9/f10.
- **wallet_defined_by_keys.js signing**: composer-side signing (f15's family) — I confirmed the
  verify-side only; the sign-side input checks (f5d8552) are f15's.
- **secp256k1 low-level edge cases** (R/S = 0, pubkey at infinity): `ecdsaVerify` returns false for
  invalid points (library guarantees; spot-checked via the throw tests).
- **Cross-node OpenSSL divergence on exotic pre-MCI curves**: needs two different OpenSSL builds to
  test; value is low (locked to safe curves post-MCI) — deferred.
