## Triples

### T1 (S8 — spend-proof uniqueness full-vs-light asymmetry) — **suspected_signal (weak, cross-family to f8/f9)**
- **mechanism:** the divisible private payment money boundary is spend-proof verification +
  input-uniqueness enforcement. On the full node, a doublespend conflict on a private asset THROWS
  ("spend proof didn't help") — `validation.js:2066` (`onDone` in `checkInputDoubleSpend`:
  `if (err && objAsset && objAsset.is_private && !conf.bLight) throw Error("spend proof didn't help: "+err)`).
  In light mode the conflict is a plain rejection and the payment is "resent and revalidated when
  stable" — `validation.js:1670` (`if (conf.bLight) ... return cb2(...)` in `checkForDoublespends`).
- **source→sink→path:** attacker-controlled private divisible payment unit → `validateSpendProofs`
  (`divisible_asset.js:95-147`, proofs computed from payload inputs + DB src-output secrets, compared
  in-order against the unit's stored spend_proofs `divisible_asset.js:152-162`) → `validatePayment`
  → `checkInputDoubleSpend` (`validation.js:2250`) → `checkForDoublespends` (`validation.js:1655`).
- **concrete input construction:** a private divisible asset; spend the same hidden output in two
  units (same spend proof), both broadcast; the second one's doublespend query finds the first.
- **expected outcome:** full node throws/rejects the second; the proof-holding owner is the only one
  who can produce the proof (it hashes the src output's address+amount+blinding —
  `divisible_asset.js:117-123`), so an *attacker without the victim's blinding cannot forge it*. The
  asymmetry is architectural: a light client relies on its light VENDOR having verified uniqueness —
  the core lib itself cannot (no graph in light). Not a core-lib bypass; vendor trust boundary.
- **negative control:** same proof in two units where the first is STABLE on MC — second unit
  rejected on full node (the `sequence='good'`/`is_unique` path); spend proof for a victim output
  with unknown blinding cannot be computed (hash mismatch → "incorrect spend proof").
- **verdict:** held-as-designed in core; the asymmetry is a documented, non-exploitable-by-core
  vendor-trust model. Hand to f8/f9 to check the vendor path.

### T2 (S12 — JS Number precision on amounts) — **held / refuted in this family**
- **mechanism:** `total_input`/`total_output` are float sums (`validation.js:2130,2141`), and the
  change computation uses floats (`divisible_asset.js:220` `change = total_input - target_amount`).
- **path:** unit payload amounts → `isPositiveInteger` per input/output (`validation.js:2309,2152`)
  + per-amount and TOTAL caps `> constants.MAX_CAP` (`validation.js:2190, 2597, 2600`) →
  closure `total_input !== total_output` reject (`validation.js:2600`).
- **why held:** `MAX_CAP = 9e15` (`constants.js:57`) < `2^53 ≈ 9.0072e15` — every integer ≤ 9e15 is
  exactly representable, and BOTH the per-amount and the total-sum caps bound every intermediate
  below 2^53, so no float rounding can occur on validated amounts. `TOTAL_WHITEBYTES = 1e15`
  (base asset) is likewise safe. The composer's change computation operates on the same validated
  ranges.
- **negative control:** a crafted unit with two inputs summing past 2^53 is rejected by the
  `total_input > MAX_CAP` check before any precision loss is reachable.
- **verdict:** held — the MAX_CAP bound structurally defeats float-sum divergence in the divisible
  path. Residual: fixed-denomination (indivisible, f7) and commission (f16) amounts are separate
  surfaces.

### T3 (S2 — unescaped SQL interpolation) — **held in this chain (V-001 fixed; siblings none found here)**
- **mechanism:** V-001 was unescaped `message_index`/`output_index` in the inputs-address subquery
  (`divisible_asset.js:61-62`); the fix escapes both with `conn.escape(...)`. Audit of this chain:
  - `divisible_asset.js:35-37, 68-70, 119, 152` — all `?` placeholders.
  - `private_payment.js:60-66` — placeholders.
  - `writer.js:283-288` (spend_proofs INSERT), `inputs.js:48-60` (`confirmation_condition` uses
    `conn.escape` on addresses and `arrAddresses.map(conn.escape)` at line 60) — safe.
  - `wallet.js` sampled payment/address queries (133-1255) — placeholders.
- **path:** attacker-controlled private payload → INSERTs in `validateAndSaveDivisiblePrivatePayment`
  (`divisible_asset.js:37-70`).
- **verdict:** held in the f6 chain; full-codebase SQL-concat sweep is cross-cutting (f1/f14).
- **negative control:** the V-001 site now escapes its two interpolated values; injection test
  strings are inert.

### T4 (issue spend proof lacks unit/output binding) — **suspected_signal (weak, invariant note for f8)**
- **mechanism:** the issue-type spend proof is `objectHash.getBase64Hash({asset, amount, address,
  serial_number})` (`divisible_asset.js:101-107`) — no `unit`/`message_index`/`output_index`
  binding, unlike transfer proofs (`divisible_asset.js:117-123`).
- **path:** issue input in a private divisible payment → proof compared against the unit's
  spend_proofs rows (`divisible_asset.js:152-162`, keyed `WHERE unit=? AND message_index=?`).
- **why not exploitable here:** (a) the proof is still bound to the ISSUANCE IDENTITY
  (asset+amount+address+serial_number); (b) uniqueness of issuance is enforced separately by the
  inputs-table doublespend query on `(denomination, serial_number [, address])`
  (`validation.js:2358-2368`), not by the proof; (c) the spend_proofs check is per-unit so a proof
  reused in another unit fails the per-unit comparison only if the issuance params differ.
- **verdict:** held in this chain — no reachable exploit; record as an invariant for f8's spend-proof
  model review.

### T5 (duplicate private payment with hidden address re-processes) — **weak candidate (cross-family f8/f13)**
- **mechanism:** `private_payment.js:70-75`: on duplicate private payment, `if (rows.length > 0 &&
  rows[0].address) return transaction_callbacks.ifOk()` — silent dedup when the stored output's
  address is visible; but if the stored row's address is NULL (still hidden), it falls through to
  re-`validateAndSavePrivatePaymentChain`, re-INSERTing outputs/inputs for the same unit.
- **path:** same private payment unit processed twice (resend / unfinished-chain revalidation,
  `findUnfinishedPastUnitsOfPrivateChains` `private_payment.js:8-17`) → duplicate INSERTs.
- **expected outcome:** depends on the `outputs` table uniqueness constraints — duplicate rows either
  error the INSERT (→ ROLLBACK, reject) or succeed (→ later "not 1 row when selecting src output"
  at `divisible_asset.js:113`). No theft path identified; possible reprocessing/rejection behavior.
- **negative control:** dedup fires when the address is visible (the normal case).
- **verdict:** weak — needs (a) outputs-table DDL constraints, (b) the exact reprocessing trigger;
  hand to f8/f13.

### T6 (getSavingCallbacks throws on unexpected validation states) — **client-robustness note (low)**
- **mechanism:** `divisible_asset.js:345-355` — `ifJointError`/`ifTransientError`/`ifNeedHashTree`/
  `ifNeedParentUnits` handlers `throw Error(...)` instead of calling back. A composed-and-saved
  payment hitting a transient validation state crashes the client process.
- **verdict:** low — the attacker cannot force these states from a remote position without the
  victim's own chain state; recorded as robustness note, not a candidate.
