## Triples

### F7-C1 — Full-node process crash on private-asset double-spend (SUSPECTED, needs PoC)

- **mechanism:** `validation.js:2287` — `if (err && objAsset && objAsset.is_private && !conf.bLight) throw Error("spend proof didn't help: "+err)` throws inside the double-spend check's `onDone`. The error is produced by `checkForDoublespends` (`validation.js:1655–1720`) when a conflicting input record exists whose unit is included in the new unit's parents (`determineIfIncludedOrEqual` → `cb2(error)` for any non-`final-bad` state). Uncaught → `process.on('uncaughtException')` handler at `network.js:4367` **re-throws to crash the process**.
- **source→sink→path:** attacker's private asset, 2 coins → unit U1: valid private payment spending coin X (accepted, `inputs` row recorded with `src_unit/message_index/output_index`) → unit U2: private payment whose chain re-spends X (same `src_*` triple) with **U1 in U2's parent units** → full node validates U2 (`network.js:2269` `handleOnlinePrivatePayment` → `validateAndSavePrivatePaymentChain` → `validation.validatePayment` → `validatePaymentInputsAndOutputs` → `checkInputDoubleSpend` → `checkForDoublespends`) → conflicting row = U1's input, address = attacker ∈ U2 authors ✓ → U1 included in U2's parents ✓ → `cb2(error)` → `throw` → crash.
- **concrete input construction:** issue private asset (2 coins, denominations d1,d2, `auto_destroy:false` non-private? no — must be `is_private:true`, `fixed_denominations:true`), transfer coin d1 in U1 (chain: issue→U1), then compose U2 with parents = [U1, ...tip] and a private chain whose head spends the *same* output X that U1 spent (send the private elements via the websocket `private_payment` message with `payload_location:'none'` on the unit). Node has U1 in `inputs` → U2 triggers the throw.
- **expected outcome:** full-node process exits (`throw err` in the uncaughtException handler). On restart, `handleSavedPrivatePayments` (`network.js:2320+`) re-validates the stored chain from `unhandled_private_payments` → crashes again → **crash-loop**. Sustained by re-sending the private elements.
- **negative control:** the identical U2 with U1 **not** in its parents (forked path) → `bIncluded=false` → `cb2()` → accepted as parallel spend, no crash. Also: the same double-spend on a **public** (non-private) asset → clean `cb2(err)` rejection, no crash. Also: light node (`conf.bLight`) → no throw.
- **DoS classification (coordination question, recorded for the orchestrator):** the crashing unit is *invalid* (double-spend) — all nodes agree; the fix is a node-side clean-rejection patch (the throw → `cb2(err)`, exactly what 05f291d8 did for light nodes). **Strict reading of the program rule → out of scope** ("node crashes, DoS… when a fix resolves them without network coordination"). Counter-argument for the record: the crash-loop is network-wide and persistent (unhandled_private_payments re-validation), freezing full-node transaction processing until per-node operator action; and the fix was *already* applied to the light path but **not** the full-node path — the sibling was missed. Worth surfacing to the operator as a real robustness bug regardless of bounty classification; escalate to the DoS lane decision.

### F7-C2 — Public-asset crash via spending a stable temp-bad output (CANDIDATE, reachability needs PoC)

- **mechanism:** `validation.js:2449` — `if (bStableInParents) { if (src_output.sequence === 'temp-bad') throw Error("spending a stable temp-bad output " + input.unit); ... }`. A transfer spending an output whose unit is on the MC (`main_chain_index <= last_ball_mci`) and still `temp-bad` throws → process crash (same uncaughtException path).
- **source→sink→path:** attacker unit U0 made `temp-bad` (e.g., attached to a parent that later becomes nonserial) → U1 spends U0's output (post-`spendUnconfirmedUpgradeMci`, sequence inheritance: `console.log("inheriting sequence ...")` at ~2474) → U1 becomes `temp-bad` and lands on the MC → U2 spends U1's output → crash on every full node that has U1 stable+temp-bad.
- **concrete input:** the exact window (stable + temp-bad simultaneously) must be demonstrated in the lab; the MC/stability state machine determines reachability. This is the same crash family as F7-C1 (throw-on-crafted-input in a consensus path), public-asset variant.
- **expected outcome:** process crash; classification same as C1 (DoS coordination question).
- **negative control:** U1 `good` or `final-bad` → clean paths (cb or accept); U1 not stable → no throw.
- **status:** keep-biased candidate — the window is narrow; the PoC phase must show a stable-temp-bad state is attacker-reachable.

### F7-C3 — Issue serial-number lost-update race in the wallet composer (CANDIDATE, weak)

- **mechanism:** `indivisible_asset.js` `issueNextCoin` (~510–560): `SELECT max_issued_serial_number` then compute `serial_number = row.max_issued_serial_number + 1` then `UPDATE asset_denominations SET max_issued_serial_number=max_issued_serial_number+1 WHERE denomination=? AND asset=?` — no `WHERE max_issued_serial_number=<read value>` guard; SELECT and UPDATE not atomic. For capped assets the SELECT gate is `max_issued_serial_number=0`.
- **source→sink→path:** two concurrent `composeAndSaveIndivisibleAssetPaymentJoint` calls (different from-addresses, or cross-process wallets sharing a DB) → both read max=0 → both issue serial 1 → two units each "issuing the cap" (capped asset) or duplicate serials (uncapped).
- **mitigations found:** `composer.js:289` locks per from-address (`'c-'+from_address`) for the whole compose **within one process**, and the compose runs in a DB transaction; capped assets are forced `issued_by_definer_only` (`validation.js:2788`) → single address → same-process race closed. Ledger-side `checkInputDoubleSpend` keyed `(asset, denomination, serial_number[, address])` under the `handleJoint` mutex rejects the second unit on any node that saw the first.
- **expected outcome / verdict:** cross-process only; even then the ledger's per-node serialization mostly contains it (only a propagation race where the two units reach disjoint node sets first could mint twice). **Weak — record, do not prioritize.**

### F7-C4 — Private-payment secrecy leak via console logging (OBSERVATION, info-level, likely OOS)

- **mechanism:** `indivisible_asset.js:126–131` logs the full transfer spend-proof inputs including **blinding, amount, address** (`console.log("validation spend proof: " + JSON.stringify({...blinding: src_output.blinding...}))`); also `:241–258` (`"inserting output " + JSON.stringify(output)`), `:551` (`"payloads with proofs: " + ...`). The blinding is the secret that hides a private output's amount.
- **source→sink→path:** any full node validating a private payment logs the receiver's/change output blinding + amount to stdout → node operator / log reader learns hidden private-payment amounts.
- **expected outcome:** privacy disclosure on the node operator's own machine.
- **verdict:** real but the program's in-scope impacts are fund loss/freezing — privacy leaks are not on the list and would land in the "best-practice" exclusion. Record as observation; do not file unless the operator widens scope.

- **Ledger-side duplicate-issue containment (HELD at node level).** Issue double-spend key `(asset, denomination, serial_number[, address])` + `handleJoint` mutex serialization → a single node accepts at most one same-key issue. (The propagation-race residue is F7-C3's scope.)
