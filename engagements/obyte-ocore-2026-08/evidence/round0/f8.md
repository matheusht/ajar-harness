## Triples

### TRIPLE-1 (STRONG — crash, remote, persistent): private-payment recipient node crash when a doublespend unit arrives with the correct spend-proof address

- **Mechanism.** `checkForDoublespends` (validation.js:1655) is used by the unit-level spend-proof
  uniqueness check `validateSpendProofs` (validation.js:1640-1654). At validation.js:1662:
  `if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1) throw Error("conflicting
  spend proof spent from another address?")`. This throw is UNCONDITIONAL — it fires before the
  `conf.bLight` branch (1664) and is not gated on `is_private`. There is no try/catch between this
  throw and the process-level handler (network.js:4367, which logs then re-throws to crash).
- **Source→sink→path.** Attacker (sender of a private payment, who retains the spend proof — see
  TRIPLE-3) → victim spends the private output X (their node stores spend_proof row
  (P, victim_address) via writer.js:283) → attacker broadcasts unit A spending X with
  `spend_proofs:[{address: victim_address, spend_proof: P}]` (the address the attacker must use for
  A to ever validate) → hub delivers A to the victim's node (A touches the victim's address) →
  `validate()` → `validateMessages()` → `validateSpendProofs()` (validation.js:1640) → query
  matches the victim's own row (P, victim_address) → `checkForDoublespends` (1662): victim's
  address is NOT among A's authors (attacker) → **throw** → uncaught → process crash.
- **Concrete input construction (lab).** Two locally generated keypairs (sender, recipient). Sender
  composes a private divisible payment to recipient (output X). Recipient's node validates the
  chain (X row created). Recipient spends X (unit C; C's spend proof P stored). Sender composes
  unit A spending X (same P, `address` field = recipient's address), parents anchored on the MC tip,
  broadcasts to the recipient's node. Expected: recipient's node crashes (uncaught exception) while
  a clean rejection is the correct behavior (A is a doublespend).
- **Expected outcome.** Process exit on the victim node; persistent (A remains a valid unit in the
  DAG — it passed check #1 on nodes without the victim's row — so re-delivery on restart re-crashes).
  Negative control: same flow with a PUBLIC asset → conflicting unit rejected cleanly (the throw is
  gated to private assets only via reachability: for public assets the conflict row's address is
  always the owner, who must be among the authors).
- **Negative control.** (a) Public-asset doublespend → clean rejection. (b) Private-asset
  doublespend where the attacker's A sets `address` = attacker's own address → no match → A accepted
  as a forked doublespend (no crash on receipt; the poison-row variant, TRIPLE-2). (c) Same flow on
  a light client → same throw (address check precedes `conf.bLight`), light wallets crash too.
- **Severity note (orchestrator).** Single-node crash (recipient's), remote, persistent, zero-cost
  to attacker beyond owning a private payment sent to the victim. Candidate "temporary freezing of
  funds" (Medium, $1,000) if the victim cannot spend the output until a fix; revisit the DoS
  coordination question (a code fix resolves it without network coordination → possibly out of
  scope as pure DoS; the fund-freeze framing is the in-scope angle).

### TRIPLE-2 (STRONG — poison row / payment race): attacker-controlled address in a spend proof creates an undetectable doublespend or a fork race

- **Mechanism.** The unit-level uniqueness check (validation.js:1646) matches on
  `spend_proof=<P> AND address=<address-from-unit>`. The `address` used in the match comes from the
  unit's OWN spend_proofs entry (`objSpendProof.address ? ... : authors[0]`), which for a
  payload-location-"none" private payment is attacker-controlled and never validated at the unit
  level (the payload — where the address would be checked against the src output owner at
  divisible_asset.js:152-153 — is not in the unit and is only validated recipient-side).
- **Source→sink→path.** Attacker composes A spending X with `spend_proofs:[{address: attacker_address,
  spend_proof: P}]` → unit-level check #1 on every node: no existing row (P, attacker_address) →
  A accepted network-wide → A's payload is never validated (delivered to nobody / rejected on the
  attacker's own node) → A is a permanent DAG unit with an unvalidated private payload and a
  spend-proof row poisoning the uniqueness table. Two consequences: (a) if the victim later spends X,
  the victim's own check #1 uses (P, victim_address) which does NOT match A's row → no conflict
  detected at unit level → the two spends coexist as a fork (both 'good' until MC resolution) —
  the doublespend is invisible to the standard check; (b) if the attacker uses the correct
  (victim) address instead, TRIPLE-1's crash fires on nodes holding the victim's row.
- **Concrete input construction.** Same lab setup; A's spend_proofs address = attacker address.
  Observe: A accepted by all nodes; victim's spend C also accepted (no conflict); MC later marks one
  final-bad. The winner is whoever the MC picks; the attacker can anchor A on the best parents to
  maximize win probability.
- **Expected outcome.** Private-payment doublespend with the resolution deferred to the fork race;
  a merchant accepting the victim's payment C before resolution can be defrauded when C goes
  final-bad (outputs deleted via archiving.generateQueriesToVoidJoint → DELETE inputs/outputs).
- **Negative control.** The same attack on a public asset: check #1 cannot be dodged (address is
  bound to the output owner by signature) → second spend rejected cleanly.
- **Severity note.** Economic — payment-race fraud against merchants accepting private payments;
  needs the orchestrator's judgment on whether this is by-design (bearer spend proof) or a bug
  (address not validated at unit level). The asymmetry with public assets (clean rejection vs.
  invisible fork) is the strongest argument it is unintended.

### TRIPLE-3 (STRONG — root cause / bearer secret): the spend proof is a plain hash of output fields + blinding, and the sender retains it

- **Mechanism.** `validateDivisiblePrivatePayment` computes
  `spend_proof = objectHash.getBase64Hash({asset, unit, message_index, output_index, address,
  amount, blinding})` (divisible_asset.js:125-136) and compares to the stored proof
  (divisible_asset.js:151-153). It is a deterministic hash — NOT a signature, NOT zero-knowledge.
  The blinding is generated by the sender (composer.js:839 `generateBlinding`), stored in plaintext
  in the node's outputs table (divisible_asset.js:60), and communicated to the recipient via the
  private payload chain. The sender can therefore recompute the spend proof at any time — the proof
  is a bearer secret the sender never has to surrender.
- **Source→sink→path.** Sender → retains blinding/spend proof → spends X at will (TRIPLE-1/2
  mechanics). This is the root enabler of both triples.
- **Concrete input.** None needed beyond TRIPLE-1/2.
- **Expected outcome.** Any sender can create competing spends of a private payment they sent.
- **Negative control.** For a public payment, spending requires the output owner's signature
  (signature.js) — the sender cannot re-spend.
- **Severity note.** Possibly by design (the recipient is expected to spend promptly / trust the
  sender). The orchestrator should check the Obyte private-payment documentation and the AA guide
  before promoting; the crash (TRIPLE-1) does not depend on this being a design bug.

### TRIPLE-4 (WEAK-MEDIUM — crash, wallet-local): `getSavingCallbacks` throws uncaught on joint/transient validation errors

- **Mechanism.** `indivisible_asset.js:861-872` (`getSavingCallbacks`): `ifUnitError` is handled
  cleanly (the `throw` is commented out), but `ifJointError`, `ifTransientError`, `ifNeedHashTree`,
  and `ifNeedParentUnits` all `throw Error(...)` synchronously inside async callbacks → uncaught →
  node crash. Reached via `composeAndSaveIndivisibleAssetPaymentJoint` /
  `composeAndSaveMinimalIndivisibleAssetPaymentJoint` (indivisible_asset.js:1068, 1154) — the
  wallet's own-unit validation.
- **Source→sink→path.** Wallet user composes an indivisible asset payment (e.g., spending an input
  whose unit is not yet stable → transient error; or parents missing → need_parent_units) →
  `validation.validate(objJoint, {...})` → the error callback throws → crash. `ifTransientError`
  fires for "input unit is not on stable MC yet" and "max_aa_responses=0 not allowed in new units".
- **Concrete input.** Compose a minimal indivisible asset payment spending a freshly received
  (unconfirmed) coin with `spend_unconfirmed='own'`; trigger the transient path.
- **Expected outcome.** Node crash instead of a user-facing error.
- **Negative control.** The divisible-asset equivalent (`composeDivisibleAssetPaymentJoint`,
  divisible_asset.js:170-260) routes errors through `callbacks` without throwing.
- **Severity note.** Self-inflicted (the operator's own node, own action) unless an attacker can
  steer a victim wallet into composing such a payment (e.g., via an AA interaction). Mostly a
  robustness bug; low reachability; record for the record.

### TRIPLE-5 (refuted): "spend proof didn't help" throw reachable via the input-level check alone

- **Mechanism attempted.** validation.js:2289 `if (err && objAsset && objAsset.is_private &&
  !conf.bLight) throw Error("spend proof didn't help: "+err)` — the input-level doublespend check
  (checkInputDoubleSpend). Analysis: to reach it, the unit-level check #1 (validateSpendProofs,
  1646) must have passed, but the input-level check must find an included good conflict. Since the
  spend proof is deterministic and both checks key on the same output, check #1 fires first for any
  included conflict. The only gap is the concurrent-validation race (two units validated before
  either is saved) or the address-mismatch case (TRIPLE-2), which routes to the fork path, not the
  throw.
- **Decisive control.** Unit-level check #1 (1646) rejects included conflicts cleanly before payload
  validation can run; therefore 2289 is only reachable via a narrow race. Recorded as
  `held`-adjacent rather than independently exploitable; TRIPLE-1's throw (1662) is the reachable
  variant.

## Held or refuted observations (with the decisive control)

- **H1 — SQL interpolation siblings in the private payment paths (S2): none found.**
  The V-001 site (divisible_asset.js:53-54) is fully escaped. All other queries in the private
  paths use parameterized `?` placeholders (indivisible_asset.js:254-287, private_payment.js:44-49).
  The `fields` string built at indivisible_asset.js:287 is constant, values are parameterized.
  *Held — the fix covers this surface; no sibling.*
- **H2 — output binding is present.** The transfer spend proof binds
  (asset, unit, message_index, output_index, address, amount, blinding) (divisible_asset.js:126-133;
  indivisible_asset.js:117-124) — a proof cannot be replayed to a different output.
- **H3 — spend-proof uniqueness IS enforced network-wide at the unit level.**
  `validateSpendProofs` (validation.js:1640) runs on every node for every unit carrying
  `spend_proofs` and rejects cleanly when a matching (proof, address) pair was used by an included
  good unit. The sweep title "uniqueness of spend proof is not verified in light" maps to the
  light-client branch (1664): light clients cannot run the graph check and reject any conflict —
  they do not *crash* since 05f291d8 removed the throw on that branch. What remains broken is not
  the check's existence but the address-mismatch hole (TRIPLE-2) and the crash (TRIPLE-1).
- **H4 — archiving deletes spend_proofs; this is correct, not a bypass.** Voided/uncovered units
  get their inputs/outputs/spend_proofs deleted (archiving.js:22-60) and their spent outputs are
  unspent (`generateQueriesToUnspendOutputsSpentInArchivedUnit`) — the output is legitimately
  reusable after its spend is voided. No history-loss bypass.
- **H5 — the light-vs-full asymmetry is intentional at the payload level.** Light clients cannot
  hold the full inputs table; uniqueness is enforced by the full nodes they connect to. Not a
  finding by itself; only the crash (TRIPLE-1, which also hits light wallets via 1662) and the race
  (TRIPLE-2) are exploitable.

## Suspected_success candidates

- **sus-f8-01 — private-payment doublespend crashes the recipient's node (validation.js:1662).**
  Code-verified end to end; the throw is unconditional, uncaught, and the conflicting spend proof
  row is attacker-arrangeable via the sender position. Requires lab confirmation (TRIPLE-1
  experiment). Assessment: suspected_signal — mechanism + concrete input both stated; the live
  crash (process exit) is the oracle.
- **sus-f8-02 — sender-controlled spend-proof address creates an invisible doublespend fork
  (validation.js:1646 + payload-less units).** Code-verified; the address in the uniqueness match is
  attacker-chosen and never unit-level validated. Assessment: suspected_signal — needs the MC
  resolution behavior confirmed in the lab (which unit goes final-bad) to size the economic impact.

- **`dd29823` multiple-private-assets.** The divisible path validates one chain per payment message;

- **Blinding entropy/derivation.** `generateBlinding` (composer.js:839) — I did not audit the RNG

- **The sender-side wallet behavior.** Whether the sender's own node stores X's row and thus
  crashes on the sender's own doublespend (self-DoS) — wallet.js composition path, partially
  covered, deferred.

## Honesty note

TRIPLE-3 (bearer spend proof) may be documented design; TRIPLE-1/2's exploitability does not depend
on it being a bug — they are crash/race mechanics on top of the bearer property. The address-mismatch
hole (TRIPLE-2) is the least-design-dependent and therefore the most likely to be judged a genuine
defect: a public asset's doublespend is rejected cleanly, a private one is not, purely because the
spend-proof address is never validated at the unit level.
