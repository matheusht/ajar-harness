## Triples (candidate hypotheses)

### T1 — Unbounded joint streaming via `refresh`/`subscribe`/`free_joints` (resource amplification, no cap, no rate limit)
- **Mechanism:** `handleJustsaying` `case 'refresh'` (network.js:2634-2640): `if (bCatchingUp) return;
  var mci = body; if (ValidationUtils.isNonnegativeInteger(mci)) return sendJointsSinceMci(ws, mci);
  else return sendFreeJoints(ws);` → `sendJointsSinceMci` (network.js:842-852) →
  `joint_storage.readJointsSinceMci(mci, handleJoint, onDone)` (joint_storage.js:302-327) runs
  `SELECT units.unit FROM units LEFT JOIN archived_joints USING(unit) WHERE (is_stable=0 AND
  main_chain_index>=?) OR main_chain_index IS NULL OR is_free=1 ORDER BY +level` with **no row cap and
  no pagination**, then for EACH row a `storage.readJoint` DB roundtrip → `sendJoint` (network write).
  Same shape: `sendFreeJoints` (network.js:834-841) streams ALL free joints; the `subscribe` request
  handler (network.js:3165-3170) calls `sendJointsSinceMci(ws, params.last_mci)` for any
  non-negative `last_mci` including 0.
- **Source→sink→path:** attacker ws connection → `onWebsocketMessage` (4100) → `handleJustsaying`
  (2634) → `sendJointsSinceMci` (842) → `readJointsSinceMci` (joint_storage.js:302) → N×
  (`storage.readJoint` + `sendJoint`). N = size of the node's unstable/free joint set (on a live
  full node: tens of thousands).
- **Concrete input:** `["justsaying", {"subject": "refresh", "body": 0}]` — repeat from multiple
  connections (up to `MAX_INBOUND_CONNECTIONS`=100, conf.js:54). Also `["request",
  {"tag":"<16B>", "command":"subscribe", "params":{"subscription_id":"<str>","library_version":
  "<valid>","last_mci":0}}]` (needs valid version to pass the version gates).
- **Expected outcome:** node CPU/DB/bandwidth exhaustion from repeated full-history enumeration;
  joint-processing delay (the global `handleJoint` mutex + DB pool are shared). No rate limiting
  exists anywhere in the network layer (grep for throttle/rate-limit: zero hits).
- **Negative control:** `refresh` with `body` = current last_mci returns ~0 joints quickly.
- **Disposition:** real amplification, but per the engagement's DoS rule this is a node-side-fixable
  temporary disruption → **likely out-of-scope class**; still the strongest network candidate — worth
  a lab measurement of the amplification factor in round 1. No fund-loss path.

### T2 — `upgrade_required` justsaying → intentional uncaught throw → node crash
- **Mechanism:** network.js:3069-3074: `case 'upgrade_required': if (!ws.bLoggingIn && !ws.bLoggedIn)
  return; ws.close(1000, "my core is old"); throw Error("Mandatory upgrade required ...");`. The
  process `uncaughtException` handler (network.js:4367-4381) logs then **re-throws** → process death.
- **Source→sink→path:** ws message → `handleJustsaying` (3069) → `throw` → uncaughtException handler
  (4367) → `throw err` → crash. Requires the connection to have `bLoggedIn=true`, which is set only
  in `device.js:292 sendLoginCommand` — i.e., **only our own configured hub** can trigger it.
- **Concrete input:** from a connection the node treats as its logged-in hub: `["justsaying",
  {"subject":"upgrade_required","body":null}]`.
- **Expected outcome:** crash. **Negative control:** same message from a non-hub connection → ignored
  (guard returns).
- **Disposition:** crash-by-design (forces upgrade). Reachability requires controlling the node's hub
  (config/DNS) → **weak, config-dependent, by design — not a finding.** Recorded as an observation
  because the crash mechanism (uncaught throw) is the sharpest instance of the handler-crash surface.

### T3 — Outbound ws connection to arbitrary attacker-chosen URLs (SSRF-ish; no private-IP block)
- **Mechanism:** `case 'my_url'` (network.js:2780-2810): an inbound peer advertises any URL;
  `isValidWsUrl` (network.js:731-743) checks **only** the protocol (`wss:`/`ws:`) — no loopback/private
  IP block. Node then `findOutboundPeerOrConnect(url)` → `connectToPeer` (433-515) opens a ws
  connection and speaks the Obyte protocol (sendVersion, subscribe, want_echo). Same via
  `handleNewPeers` (690-729): any subscribed peer shares up to 100 peer URLs.
- **Source→sink→path:** inbound peer `["justsaying",{"subject":"my_url","body":"ws://127.0.0.1:8080/
  "}]` → node connects to the URL (433) → internal host receives ws handshake + version JSON + joint
  traffic; the node's IP and identity are exposed to the attacker; internal services can be probed
  (connection timing, protocol responses).
- **Concrete input:** `my_url` with `ws://<internal-host>:<port>/` or a URL the attacker controls.
- **Expected outcome:** node-initiated connection to attacker-chosen host; internal probing; identity
  leak. No code execution on the remote host.
- **Negative control:** a benign peer advertising its real public URL — same code path, expected
  behavior.
- **Disposition:** low-severity SSRF-ish vector (protocol-restricted, outbound-only, one handshake +
  a few JSON messages). Not fund-related. Weak candidate.

### T4 — `unhandled_joints` flood from peers sending joints with missing parents (bounded DB/memory growth)
- **Mechanism:** `handleOnlineJoint` `ifNeedParentUnits` (network.js:1298-1307) →
  `joint_storage.saveUnhandledJointAndDependencies` (joint_storage.js:70-95) writes rows into
  `unhandled_joints` + `dependencies` for every new unit whose parents are missing, then
  `requestNewMissingJoints` asks the peer for the parents. An attacker can mint units with random
  parents (content-hashed → unique hashes, trivial) and send them; each is stored pending.
- **Source→sink→path:** attacker `["justsaying",{"subject":"joint","body":{unit:{unit:"<hash>",
  version:"4", parents:[...unknown...], ...}}}]` → `handleOnlineJoint` (1271) → `handleJoint` (1057)
  → validation `ifNeedParentUnits` → `saveUnhandledJointAndDependencies` (joint_storage.js:70).
- **Concrete input:** many unique units each referencing a random non-existent parent hash.
- **Expected outcome:** unbounded `unhandled_joints`/`dependencies` growth and `assocUnhandledUnits`
  memory growth during the flood; bounded only by `purgeOldUnhandledJoints` (joint_storage.js:343-357,
  deletes rows older than 1h) — but the purge itself runs only when
  `!bCatchingUp && online>1h && (clients>0 || outbound>0)` (network.js:1005-1009) and the large IN-list
  DELETE is a periodic DB spike. Flood rate is capped by the global `handleJoint` mutex.
- **Negative control:** joints whose parents exist → not stored as unhandled.
- **Disposition:** bounded resource-exhaustion DoS; node-side fix (cap per-peer pending count) →
  out-of-scope class per the DoS rule. Worth a lab growth-rate measurement.

### T5 — Peer-block bypass for two error classes
- **Mechanism:** network.js:1094-1102: after validation failure, `writeEvent('invalid', ws.host)` is
  skipped when `error === 'authentifier verification failed'` or `error.match(/bad merkle proof at
  path/)`. `peerIsBlocked`/`initBlockedPeers` (1873-1915) block hosts only on accumulated `invalid`
  events. So peers sending bad-signature or bad-merkle joints never accumulate blocking events.
- **Source→sink→path:** attacker joint with bad authentifier → `validation.validate` fails →
  `ifUnitError` → writeEvent skipped (1095) → no `invalid` event → never blocked.
- **Concrete input:** joints with invalid ECDSA signatures (or bad merkle proof) from one peer,
  sustained.
- **Expected outcome:** continuous validation work (ECDSA verify) from the abusive peer with no
  automatic block. Negative control: a peer sending structurally-invalid joints DOES accumulate
  `invalid` events and gets blocked after the threshold.
- **Disposition:** abuse-control gap; node-side fix → out-of-scope class; weak.

### T6 — `bugreport` justsaying → node sends emails with attacker-controlled content (config-dependent)
- **Mechanism:** network.js:2697-2720: if `conf.bug_sink_email` set, `mail.sendBugEmail(body.message,
  body.exception)` (mail.js:126-135). Attacker controls both. Dedup `prev_bugreport_hash` is computed
  over the attacker-controlled text → bypassable by varying the message → unlimited emails. Subject is
  newline-sanitized (`\s`→' '), body is plain text (nodemailer text, no html → no HTML injection).
- **Source→sink→path:** `["justsaying",{"subject":"bugreport","body":{"message":"<any>",
  "exception":"<any>"}}]` → sendBugEmail → SMTP send.
- **Expected outcome:** email flood to the operator's bug sink; log noise. Requires
  `conf.bug_sink_email` (not default).
- **Negative control:** bug_sink_email unset → `console.log("not sending bug email")`.
- **Disposition:** weak, config-dependent, not fund-related; operator-side fix.

### T7 — Hub device-message mailbox flood (attacker-controlled content delivered to a victim's mailbox)
- **Mechanism:** `case 'hub/deliver'` (network.js:3322-3420): any signed device message to a
  registered device is stored in `device_messages` (INSERT, no size/count cap beyond the 6MB
  transport maxPayload and the recipient's optional `max_message_length`) and forwarded to the
  addressee if connected. An attacker can deliver arbitrarily many messages to a victim's device
  address → mailbox growth + chat spam.
- **Source→sink→path:** attacker (signed with own key) `["request",{...,"command":"hub/deliver",
  "params":{to:"<victim device addr>",...}}]` → stored + forwarded.
- **Expected outcome:** unbounded `device_messages` rows for the victim address (per-device
  `max_message_count` ≤ 100 is enforced only if the VICTIM sets it at login). Negative control:
  victim with `max_message_count` set → hub refuses overflow.
- **Disposition:** chat-layer spam/storage DoS; not fund-related; per program rules likely below the
  minimum impact threshold. Weak. (Wallet-side parsing of the forwarded message is out of scope —
  F-other.)

## Held or refuted observations (with the decisive control)

- **H1 — Message parsing is crash-safe.** `onWebsocketMessage` try/catches `JSON.parse` (network.js:4110-4116), requires `content` to be an object, and unknown message types are logged, not thrown (the `throw Error("unknown type")` is commented out at 4136). Decisive control: malformed JSON → `console.log` return, no exception.
- **H2 — Command/tag validation is complete at the request entry.** `handleRequest` requires non-empty string command+tag, caps tag length at `HASH_LENGTH` (3090-3093), dedups in-flight identical requests (3094), and early-returns happen before `incrementPending` (balanced bookkeeping; `decrementPending` cannot be driven negative by a crafted sequence — each case either sends a response (which decrements) or explicitly decrements in `custom`/`default`).
- **H3 — The `light/*` command surface validates params thoroughly.** Checked every light command:
  addresses/counts capped (2000 history, 100 balances, 20 AAs), address/unit/hash formats validated,
  `last_ball_mci`/`amount` positive-integer checked, `amount <= MAX_CAP`, args depth-capped via
  `isTooDeeplyNestedOrHasTooManyNodes` (execute_getter). Decisive control: `light/get_history` with
  malformed `addresses` returns `ifError` (light.js:40-63), never reaches SQL.
- **H4 — No crash-on-crafted-message found (valid-unit crash class).** The network layer rejects
  unsigned joints (`"unsigned" in objJoint` at network.js:2727 and handlePostedJoint:1215), rejects
  balls on unsolicited joints (`objJoint.ball && !isGenesisUnit` at 2731), depth-caps joints and
  device messages (100/10000, string_utils.js:260), and catchup chains are witness-validated against
  OUR witness list (`catchup.processCatchupChain` → `witnessProof.processWitnessProof`, catchup.js:111).
  No message shape was found that deterministically crashes every honest node on a *valid* unit
  (the only handler throw is T2, hub-gated). Decisive control: negative tests of each gate.
- **H5 — S3 (depth/size limits) is covered on network paths.** `isTooDeeplyNestedOrHasTooManyNodes`
  is applied to joints (2735, 3228) and hub/deliver device messages (3345) and execute_getter args
  (3886); 6MB ws `maxPayload` (network.js:45) caps transport. Residual: `unhandled_joints` growth
  (T4) is a count-based, not depth-based, exhaustion.
- **H6 — Catchup cannot be used to inject a fake chain.** `processCatchupChain` validates the
  unstable-MC joints and witness-change joints against the node's own requested witness list and
  hash-verifies every proofchain ball (catchup.js:111-180). A malicious peer cannot feed a chain on
  different witnesses.
- **H7 — `version2int` is safe on all reachable paths.** Every caller validates the input is a
  string before calling (`version` handler 2647-2653; `subscribe` 3157-3160; `hub/get_arbstore*`
  read `ws.library_version` which was validated at login).
- **H8 — Private-payment direct network path is dead code.** `case 'private_payment'` returns an
  error first ("direct sending of private payments disabled, use chat instead", network.js:2751-2752);
  the remaining handler body is unreachable.

## Suspected_success candidates

None claimed. Closest is **T1** (mechanism + concrete input are statically verified, no cap, no rate
limit anywhere in the layer), but: (a) it is a resource-amplification DoS whose in/out-of-scope
classification per the engagement's DoS-coordination rule is undecided, (b) it has not been measured
in the lab, and (c) no fund-loss path. Per round-0 contract: `suspected_signal` (strong triple), not
`suspected_success`. T1 is the top round-1 lab-validation candidate for the network family.

## Gaps not covered and why

- **Live measurement of amplification factors** (T1, T4, T5): requires the local multi-node lab;
  static verification only this round. Recommend a lab harness: N peers × refresh(0) → measure node
  CPU/DB/egress; flood missing-parent joints → measure unhandled_joints growth rate.
- **`hub/message`/`hub/deliver` content handling on the RECEIVING wallet/device side** — the device
  message decode/parse path (`device.js`, chat layer) is outside this family's files; forwarded
  attacker content is parsed by the wallet layer (out of scope for the DLT surface) but may deserve a
  cross-family note (F-other).
- **Deep `validation.validate` internals** (authentifier/definition/formula paths) — handed to
  families f1/f3/f4/f5; the network layer's interaction (callbacks, mutex, purge) is covered here.
- **Race conditions between `handleJoint` mutex and per-host counters under reconnect storms** —
  partially covered (H2, H7); a sustained reconnect-flood test belongs to f13 (races/TOCTOU).
- **Proxy `x-real-ip` trust** (network.js:4186-4189): when the node is behind a proxy on a private
  network, any client on that network can spoof `x-real-ip` and therefore its identity for
  blocking/rate purposes. Noted but not exploitable from public internet; environment-specific.
