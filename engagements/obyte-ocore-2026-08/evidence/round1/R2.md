## P4 — MySQL sequence coercion → ball-hash divergence

### Link 1 — operator precedence and Oracle MySQL coercion

**Precedence: CONFIRMED.** Unary `+` binds tighter than `=` in every SQL dialect, so `+competitor_units.sequence='good'` parses as `(+competitor_units.sequence) = 'good'`. Live query at `main_chain.js:1415` (comment copy at 1401).

**Backend behavior — measured locally (sqlite + MariaDB 12.3.2, the exact version the f2 hunter tested):**

| backend | `+sequence` on `'final-bad'` | `+sequence='good'` for `'final-bad'` |
|---|---|---|
| sqlite (verified live) | `'final-bad'` (no-op) | 0 — correct |
| MariaDB 12.3.2 (verified live) | `'final-bad'` (**no-op — no coercion**) | 0 — correct |
| Oracle MySQL 8 (documented only, no Oracle server available locally) | `0` (string→number coercion) | 1 — **matches ALL rows** |

Live MariaDB run (this round):

```
SELECT sequence, +sequence AS unary_plus, (+sequence)='good' AS matches_paren, 0='good' AS zero_eq_good FROM p4test;
sequence   unary_plus   matches_paren   zero_eq_good
good       good         1               1
final-bad  final-bad    0               1
temp-bad   temp-bad     0               1
```

Key facts:
- On **MariaDB**, `+` on a TEXT column is a **no-op** (returns the string), so the filter is correct — **f2's observed result is reproduced, but the important nuance is that MariaDB agrees with sqlite**, so the divergence is *Oracle-MySQL-only*, not "MySQL-family vs sqlite".
- `0='good'` → 1 on MariaDB (number-vs-string comparison coerces the string to a double) — the coercion exists in the family, but unary `+` on a column does not trigger it in MariaDB.
- **Oracle MySQL 8**: documented semantics — unary plus converts the operand to a number (`+'final-bad'` → `0`, with a "Truncated incorrect DOUBLE value" warning), and a number-vs-string comparison converts the string to a double (MySQL 8.0 Reference Manual §12.3 "Type Conversion in Expression Evaluation": *"In all other cases, the arguments are compared as floating-point (double-precision) numbers"*). Hence `0='good'` → TRUE and the predicate matches `good`, `temp-bad` and `final-bad` alike — the filter becomes a no-op. **Documented, not live-verified** (no Oracle MySQL 8 available locally; residual risk noted).

### Link 2 — do Obyte full nodes run Oracle MySQL? → **decisive refutation**

- `conf.js:66-68`:
  ```
  // storage engine: mysql or sqlite
  // mysql is not currently supported
  exports.storage = 'sqlite';
  ```
  The "mysql is not currently supported" line was added by core maintainer **tony on 2026-07-11** (commit `a5f7551` "mysql support note") — one month before the pinned commit. This is the maintainers' formal statement of the supported configuration.
- The mysql backend exists (`db.js:5-19` → `mysql_pool.js`) but last substantive maintenance is 2019-2020 (`55bbf29` 2019-06-21, `3f08fde` 2020-08-20); `9d15a9f` (2026-02-19) is an incidental Object.assign cleanup. No MySQL tests exist in `test/` (suite is sqlite-only).
- **Decisive control for severity:** the consensus set runs the supported sqlite backend; a MariaDB node (the installed MySQL-family server) computes the same filter result as sqlite. An Oracle MySQL node is an unsupported, unmaintained deployment with no evidence of existence (live-node census is prohibited by the engagement rules). With no Oracle MySQL in the node set, there is **no divergence and no consensus impact**.

### Link 3 — does sequence enter getBallHash, and would divergent resolution change consensus?

**Mechanism: CONFIRMED.** `main_chain.js:1485`:
```js
var ball = objectHash.getBallHash(unit, arrParentBalls, arrSkiplistBalls.sort(), objUnitProps.sequence === 'final-bad');
```
`object_hash.js:105-114`: `bNonserial` adds `objBall.is_nonserial = true`, changing the base64 hash. Balls are stored per-node (`main_chain.js:1493-1496`, plus the kv-store joint record) and flow into downstream ball chains (parent_balls/skiplist_balls) and hash-tree/catchup/light proofs. So a unit that resolves `good` on one node and `final-bad` on another **does** produce different balls and a divergent ball DAG.

**Reachability of a divergent resolution:** the widened filter only *adds* competitors (stable `final-bad` same-author units), so an Oracle-MySQL node resolves strictly *more* units `final-bad` than sqlite. A constructive scenario requires a same-author fork (same-author forks are explicitly accepted at validation — `validation.js:1312` "will accept a conflicting unit") in which a temp-bad unit's only window competitors are `final-bad` units. The construction is intricate (the window bounds `(latest_included_mc_index, main_chain_index]` and the good-unit competitors tend to leak into both backends' result sets) and was **not demonstrated** — no Oracle MySQL was available to exhibit an actual divergence. The same `+sequence='good'` idiom also appears at `validation.js:845, 846, 853, 874, 1328, 1333`; on an Oracle MySQL node, site 1333 could even flip `final-bad` rows back to `temp-bad`. All of this is moot without link 2.

### Link 4 — canonicalization before the query?

**None exists and none is applicable.** `sequence` values are node-generated literals (`'good'`/`'temp-bad'`/`'final-bad'`, written at `validation.js:1185, 1321-1322`, `main_chain.js:1296, 1303, 1319`); no user-controlled input reaches the column, and no layer normalizes the predicate. The issue is pure SQL-dialect sensitivity of the `+` idiom on a string column — a one-line fix (`sequence='good'`).

### P4 verdict

- Mechanism (precedence + documented Oracle coercion + ball-hash dependence): **confirmed in source**.
- Live-network consensus divergence: **refuted** — decisive control `conf.js:67-68` ("mysql is not currently supported", commit `a5f7551`, 2026-07-11); MariaDB (verified) matches sqlite; Oracle MySQL-only divergence requires an unsupported deployment.
- Residual: latent hazard + code-quality issue; if Oracle MySQL support returns or any node runs it, the filter silently matches everything. Oracle-MySQL-8 coercion itself is documented but not live-verified here (no server available).

## P6 — tps-fee `exp()` blow-up → author balance poisoning

### Link 1 — reachability of count≥30 with elapsed=1

**Equal timestamps are valid.** `storage.js:1174`: `elapsed = (objMcUnitProps.timestamp - objLastBallUnitProps.timestamp) || elapsedTimeWhenZero` (`elapsedTimeWhenZero = 1`, `storage.js:44`). A unit's timestamp must be a positive integer ≤ `now+5` (`validation.js:280-285`) and ≥ its *parents'* timestamps (`validation.js:692-693`, equality allowed); the `last_ball_unit` is only required to exist, have a ball, and be included in the parents (`validation.js:722-740`) — **no "must be the newest ball" check**, and no timestamp relation to the last-ball unit. An attacker can therefore author a chain of units all sharing the last-ball unit's second → elapsed=1.

**Measured through the real path** (lab, `evidence/round1/r2-tps-fee-drive.js`, real `storage.getFinalTpsFee` + `storage.updateTpsFees` with a synthetic stable-unit cache shaped like a 30-unit flood window):

```
count=30 elapsed=(T-T)||1
final tps fee (base units) = 106864745815235 = 106864.745815 GBYTE
author AUTHOR tps_fees_balance after settlement = -106864745815235
author HONEST tps_fees_balance after settlement = -106864745815218   (declared 17, delta = 17 - fee)
```

- count=30, elapsed=1 → fee ≈ **106,865 GBYTE ≈ 10.7% of total supply** (`constants.js:15` `TOTAL_WHITEBYTES = 1e15` base = 1,000,000 GBYTE). Matches `10×(exp(30)−1)` (base_tps_fee=10, tps_interval=1, `initial_votes.js:36-37`).
- The honest author's balance goes to **−106,865 GBYTE**; the `validation.js:1087` gate (`tps_fees_balance + declared < min_tps_fee`) then hard-rejects any later unit with a normal declared fee (verified in `r2-sqlite-infinity-test.js`: balance −10686474581524 + 17 < 17 → rejected).
- **Self-limiting?** The min-fee gate prices the *attacker's own* units (each flood unit must declare ≥ its local estimate, and ≥ `current_tps_fee × multiplier × count` with multiplier 5 when recent tps > 15, `storage.js:1452-1456`), and `validation.js:2649-2653` requires the unit's inputs to **fund the declared fee**. It does **not** prevent the poisoning — it caps it at what the attacker can afford to declare and fund.

### Link 2 — sqlite Infinity/NaN in the INT column → **Infinity claim refuted**

Measured (`r2-sqlite-infinity-test.js`, real sqlite3 binding):

```
A stored: -Infinity   (persists!)   -> gate with declared 17: rejected = true
B stored: Infinity    (persists!)   -> gate with declared 17: rejected = false
C stored: NaN -> 0                 (NaN coerced to 0, no poisoning)
D stored: -10686474581524          (count=30 magnitude, exact)
```

So an Infinity balance *would* store and permanently freeze — **but Infinity is unreachable**:
- `fee = Math.round(base_tps_fee × (exp(tps)−1))` overflows double only at tps ≥ 710 (`Decimal.exp().toNumber()`: exp(709)=8.2e307 finite, exp(710)=Infinity — measured).
- The final flood unit must **declare and fund** a fee ≥ `10×(exp(710)−1) ≈ 3.3e309` base units (`validation.js:1087` gate + `validation.js:2649-2653` input funding). Total supply is 1e15 base — even holding **100% of the money supply** caps count at ≈ 32 (`10×(exp(32)−1) ≈ 2.2e15`). count=710 is unreachable by ~20 orders of magnitude.
- **Decisive control:** `validation.js:2649-2653` (inputs must cover the declared tps_fee) + `validation.js:1087` (min-fee gate) bound the fee to the attacker's real funds.

### Link 3 — recovery / permanence → **"permanent freeze" overstated**

- `updateMissingTpsFees` (`storage.js:1288-1306`) only fills *gaps* between `getLastTpsFeesMci()` and `last_stable_mci`, recomputing the **same** deltas from the same DAG — idempotent, no recovery. The poisoned `(address, mci)` rows persist (they are the newest rows, so gap-fill never re-runs them).
- Restart: `initCaches` (`storage.js:2521-2534`) reloads the persisted balances; nothing resets them.
- Other authors in the window: recipients default to the unit's own author (`storage.js:1460-1461`), so each author's balance is debited **only by their own units' deltas** — the poisoning is per-author, not shared.
- The only recovery is overpaying on future units (declared ≫ final → positive delta ≈ declared), which requires the author to hold and spend > the debt (~106,865 GBYTE per poisoned unit). Authors holding ≤ the debt are effectively permanently frozen; larger holders can recover at ≈ the debt's cost. The brief's "permanently frozen" holds only for the former class.

### Link 4 — 200%-expense feasibility

- Attacker expense ≈ **106,865+ GBYTE ≈ 10.7% of the entire money supply** (the final flood unit's declared fee, which the min-fee gate forces and inputs must fund; earlier units can be made cheap by pointing `last_ball_unit` at an older ball — allowed by `validation.js:722-740`).
- Per-poisoned-author damage ≈ the debt (~106,865 GBYTE of authoring capacity) — roughly **1:1 with the attacker's expense**, i.e. under the program's "direct financial damage ≤ 200% of attacker's total expense" bar (`program-policy.md:70`). Damage exceeds 200% only for a single whale author holding > 213k GBYTE.
- The attack is **scatter, not targetable** — it hits whatever honest units land on the attacker's final flood MCI (same-second authors). Combined with the attack-investment and griefing-downgrade feasibility rules (`program-policy.md:102-106`), the finite version lands below the in-scope bar.

### P6 verdict

- **Infinity claim: refuted** (decisive control `validation.js:2649-2653` + `validation.js:1087` — funding bound caps count ≤ ~33; measured exp(710)=Infinity, unreachable).
- **Finite poisoning (count≈30, elapsed=1): confirmed through the real path** (measured fee ≈ 106,865 GBYTE; honest balance → −106,865 GBYTE; `validation.js:1087` hard-rejects subsequent normal-fee units). Equal timestamps are valid; the min-fee gate prices but does not prevent.
- **Permanence: refuted as stated** — repayable debt for holders > debt; no code recovery path exists (`storage.js:1288-1306` idempotent, restart no-op).
- **Severity: economics-capped below the in-scope bar** (attacker spends ≈10.7% of supply for ≈1:1 per-author damage; scatter; griefing downgrade applies).
