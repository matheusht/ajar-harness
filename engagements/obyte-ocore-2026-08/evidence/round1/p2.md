## Answers to the brief's three flows for 2289

- **(a) private-elements chain flow** — REFUTED: the elements flow's input-level check mirrors the
  message-level graph decision (exp-c fork: accepted, no crash). The only state that errors it
  (included good conflict) requires B to be saved while such a conflict exists — impossible (see
  above; exp-a 'good' is the empirical proof).
- **(b) concurrent-validation race** — REFUTED: within a node, `handleJoint` serializes validation
  (network.js:1057+); cross-node, a B whose parents include U1 cannot be validated before U1 exists
  on that node (parents-exist check), and once U1 exists its spend_proofs row exists → message-level
  rejection. No interleaving found where the input-level fires first with an error.

  spend proof(s)" (exp-a 'no-sp').

## The reachable crash (1678 + 2450) — attacker narrative

1. Attacker (owner of private output X, who retains the spend proof P as bearer secret) broadcasts
   U1: a private payment spending X.
2. Attacker broadcasts U2 spending the same public fee input as U1 → `checkSerialAddressUse`
   (validation.js:1303-1339) marks both unstable conflicting units temp-bad
   (`UPDATE units SET sequence='temp-bad' WHERE unit IN(?) AND +sequence='good'`, :1333).
3. The MC includes U1 (main_chain_index set, is_stable=0, sequence='temp-bad') — the window between
   MC inclusion and stability resolution.
4. Attacker broadcasts B: spending X with spend proof P, parents including U1 (or descending from
   it). B's message-level `validateSpendProofs` → `checkForDoublespends` → U1's `(P, owner)` record:
   owner ∈ B's authors; U1 included; `main_chain_index <= last_ball_mci`; sequence temp-bad →
   **throw at 1678 → uncaught → full-node crash** (network.js:4367 re-throw). Every full node that
   validates B crashes; B re-delivery re-crashes.
5. Public-asset variant: any unit spending an output of a stable temp-bad unit → 2450 crash
   (no spend_proofs required).
