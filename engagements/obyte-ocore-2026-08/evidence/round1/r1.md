# R1 — Refutation of the private-payment crash family (P1: validation.js:1662/1667; P2: 2289/2292, 1678/1686)

**Refuter:** R1 (fresh context, adversarial) · **Target:** ocore pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`
**Sources read:** `evidence/round0/f1.md` (T1), `f7.md` (C1/C2), `f8.md` (TRIPLE-1/2/3/5), `f13.md` (T-A), `round1/BRIEFS.md` P1/P2, plus the pinned source at the file:line level.
**Empirical:** `evidence/lab/r1/p1-refute.js` (real path: `composer.composeJoint` → `validation.validate` → `writer.saveJoint`; synthetic genesis; run log `evidence/lab/r1/p1-refute.raw.log`).

Verdict up front: **all four claimed crash sites are refuted**. P1's construction is blocked by an
address-binding check the round-0 hunters missed (validation.js:1557–1568); P2-2292 is blocked by
flow ordering + serialization; P2-1686 is blocked by the sequence state machine. The uncaughtException
crash *mechanism* itself (network.js:4367–4379 re-throw) is real — but none of the four validation
throws is reachable from attacker input through the real path.

## 1. The crash mechanism (link 2) — CONCEDED as a mechanism, irrelevant per site

- `process.on('uncaughtException')` at network.js:4367–4379 logs then `throw err; // crash the process to avoid ending up in an inconsistent state` (4379). A throw inside a `conn.query` callback escapes to the event loop: `sqlite_pool.js` query wrapper (241–270) invokes the callback with no try/catch; `async` 2.6.4 `_eachOfLimit` invokes iteratees with no try/catch (verified in `node_modules/async/dist/async.js` `_eachOfLimit` → `iteratee(elem.value, elem.key, onlyOnce(iterateeCallback))`); `mutex.exec` (mutex.js:47) invokes `proc` with no try/catch. So *any* throw in these positions kills the process.
- **Incidentally confirmed empirically:** during lab bring-up the composer's own async throw (`parent_composer.js:461` "all potential parents underpay the tps fee") crashed the lab process through exactly this handler — mechanism real.
- **But:** the four validation sites below are not reachable, so the mechanism is moot for this family.

## 2. P1 — validation.js:1667 (`throw Error("conflicting <type> spent from another address?")`) — REFUTED

Claim (f8 TRIPLE-1): attacker authors unit A spending the victim's private output X with
`spend_proofs:[{address: <victim_addr>, spend_proof: P}]`; any node holding the victim's spend-proof
row (P, victim_addr) throws at 1667 → crash.

**Decisive control — validation.js:1557–1568 (before `checkForDoublespends`):**

```js
// validation.js:1557-1562 (single-authored)
if (arrAuthorAddresses.length === 1){
    if ("address" in objSpendProof)
        return callback("when single-authored, must not put address in spend proof");
    address = arrAuthorAddresses[0];
}
else{ // validation.js:1563-1568 (multi-authored)
    if (typeof objSpendProof.address !== "string")
        return callback("when multi-authored, must put address in spend_proofs");
    if (arrAuthorAddresses.indexOf(objSpendProof.address) === -1)
        return callback("spend proof address "+objSpendProof.address+" is not an author");
    address = objSpendProof.address;
}
```

These run in `validateMessage` **before** the `async.series([validateSpendProofs, validatePayload])`
that reaches `checkForDoublespends` (1640–1654). Consequences:

1. **Single-authored A** (the f8 construction): an explicit `address` field is rejected outright at
   1560 — clean unit error, **no crash**. Without an explicit address the match query uses
   `authors[0]` = attacker's address → the victim's row (P, victim_addr) does **not** match → no
   conflict at all.
2. **Multi-authored A**: the spend-proof address must be one of A's authors (1565–1567). The match
   query (`spend_proof=P AND address=<author>`) therefore can only return rows whose address is
   among A's authors → `arrAuthorAddresses.indexOf(objConflictingRecord.address)` can never be -1 →
   **the guard at 1667 can never fire** for the message-level spend-proof path. (The victim cannot be
   made a co-author without the victim's key.)

The same argument applies to the input-level invocation (type "divisible input", 2264+): reaching
`checkInputDoubleSpend` for a *private* asset requires the private-chain payload flow (`bPrivate`,
set only at validation.js:2695) or an inline payload (rejected for private assets at
validation.js:2091 `"asset privacy mismatch"` — `bPrivate` is never set on the inline path). The
payload flow's own spend-proof comparison (divisible_asset.js:102–150; indivisible_asset.js:20–31)
binds the message spend proofs to the true output-owner's address **before** `validatePayment` runs
(`arrFuncs = [validateSpendProofs, validatePayment]`, divisible_asset.js:137–143) — any payload that
passes it carries the owner's address, which re-arms the message-level guard (clean rejection /
1667-impossible) for a second spender.

**Empirical (raw log):**
- `U2` (victim, single-authored, `spend_proofs:[{spend_proof:P}]`) → VALIDATION OK, saved; row `(P, victim_addr)` present in `spend_proofs`.
- `A_own` (attacker, same P, implied address) → **VALIDATION OK, saved, NO crash** (this is f8's TRIPLE-2 fork behavior — a real economic-race observation, but not a crash).
- `A_victim` (attacker, `spend_proofs:[{address: victim_addr, spend_proof: P}]`) → **clean rejection `"when single-authored, must not put address in spend proof"`** (validation.js:1560), **NO crash**.
- `A_multi` (attacker1+attacker2, `address: attacker1`, P matching attacker1's own saved row) → reaches `checkForDoublespends` → `cb2(error)` → **clean unit error `"conflicting spend proof in inner unit …"`** (1667 not taken: address ∈ authors), **NO crash**.

## 3. P2 — validation.js:2292 (`throw Error("spend proof didn't help: "+err)`) — REFUTED

Claim: reachable via (a) private-elements chain flow, (b) concurrent-validation race, (c) missing
`spend_proofs` message.

- **(a) chain flow:** the unit-level message check (`validateSpendProofs`, 1644–1654) runs on **every**
  node at unit arrival — `handleJoint` → `validation.validate` → `validateMessages` (network.js:1057+,
  1086) — and the payload flow **waits for the unit** (`handleOnlinePrivatePayment` → `checkIfNewUnit`
  ifKnown/ifNew, network.js:2269–2295; `ifNew` queues the payload and requests the joint). A unit
  that would create the conflicting `inputs` row must itself have passed its own message-level check
  and been saved (spend_proofs row inserted in the same `saveJoint` transaction, writer.js:280–285).
  The second spender's message-level check therefore always sees the first spender's row before any
  payload of the second spender is processed → clean rejection (address ∈ authors) → 2292 never
  reached. The address-mismatch dodge is closed by the payload-level comparison
  (divisible_asset.js:102–150: recomputed proof includes `src_output.address`, compared against the
  unit's stored rows; mismatch → `"incorrect spend proof"` clean error).
- **(b) concurrent-validation race:** refuted by serialization — `handleJoint` runs validate + save
  under the single `['handleJoint']` mutex (network.js:1071–1075; `writer.saveJoint` called inside
  `ifOk` at 1165). Two units cannot interleave their message-level checks with each other's row
  inserts. Cross-process races are outside the single-node model and, even if present, only affect
  which unit is rejected — the loser is still cleanly rejected at its message check.
- **(c) missing spend_proofs:** `payload_location:'none'` without `spend_proofs` is a **clean
  rejection** at validation.js:1613–1616 (`"private payment must come with spend proof(s)"`) — never
  reaches the input check.

## 4. P2 — validation.js:1686 (`throw Error("unreachable code, conflicting …")`) — REFUTED

Requires a conflicting record with `main_chain_index <= last_ball_mci` (not "too young") and
`sequence` neither `'good'` nor `'final-bad'` — i.e. **stable + temp-bad**. The state machine forbids
this: a temp-bad unit on the MC is resolved to `'good'` or `'final-bad'` by
`handleNonserialUnits` (main_chain.js:1322–1333) **inside the same `stabilizeMci(mci)` call that
creates the balls for that MCI** (`propagateFinalBad(arrFinalBadUnits, addBalls)`, main_chain.js:1333;
`addBalls` at 1441). Since `last_ball_mci` is the MCI of the last created ball, a unit's
`main_chain_index <= last_ball_mci` implies its MCI has a ball, which implies its temp-bad state was
already resolved. The sibling throw at validation.js:2451 (`"spending a stable temp-bad output"`,
gated on `bStableInParents`, 2449–2450) is blocked by the same impossible state.

## 5. Prerequisite links (bearer secret, delivery) — conceded as real, but non-crashing

- **Bearer-secret premise (link 3): CONCEDED.** `generateBlinding` = `crypto.randomBytes(12)`
  (composer.js:839); the blinding is put on each private output at compose time
  (divisible_asset.js:269) and stored in the sender's `outputs` row (divisible_asset.js:60) and in
  the sender's private payload; the transfer spend proof is a deterministic hash of
  `{asset, amount, address, unit, message_index, output_index, blinding}` (inputs.js:73–80). The
  sender retains everything needed to recompute P at any time. (This is f8 TRIPLE-3 — a design-level
  observation, not a crash enabler once 1557–1568 is accounted for.)
- **Delivery path (link 4): CONCEDED as a mechanism.** A unit with `payload_location:'none'` needs no
  payload to be gossiped; every full node processes every unit; the victim's node can be forced to
  validate A. But validation of A is exactly where the clean rejection happens — no crash.

## 6. What survives (residual, non-crash)

- **f8 TRIPLE-2 fork behavior confirmed empirically:** `A_own` (same spend proof P, attacker address)
  is accepted as a good unit while the victim's row (P, victim) exists — the private-payment
  doublespend is invisible to the standard check and resolution is deferred to the fork race. This is
  an economic/payment-race issue, not a crash; out of my refutation lane, flagged for the operator.
- The uncaught-throw pattern itself (network.js:4379) is a hardening note: any future reachable throw
  in these async completion paths becomes a network-wide crash-loop; the 05f291d8-style `cb2(err)`
  conversion for the light path was never mirrored on the full-node path because the full-node throw
  sites are unreachable today.
