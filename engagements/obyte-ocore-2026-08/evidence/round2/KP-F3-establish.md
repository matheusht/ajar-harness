**Worker:** KP-F3-establish (fresh context, blind to the killer brief)
**Target:** ocore pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`
**Sources read:** `evidence/round0/f8.md` (TRIPLE-2/3), `evidence/round1/r1.md` §1–§7 (incl. §6), `evidence/round2/BRIEFS.md`, plus pinned source at file:line and the Obyte design context cited in the briefs.
**Empirical (independent run, RAW output):** `evidence/lab/r1/kp-f3-establish.js` → `evidence/lab/r1/kp-f3-establish.raw.log` (real path: `composer.composeJoint` → `validation.validate` → `writer.saveJoint`; synthetic genesis; no mocks). I also re-ran the r1 experiment (`p1-refute.js`) and reproduced its §6 result.

**Verdict up front:** F3 is a **real defect**. The strongest TRUE form is not "the merchant is directly defrauded" (the code forces concessions there — the attacker's competing payload cannot materialize outputs, and the victim's unit is not voided in the same-branch case). The strongest TRUE form is:

> **The network's only unit-level anti-double-spend protection for private payments — the spend-proof uniqueness check (validation.js:1637–1654) — keys the conflict match on `(spend_proof, unit-claimed-address)` where the address is attacker-chosen and never bound to the private-output owner. A private-payment sender can therefore place a second `'good'` unit carrying the same spend proof on the main chain — even as a direct descendant of the recipient's own included spend — with no conflict detection, no rejection, and no resolution. The same economic act on a public asset is rejected cleanly at unit level. The designed early-detection protection is defeated for exactly the party it exists to constrain, and the private-vs-public asymmetry has no code-level design rationale.**

Severity: **Low–Medium payment-race / ledger-integrity defect** (see §7).

## 1. The mechanism, code-verified (pinned commit)

**The unit-level uniqueness check** — `validateSpendProofs`, validation.js:1637–1654:

```js
// validation.js:1640-1642
var arrEqs = objMessage.spend_proofs.map(function(objSpendProof){
    return "spend_proof="+conn.escape(objSpendProof.spend_proof)+
        " AND address="+conn.escape(objSpendProof.address ? objSpendProof.address : objUnit.authors[0].address);
});
// validation.js:1644-1648
checkForDoublespends(conn, "spend proof",
    "SELECT address, unit, main_chain_index, sequence FROM spend_proofs ... WHERE unit != ? AND ("+arrEqs.join(" OR ")+")", ...);
```

The conflict key is `(spend_proof, claimed-address)`. The claimed address is:
- single-authored: `objUnit.authors[0]` — the spender's own address (validation.js:1557–1562; an explicit `address` field is **rejected** here),
- multi-authored: any author's address (validation.js:1563–1568).

**It is never compared against the output owner.** The address the spend proof *cryptographically commits to* is the output owner's: the transfer spend proof is `objectHash.getBase64Hash({asset, amount, address: input.address, unit, message_index, output_index, blinding})` (inputs.js:73–80), where `input.address` is the owner of the source output; the payload-side recomputation reads it from the outputs table as `src_output.address` (divisible_asset.js:120–136). So a *true* spend proof P for the recipient's private output X is bound to the **recipient's** address — yet the unit-level check looks it up under the **spender's** claimed address.

**The spend proof is a bearer secret the sender retains.** The blinding is generated by the sender (`crypto.randomBytes(12)`, composer.js:839), attached to each private output at compose time (divisible_asset.js:266; indivisible_asset.js:426/434), and stored in the sender's own `outputs` row (divisible_asset.js:56–65). The sender therefore holds every field needed to recompute P for the recipient's output at any time. (Conceded by r1 §5 as link 3; re-verified here.)

**Consequence:** a unit A authored by the sender S carrying the *same* spend proof P as the recipient's unit C (row `(P, R)`) is checked under `(P, S)` — no row matches → **no conflict → A is accepted as `'good'` by every node**, regardless of arrival order, inclusion state, or even ancestry.

Key facts from the raw DB end-state:

## 3. The brief's questions, answered

### Q1 — What does the address-validation gap enable that the public-asset model cannot do?

A **descendant re-spend of an already-included, already-`'good'` private output is accepted** — permanently, on the main chain, in any arrival order, even after the victim's spend is saved/stable. In the public model the same act is structurally impossible at unit level: a second spend of an included-good output is rejected by `checkInputDoubleSpend` (validation.js:2252–2295; the conflicting record's address is the output owner, who must be the spender → the `throw` at validation.js:1667 is unreachable for public, and the clean error path fires). The lab's `A_multi` control demonstrates the public-style behavior on the *same* machinery: keyed to the right address, the duplicate spend proof is rejected. The gap is purely that the key is attacker-chosen.

Additionally, the public model's *resolution* machinery — `findConflictingUnits` (validation.js:1250–1272, query keyed `WHERE address=?` on the **author**) and the temp-bad/final-bad ladder (validation.js:1321–1333; `handleNonserialUnits` main_chain.js:1297–1333; `findStableConflictingUnits` main_chain.js:1393–1424, join `unit_authors USING(address)`) — is author-identity-keyed. A sender-vs-recipient double-spend has **different authors**, so *neither* the unit-level check nor the fork-resolution machinery can see it. Both defensive layers are structurally blind.

### Q2 — Is the designed early-detection protection (unit-level rejection) defeated?

**Yes.** The check exists to reject duplicate spend proofs at unit arrival ("uniqueness of spend proof" hardening, 05f291d8; the hard-error paths at validation.js:1667 and the "conflicting spend proof in inner unit" rejection). It rejects duplicates *only when the claimed address coincides*. The sender — the one party besides the owner who can compute P (Q1/Q5) — trivially claims their own address. The protection is therefore defeated for exactly the party that creates the payment. The empirical record shows the protection *firing correctly* in the multi-author control and *silently passing* in the sender case.

### Q3 — Can a merchant accepting a private payment be defrauded in a way the public model prevents?

**Partially — this is where the code forces the biggest concession.** The f8 expected-outcome ("merchant defrauded when C goes final-bad") does **not** hold in the same-branch case: my raw output shows the victim's unit U2 stays `'good'` and on the MC; nothing voids it, because no resolution mechanism fires (Q1). The attacker's own competing payload cannot even materialize: the payload-level binding (divisible_asset.js:95–165) recomputes P with `address: src_output.address` (the victim's) and compares against the unit's stored row `(P, attacker)` → mismatch → `"incorrect spend proof"` (divisible_asset.js:159) on the only node that can validate it (the sender's). So **no direct theft of the double-spent value and no voiding of the merchant's unit are demonstrated**.

What the gap *does* enable against a merchant, and the public model prevents:
- **Silent contest of a settled-looking payment.** After the merchant's payment unit C is included (even `'good'` on the MC), the sender can publish a competing `'good'` unit spending the same output. The merchant's node shows both units `'good'`; there is no rejection signal. In the public model the same act is a clean, visible unit rejection ("The transaction would be non-serial (a double spend)", network.js:1146). Any acceptance logic that keys on "unit accepted + included" (a common, reasonable public-model rule) is sound for public bytes and wrong for private bytes.
- **Fork-race pollution.** If the sender's unit wins the MC race (timing/parent anchoring — the F2-link question, out of this lane), the merchant's unit is off-MC; the merchant's "accepted" payment evaporates with no rejection ever having been emitted.
- **Permanent ledger corruption.** Two `'good'` MC-path units carry the same spend proof, forever unresolved (Q1). Every downstream consumer of the private ledger that trusts spend-proof uniqueness is wrong.

### Q4 — Is the private-vs-public asymmetry (clean rejection vs invisible fork) evidence of unintended behavior?

**Yes — strongest signal in the finding.** There is no code-level design rationale for the asymmetry:
- The check's query keys on the claimed address *only* to disambiguate multi-authored units (which author claims the proof) — validation.js:1563–1568 exists for that purpose and for nothing else. Nothing anywhere compares the claimed address to the output owner at unit level.
- The same code path treats a duplicate spend proof as a **hard error** when the addresses coincide (validation.js:1667; "conflicting spend proof in inner unit") and as **no event at all** when they differ. The intent to reject duplicates is unambiguous; only the key is wrong.
- The payload-level check (divisible_asset.js:159) *does* bind the address to the output owner — proving the designers knew the binding matters — but it runs only on the payload recipient's node, not as network consensus.
- The 05f291d8 fix ("uniqueness of spend proof is not verified in light") and the check's existence show the protection is a first-class invariant, not an accident.

No documentation in the pinned tree (README, code comments) describes the sender as allowed to publish a second `'good'` unit with the same spend proof. The asymmetry is best explained as an oversight in the check's keying.

### Q5 — Does the spend proof's documented purpose make fork-deferral a design violation?

The brief itself records the design context: spend proofs are published "to protect against double-spends" (blackbytes docs). Against that purpose:
- The uniqueness check *is* the network-wide double-spend protection for private payments (the payload is not in the unit, so the input-level check `checkInputDoubleSpend` cannot run network-wide for private payloads — it runs only where the payload arrives; validation.js:2695 sets `bPrivate` only in the payload flow).
- "Fork-deferral" (letting the MC race decide) is *not* a resolution mechanism for this case: in the same-branch construction the conflict is **never** resolved (Q1), and in the fork construction the resolution is timing/parent-selection, not validity. So deferral is not a working backstop — it is the absence of protection.
- A payer-controlled-output argument would only be consistent if the network rejected-or-resolved the sender's re-spend the way it does a public owner's own-output double-spend (temp-bad → final-bad at stabilization). It does neither, because both mechanisms are author-keyed.

So: **yes** — fork-deferral for the sender's re-spend violates the spend proof's documented purpose, because the deferral never resolves and the unit-level rejection the mechanism is built to provide is keyed out of reach.

## 4. Concessions (where the code forces me)

1. **No direct theft of the double-spent value.** The attacker's competing payload is rejected by the payload-level address binding (`"incorrect spend proof"`, divisible_asset.js:159) on the only node that can validate it. A's outputs never materialize.
2. **The merchant's unit is not voided in the same-branch case.** U2 stays `'good'` and on-MC (raw log). The f8 "C goes final-bad" expected outcome does not reproduce for the same-branch construction.
3. **The bearer property itself is conceded as (possibly) by-design.** The defect is not "the sender can recompute P" — it is "the network's only check on P is keyed on a party-chosen string". r1 §5 and f8 TRIPLE-3 both concede the bearer premise; the establishment case does not need it to be a bug.
4. **Fork-variant economics depend on the F2 link** (can the attacker's unit win the MC race) — outside this lane; recorded as the sizing dependency.
5. **DoS/robustness framings are out.** The A_victim crash (TRIPLE-1) is refuted (validation.js:1557–1568); no crash is involved in F3's true form.

## 5. What is NOT claimed

- Not "the merchant is directly defrauded of the payment" (concession 2).
- Not "the attacker creates money" (concession 1).
- Not a crash / availability issue.
- Not a full-node-only divergence: the acceptance is network-wide and order-independent (unit-level check identical on every node).

## 7. Severity assessment (honest)

- **Real defect: yes** (the check is defeated; the asymmetry is code-level and undocumentable).
- **Impact class:** payment-race / ledger-integrity — a private-payment sender can publish a permanent, undetected, unresolved duplicate-spend record on the main chain and silently contest a merchant's included payment, where the public model emits a clean rejection.
- **Direct financial impact:** bounded — no demonstrated theft or freezing of the double-spent value (concessions 1–2). Escalation to a fund-level claim requires either (a) a merchant acceptance flow keyed on unit-inclusion without uniqueness/stability guarantees for private payments (then the merchant *is* exposed in the fork variant), or (b) the F2-link showing the sender can win the MC race — both out of this lane.
- **Classification vs the program ladder:** not Critical (no theft/freezing/insolvency demonstrated); candidate **Medium** (payment-race against merchants accepting private payments, conditional on the acceptance-flow link) with an honest floor at **Low** (ledger-integrity/robustness). This matches the round-1 adjudication ("Low/Medium payment race").
- **Suggested fix direction (for the report, not the fix):** bind the unit-level uniqueness key to the output owner — i.e., resolve the spend proof's committed address (the payload-side recomputation, divisible_asset.js:120–136) at unit level, or store the output owner's address with the row and key the check on it.

## 8. Residual risks / open items

- **F2-link dependency:** fork-variant win probability and the merchant-exposure escalation (KP-F2-link).
- **Multi-private-asset interaction** (f8 gap note): per-tuple uniqueness across two private assets in one unit not verified.
- **Blinding entropy** (f8 gap note): `crypto.randomBytes(12)` = 96 bits — out of this lane (F12).
- **Same-author-with-two-addresses variant:** a multi-authored unit where the attacker signs with two keys can carry an explicit address equal to an author — the check fires only when the *victim's* row matches an author; the attacker's own-author keying still dodges it. Same defect, no fix.
