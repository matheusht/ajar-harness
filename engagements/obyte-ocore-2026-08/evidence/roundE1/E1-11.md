# E1-11 — AA storage-size economics: conservation audit + growth/shrink gates

Pinned: `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation lane E1-11. Real-path analysis +
empirical serialization check on the pinned tree. No AA-with-state lab fixture was run (see
Residual); the conservation proof below is stronger than a smoke test for the accounting question.

## Verdict (one line)

**Held/capped.** The storage-size accounting is conserved by construction — getValueSize (the
accounting measure) exactly matches the kvstore serialization for every value shape (16/16 shapes,
0 mismatches, measured). No path lets an AA grow state beyond its byte balance (gate active since
genesis) or shrink state to "steal" a released balance. **One robustness finding:** the periodic
`checkStorageSizes` audit (aa_composer.js:1913-1935) throws on ANY mismatch → uncaught → node
crash, scheduled at startup + every 10 minutes on every full node (aa_composer.js:2061-2062) — the
HN-2 uncaught-throw pattern; not attacker-reachable today (accounting conserved), capped at a
hardening note.

## Q1 — Can an AA grow state beyond its byte balance? NO (gate proven)

- **The gate** (aa_composer.js:1550-1551):
  ```js
  if (byte_balance < new_storage_size && new_storage_size > FULL_TRANSFER_INPUT_SIZE && mci >= constants.aaStorageSizeUpgradeMci)
      return cb("byte balance " + byte_balance + " would drop below new storage size " + new_storage_size);
  ```
- `aaStorageSizeUpgradeMci = 0` (constants.js:136) → the gate is active since genesis on every
  network that keeps the default. `FULL_TRANSFER_INPUT_SIZE = TRANSFER_INPUT_SIZE + (bWithKeys ?
  TRANSFER_INPUT_KEYS_SIZE : 0)` (aa_composer.js:456) — small states (≤ ~200 bytes) may exceed the
  balance, which is the documented free-small-state design, not a bypass.
- `new_storage_size < 0` is rejected with a throw (aa_composer.js:1554) — negative state is
  impossible through the trigger path.
- **Cap proven:** growth beyond `byte_balance` is blocked whenever storage exceeds
  FULL_TRANSFER_INPUT_SIZE. The only balance-exceeding states are the sub-threshold small states,
  bounded by construction.

## Q2 — Can an AA shrink state to "steal" the difference? NO (no mechanical release)

- Shrinking/deleting state reduces `storage_size` (aa_composer.js:1533-1536: `delta -= var_name.length
  + getValueSize(original_old_value)`). The `byte_balance` is the AA's own token balance — it is
  **not** a locked deposit; it is a minimum-balance requirement. Deleting state does not release a
  mechanism that was holding the tokens — the tokens were always the AA's, gated only on the way out.
- The transfer path keeps the buffer: send-all adds a change output of `amount: storage_size`
  (aa_composer.js:1069-1073) so a send-all cannot drop the AA below its storage requirement.
- An AA author who deliberately drains their own balance below `storage_size` (explicit outputs)
  is self-inflicting a liveness restriction (future growth blocked by Q1's gate) — no third-party
  benefit, no theft, no consensus effect.

## Q3 — Is the accounting conserved when state is written/updated/deleted? YES (proven)

**The write path** (saveStateVars, aa_composer.js:1479-1495) serializes each updated var via
`getTypeAndValue` (aa_composer.js:1497-1507):
- string → `'s\n' + value` (RAW, no JSON escaping)
- number → `'n\n' + value`
- Decimal → `'n\n' + value.toNumber()` (double conversion)
- wrappedObject → `'j\n' + string_utils.getJsonSourceString(value.obj, true)`

**The accounting measure** (getValueSize, aa_composer.js:1511-1521) mirrors it exactly (string
`.length`, number `.toString().length`, Decimal `.toNumber().toString().length`, object
`getJsonSourceString(...).length`).

**The audit measure** (checkStorageSizes, aa_composer.js:1913-1935) computes
`var_name.length + data.value.length - 2` (strips the 2-char type prefix) — the same quantity.

**Empirical verification (this run, exact replication of all three functions on the pinned tree):**

```
OK  plain string      stored= "s\nhello"            check= 5  accounted= 5
OK  string with quote stored= "s\na\"b"             check= 3  accounted= 3
OK  string with bslash stored= "s\na\\b"            check= 3  accounted= 3
OK  string with newline stored= "s\na\nb"           check= 3  accounted= 3
OK  unicode string    stored= "s\nhéllo→世界"        check= 8  accounted= 8
OK  number int/float/exp/-0/NaN/Infinity            all equal
OK  decimal high precision / subnormal / exp        all equal (double conversion on both sides)
OK  object nested (with quote inside)               all equal
TOTAL MISMATCHES: 0   (16/16 shapes)
```

**Lifecycle conservation (source-traced):**
- finish() (aa_composer.js:1691-1707) runs `fixStateVars()` (true→1, consistent on both sides),
  `saveStateVars()`, `updateStorageSize()` in the same transaction; an updateStorageSize error
  routes to `revert(err)` (aa_composer.js:1809-1831) which clears the batch and rolls back to the
  savepoint — the kvstore write and the storage_size UPDATE are both rolled back together.
- Cross-trigger chains (primary + secondaries, including self-trigger): `updateOriginalOldValues`
  (aa_composer.js:1559-1569) anchors `original_old_value` at the secondary's current value, so each
  trigger's delta is relative to the previous — summed deltas = final − initial (traced for create,
  update, delete, delete-then-recreate, true→1, and self-secondary).
- `state.value === false` (deletion) subtracts `var_name.length + oldSize`; re-creation in the same
  trigger adds the new size; a delete of a never-existing var subtracts 0 — all conserved.

## Robustness finding (candidate — HN-2 family, not attacker-reachable)

**checkStorageSizes throws on any mismatch → node crash; scheduled on every full node.**
(aa_composer.js:2061-2062: `setTimeout(checkStorageSizes, 1000); setInterval(checkStorageSizes,
600*1000)`; the throw at :1931 is inside a mutex callback → escapes to uncaughtException → crash).

- **Why not attacker-reachable today:** the accounting is conserved (Q3 proof) through every path
  an attacker can drive (formula state writes, triggers, secondaries, deletion). No mismatch was
  found.
- **The fragility:** (1) the rocksdb kvstore batch and the sqlite COMMIT are separate stores with
  NO cross-store transaction — a node killed mid-write (crash between the two commits) leaves
  `storage_size` ≠ kvstore state permanently; on restart the 1-second check throws → crash-loop
  until manual repair. (2) Any future accounting bug becomes a network-wide crash (10-min interval,
  all full nodes) instead of a soft alarm. (3) The correct pattern is the commented-out style of
  non-fatal auditing (or log+repair), matching the HN-2 recommendation (convert throws to events).

## Marginal-contribution note

- World without the throw: a mismatch would be logged/repaired instead of crashing the node.
- Delta: a permanent crash-loop AFTER any inconsistency arises (from a node kill mid-write, a
  future bug, or operator DB edits) — real availability consequence, but requires a pre-existing
  inconsistency. Below the in-scope bar (no attacker-controlled trigger found).

## Residual risks

1. **No end-to-end AA-with-state lab run.** The conservation proof is a direct, exact replication
   of the three functions on the pinned tree (stronger for the accounting question than a smoke
   test); an end-to-end trigger (define AA → write vars → trigger → compare kvstore vs
   aa_addresses.storage_size) would additionally exercise the batch/transaction ordering. Not
   performed: requires an AA-trigger lab fixture beyond this lane's scope.
2. **The crash-window ordering** (batch.write vs sqlite COMMIT order) was not empirically
   demonstrated; the inconsistency-on-kill claim is argued from the two-store design. The exact
   order determines which side is stale after a mid-write kill.
3. **`fixStateVars`/`updateOriginalOldValues` interactions** were traced, not executed; the
   self-secondary double-account case is argued conservatively (delta-anchored) — a full AA chain
   run would close the last 1% doubt.
