# E1-12 — Multisig wallet paths audit (wallet_defined_by_addresses.js + wallet_defined_by_keys.js)

**Scope flag:** this family is the WALLET layer — outside the declared DLT surfaces (SF-1..SF-10) per

## Verdict (one line)

**One confirmed wallet-layer finding (quarantine candidate): an unauthenticated, remote, permanent,
silent DoS on multisig wallet creation via `extended_pubkeys` row injection (`my_xpubkey` accepted
from non-correspondents with no membership or wallet validation).** Plus design observations and
held negatives (threshold semantics, signing determinism, address-resolution races).

## Finding W1 (confirmed, quarantine candidate) — permanent silent DoS on multisig wallet creation

### Mechanism
1. `device.js:214` allows `my_xpubkey` from **non-correspondents** (unpaired devices).
2. `wallet.js:162-170` `case "my_xpubkey"`: validates `body.my_xpubkey` is a string ≤112 chars but
   does **not** validate the wallet id format, wallet existence, or sender membership.
3. `wallet_defined_by_keys.js` `addDeviceXPubKey` (361-378): `INSERT OR IGNORE INTO
   extended_pubkeys (wallet, device_address) VALUES(?,?)` then
   `UPDATE extended_pubkeys SET extended_pubkey=?, approval_date=... WHERE wallet=? AND
   device_address=?` — the sender's device_address is inserted as a **new member** with an
   approval_date, with **no membership check**. `extended_pubkeys` has **no FK** to wallets
   (initial-db comment).
4. `checkAndFullyApproveWallet` (140-167): requires every row to have `approval_date` — the
   attacker's row has it → `full_approval_date` is set; notifications
   (`sendNotificationThatWalletFullyApproved`) go to **all** rows including the attacker's.
5. `checkAndFinalizeWallet` (123-138): requires every row to have `member_ready_date` — the
   attacker's row never gets one unless the attacker responds → **the wallet never reaches
   `ready_date` → permanently unusable**, with no error surfaced anywhere.
6. **No removal path:** `deleteWallet` (332-360) requires the rejector's row to have NO
   approval_date (`if (rows[0].approval_date) return onDone(); // you've already approved, you
   can't change your mind`) — the attacker's row HAS approval_date → cannot be declined away.
   `cancelWallet` is initiator-only and re-creating with the same xpubkey reproduces the same
   wallet id (wallet = sha256(xPubKey)) → same poisoning.

### Empirical confirmation (real schema + real query logic, lab scratch sqlite)
- BEFORE injection: 2 legit rows, all `member_ready` → wallet finalizes.
- AFTER the attacker's row (exact addDeviceXPubKey SQL): 3 rows; attacker row has approval_date,
  `member_ready_date = 0` → `all member_ready: false` → **ready_date never set**.
- `deleteWallet` on the attacker row: approval_date set → "already approved" → row kept.
- Malformed xpubkey "x" in the attacker row: `new Bitcore.HDPublicKey("x")` throws → and
  `deriveAddress` (544-568) iterates **all** extended_pubkeys rows calling `derivePubkey` on each →
  a malformed injected xpubkey additionally crashes address derivation for the wallet.

### Reachability (honest)
The attacker must know the wallet id (44-char base64 = sha256(initiator_xpubkey)). It is sent
E2E-encrypted to members, so the realistic attacker is a **malicious invited cosigner using a
second device**, a compromised member device, or any party the id leaks to. Once known, the attack
is remote, zero-cost, unauthenticated (non-correspondent), and silent.

### Marginal contribution (what the bug adds over the world without it)
- Without the bug: a malicious invited cosigner can only **decline** — visible to the initiator
  (`wallet_declined` event), the wallet is deleted, and creation can be re-attempted.
- With the bug: **silent** (no decline event — the initiator waits indefinitely), **permanent**
  (no removal path), **works after all members already approved** (injection after final approval
  still blocks ready_date), and **available to any device** that knows the id (not just members).
  Also leaks all derived wallet addresses to the injected device (`issueAddress` →
  `sendNewWalletAddress` iterates extended_pubkeys rows, including the attacker's).

### Severity (if the operator widens scope)
Low–Medium: availability of the multisig wallet feature; zero-cost; permanent; silent; requires the
wallet id. Not fund loss (no signing power gained — see H1).

### Fix directions
1. `addDeviceXPubKey`: verify the wallet exists AND the sender is a member (row pre-created by
   `addWallet`); reject otherwise.
2. `my_xpubkey` handler: validate the wallet id (length/format) + membership.
3. Remove `my_xpubkey` (and `wallet_fully_approved`) from the non-correspondent allowlist
   (device.js:214) — only paired members should send them.
4. `deriveAddress`: iterate the template's member rows only, never attacker-injectable rows.
5. Add a removal path for injected rows.

## Design observations (no marginal impact, recorded)

### O1 — Shared-address member-address substitution unverified
`approvePendingSharedAddress` (wallet_defined_by_addresses.js:150-232) trusts each member's
submitted `address` and `device_addresses_by_relative_signing_paths` without verifying they derive
from the template/member key. Analysis: substitution yields **no marginal signing power at any
threshold** (a malicious member can already sign with their honest address; the final definition is
the r-of-set of the submitted addresses; for required=1 the honest member can still spend; for
required≥2 the attacker still needs honest signatures). The anomaly is undetectable substitution +
a possible self-inflicted freeze (submit an address they can't sign) — hygiene gap, not exploitable.
The approval message requires an established correspondent (not in the non-correspondent allowlist).

### O2 — `deriveAddress` iterates all extended_pubkeys rows (fragility amplifier for W1)
Even a benign-looking extra row changes `params`/derivation inputs; the function throws on any row
without an xpubkey or with a malformed one. Template-bound iteration would remove the coupling.

## Held / refuted (decisive controls)

- **H1 — injected member gains no signing power.** Signing is template-bound: the signer assembly
  uses the definition's signing paths via `wallet_signing_paths` (wallet.js:493, 668, 687) and
  `readFullSigningPaths`/getSigner (wallet.js:1968+); the derived address params only reference
  `pubkey@<template-member>`. The attacker's extra row is unreferenced by the template → no
  signatures requested from it. The E2E auth (device message signatures) also prevents
  cross-device xpubkey substitution (the UPDATE is keyed on the sender's own device_address).
- **H2 — threshold semantics sound.** r-of-set validated in the definition engine (definition.js:
  `required` positive integer, set length ≥2, required ≤ set length); `createMultisigWallet`
  additionally throws if required > members (wallet_defined_by_keys.js:260-267). required=1 is
  intentionally allowed (the "use or instead" checks are commented out) — semantically valid.
- **H3 — signing order determinism sound.** Signatures are over `objectHash.getUnitHashToSign`
  (binds all unit content except authentifiers); authors are sorted by authentifier count
  (composer.js:553) and placeholder sigs are filled deterministically (composer.js:895); the unit
  hash is authentifier-independent → no ordering divergence (consistent with f15 H3).
- **H4 — address→definition resolution race held.** `deriveAddress` requires `full_approval_date`
  and throws if any row lacks an xpubkey; since full approval requires all member xpubkeys, the
  throw is unreachable in the normal flow (a member's late xpubkey cannot precede its own
  approval). The injected-row case is W1's, not a separate race.
- **H5 — offer/template validation sound.** `handleOfferToCreateNewWallet`
  (wallet_defined_by_keys.js:65-113) validates the cosigner list exactly equals the definition's
  member devices (pubkey→device_address binding checked) and `validateWalletDefinitionTemplate`
  (485-518) validates the definition with a fake unit. A malicious initiator cannot inject a
  non-member into the template.
