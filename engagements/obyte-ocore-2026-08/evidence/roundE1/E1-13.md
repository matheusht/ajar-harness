## Edge 1 — F3 ghost on-MC → counts in getFinalTps windows → F4 composition

**Claim being settled:** CHAIN-1 said F3's forked units are off-MC (bounded with F4); LR-2/IR-F3
said the ghost is on the MC path (MC indices 1 and 2). Who is right?

**The settle — the count logic has NO author exclusion:**
`storage.js:1178-1218` `getFinalTps`: count = 1 + count_aa_responses, then a BFS over the parent
chain from the MC unit down to `last_ball_mci`, counting every `assocStableUnits[parent]` with
`main_chain_index > last_ball_mci` and `!bAA` (`storage.js:1195-1202` — `if (parentProps.main_chain_index <= last_ball_mci) continue; if (parentProps.bAA) continue; count++;`). The
cross-check loop then sums `assocStableUnitsByMci[i]` for every `i` in `(last_ball_mci, mci]`
(`storage.js:1210-1218` — `for (let i = mci; i > last_ball_mci; i--) for (let u of assocStableUnitsByMci[i]) { if (u.bAA) continue; countAll += 1 + ...; }`). **No author-based, sequence-based, or
origin-based exclusion anywhere.**

**Both sides were partially right — the ghost's MC status is case-dependent:**
- **Same-branch/descendant case** (attacker parents the ghost on the victim's spend): BOTH units
  are on the MC path. Verified empirically by IR-F3's direct DB read:
  `U2 (victim) mci=1 is_on_main_chain=1; A_own (ghost) mci=2 is_on_main_chain=1` — both `'good'`.
  In this case the ghost **IS counted** in any getFinalTps window whose `(last_ball_mci, mci]`
  range includes mci 2.
- **Fork case** (simultaneous publish, same parents): the MC loser is off-MC (`is_on_main_chain=0`,
  `main_chain_index=null` or old) — `storage.js:1210` never sees it (no mci in the window) → **not
  counted**. LR-2 documented this ("the loser is off-MC but keeps its validation-time sequence").

**The composition (F3 → F4):** an attacker doing F3 (publishing ghosts to contest a merchant
payment) can make those ghosts serve as F4's flood units in the same-branch case — the ghost IS an
on-MC unit in the window, so it raises the settlement rate like any other unit. **But this is
capability-neutral:** F4's flood economics (each unit must declare+fund a fee; the funding bound
validation.js:2649-2653 caps count at ~32) apply identically whether the flood unit is a ghost or
an ordinary unit. The attacker already held the "author many on-MC units" primitive; reusing
ghosts for it adds no new reach, no cheaper economics, no higher count ceiling.

**Verdict: edge EXISTS (correcting CHAIN-1's blanket "off-MC"), composition `bounded`.**
The permanent-unresolved property of ghosts does not extend the count beyond the ghost's own
stabilization window (getFinalTps only counts `main_chain_index ∈ (last_ball_mci, mci]`), so there
is no persistent rate tax from unresolved ghosts.

## Edge 2 — F1 vacuous proof → satisfies any AA gate using `is_valid_merkle_proof` → AA funds

**Verified precondition:** `is_valid_merkle_proof` is a first-class, test-documented formula opcode
(`test/formula.test.js:3123-3145` exercises it as `trigger.data.element/proof`), so any AA formula
may call it. The F1 finding proved the vacuous proof `"0-" + base64(sha256(X))` evaluates `true`
for ANY X (real engine, 4/4; `round2/IR-F1.md`). Therefore the edge "attacker constructs X and a
self-consistent proof → the AA's membership gate passes" **holds** — no additional code is needed.

**The cap (why this is F1's documented ceiling, not an amplifier):** the IMPACT requires an AA
that actually gates funds on the construct. No production AA in the pinned tree uses it (only the
engine's own tests); auditing individual AAs is out of scope (scope.md: AA repos deferred). So the
chain's impact is usage-dependent — exactly F1's filing (Medium, usage-capped). The edge does not
raise F1's severity; it documents the impact class (E1-3's demonstration, in flight).

**Verdict: edge EXISTS, composition `bounded` (usage-capped; no in-scope AA to escalate to).**

## Edge 3 — F4 poisoning → frozen author → F3 merchant exposure

**Verified edge half:** a poisoned author cannot author ANY unit: the min-fee gate
(`validation.js:1087-1088`: `if (tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share) return callback(...)`) blocks every new unit from an address whose balance is negative. Empirically
confirmed (R2/IR-F4: poisoned balances rejected for a normal declared=17 unit).

**The composition:** the merchant's spend settling in a poisoned window freezes the merchant —
they can no longer send units (including responding to a contested payment). **Why this is not an
amplifier:** the F3 exposure (if any) materializes at the RACE — publish order, best-parent,
witnessed level — before or independent of settlement. A frozen merchant cannot *recover* or *re-
send*, but F3's contested spend already raced; the freeze adds no new attack on the merchant's
accepted payment beyond F4's own freeze impact. Both effects harm the same victim through the same
mechanism class (authoring blocked); there is no cross-capability gain.

**Verdict: no material edge (same-victim, same-mechanism); composition `bounded`.**

hub-mediated (any hub-peer), but the impact class is unchanged (wallet availability).

**Verdict: no in-scope chain; quarantined status unchanged (operator scope decision).**
