## Quasi-new observations (recorded, not findings)

### O1 — R1-B formalized: light-wallet AA definition inserted at mci=0 bound to GENESIS_UNIT (aa_addresses.js:89-94)
Mechanism: the light path fetches unknown address definitions from the vendor; for AA definitions it
calls `storage.insertAADefinitions(db, [{address, definition}], constants.GENESIS_UNIT, 0, 0, false,
insert_cb)` — inserted with **unit=GENESIS_UNIT, mci=0**, WITHOUT `validateAADefinition`. Impact:
the wallet's `aa_addresses` recognizes the address as an AA (and `checkAAOutputs` enforces its
bounce fees) before the consensus path stabilizes it; if the vendor is honest the definition is
correct (chash-verified), so the wallet's view matches consensus for honest definitions. A
malicious vendor could serve a chash-valid but semantically different definition — but the chash IS
the address, and an AA's definition cannot change, so the consensus path will eventually write the
same chash. **Bounded by the light trust model** (LR-1 H-L2 already recorded this as a hardening
note); no consensus or fund impact demonstrated. Marginal-contribution: a wallet-side fee-estimation
/ recognition timing artifact, no value movement.

### O2 — light-wallet unknown-address cache unbounded growth (aa_addresses.js:74-83)
`cacheOfNewAddresses[address] = Date.now()` for every address the vendor doesn't know; entries are
deleted only when RE-ENCOUNTERED after 60s. A wallet checking many distinct unknown addresses grows
the cache until each is re-checked. Tiny entries, wallet-initiated composition → memory-noise only.
Not a finding.

### O3 — confirmation: the only genuinely-new crash class remains Q-1

blind round (LR-4), quarantined in QUARANTINE.md as an adjacent surface. My re-scan found no
second crash class in the uncovered files (writer.js guards are internal-state-only; graph.js
comparator throws only on missing DB rows, unreachable in the consistent ledger).
