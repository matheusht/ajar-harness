# E1-15 — The reorg corner (closing the last crash-family question)

**Hunter:** E1-15 (fork) · **Pinned:** `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`
**Question:** can a reorg (`goDownAndUpdateMainChainIndex`) ever assign `main_chain_index <=
last_ball_mci` to a previously-unballed temp-bad unit, making the validation.js:1686
("unreachable code, conflicting ...") and :2451 ("spending a stable temp-bad output") throws
reachable? This was r1's one residual risk after the round-1 crash-family refutation.

## Verdict: CORNER CLOSED — the throws remain unreachable. Three independent guards.

### Guard 1 — the reorg cannot retreat the stable region (main_chain.js:141-146)
`checkNotRebuildingStableMainChainAndGoDown` runs BEFORE every retreat:

```js
// main_chain.js:141-146
conn.query("SELECT unit FROM units WHERE is_on_main_chain=1 AND main_chain_index>? AND is_stable=1",
  [last_main_chain_index], function(rows){
    if (rows.length > 0)
      throw Error("removing stable units " + ... + " from MC after adding " + ...);
    goDownAndUpdateMainChainIndex(last_main_chain_index, last_main_chain_unit);
});
```

If the retreat point would unseat any STABLE unit, the node throws (an internal invariant error —
the MC never retreats below the stability point). Therefore the join point
`last_main_chain_index` is always ≥ the highest stable MCI.

### Guard 2 — the re-advance only assigns indices above the join point (main_chain.js:219)
`goDownAndUpdateMainChainIndex` NULLs indices above the join point (`main_chain_index=NULL`,
:154-158), then re-indexes the new MC path starting at `main_chain_index = last_main_chain_index`,
incrementing per step (:200-222). Every index assigned by the re-advance is strictly
`> last_main_chain_index >= stability point >= last_ball_mci`. The only other index-assignment
sites (:117, :461) set `main_chain_index=NULL` for later indexing in the same pass; no code path
assigns an index at or below the stability point.

`last_ball_mci` (validation state) is a balled MCI (the unit's `last_ball_unit` must carry a ball —
validation.js:722-730), and balls are created only for stabilized MCIs (`markMcIndexStable` →
`addBalls`), so `last_ball_mci <= last stable MCI <= join point <` every re-advance index.

### Guard 3 — temp-bad resolution is atomic with ball creation (unchanged from round 1)
`markMcIndexStable` (main_chain.js:1268-1300) stabilizes the units at an MCI, then
`handleNonserialUnits` (:1295-1340) resolves EVERY `sequence!='good'` unit at that MCI to
`'good'` or `'final-bad'` BEFORE `addBalls` creates the balls for it (:1333 `propagateFinalBad(…,
addBalls)`). A temp-bad unit therefore never holds a balled MCI; the reorg does not create balls,
stabilize units, or change this.

### The consequence for both throw sites
- **validation.js:1686** (`checkForDoublespends` "unreachable code"): the throw requires a
  conflicting record with `main_chain_index <= last_ball_mci` (not "too young") AND `sequence`
  neither `'good'` nor `'final-bad'` (i.e. `'temp-bad'`). A temp-bad record's index is either
  NULL (off-path after a reorg → the `=== null` branch fires a CLEAN error at :1664) or
  `> last_ball_mci` (unballed new-path index → the `>` branch fires a CLEAN error at :1664).
  The `<= last_ball_mci` + temp-bad combination requires a balled temp-bad MCI — impossible by
  guard 3.
- **validation.js:2451** ("spending a stable temp-bad output"): the throw requires
  `bStableInParents` = (`src_output.main_chain_index !== null && <= objValidationState.last_ball_mci`)
  AND `sequence === 'temp-bad'`. Same impossibility: `<= last_ball_mci` means balled (guard 3);
  a reorg-NULLed index means `bStableInParents` is false (clean transient path); a re-advance
  index is `> last_ball_mci` (also `bStableInParents` false).

### Edge cases checked
1. **Re-advance re-indexes a temp-bad unit:** new-path units get indices `> join point >
   last_ball_mci` → "too young" clean rejection. No throw.
2. **Temp-bad unit left off the new path:** `main_chain_index = NULL` → "too young" (null branch)
   clean rejection. No throw.
3. **Old-path temp-bad unit whose index survives below the join point:** impossible — the retreat
   NULLs ALL indices above the join point (:154 `WHERE main_chain_index>?`); below the join point
   everything is stable (guard 1) and resolved (guard 3).
4. **`last_ball_mci` lower than the node's stability point (old-parent attachment):** the throw bar
   is even lower; re-advance indices are still `> join point > node stability > last_ball_mci`.
   No throw.
5. **`arrRetreatingUnits` legacy override + hardcoded unit-hash workarounds** (main_chain.js:102-116,
   f2-T-f2-05): exact-hash special cases for historical units, not attacker-forgeable, and they
   pick a parent — they do not assign indices in the balled region.
6. **`updateLatestIncludedMcIndex` (:250)**: LIMCI bookkeeping only; it does not assign
   `main_chain_index`.

## Residual risks

- The analysis is a source trace against the deterministic index/stability state machine; the lab
  cannot construct a witnessed reorg (no witness infrastructure) — but each link is a direct
  `UPDATE`/`SELECT` with file:line, and the stable-retreat guard (:141-146) is a hard throw, not a
  recoverable path.
- A future code change that (a) removes the stable-retreat guard, (b) assigns indices below the
  join point, or (c) defers temp-bad resolution past ball creation would reopen the crash class.
  All three are separately invariant-protected today.
