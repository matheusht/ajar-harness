# E1-2 — F3 fork-race win analysis (MC race between the victim's spend C and the attacker's ghost A)

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation lane for finding
`obyte-2026-08-003` (spend-proof uniqueness keyed on a party-chosen address). Question from the
brief: what decides the winner of the race between two 'good' units spending the same private
output X, and can the attacker RELIABLY win? Feeds the merchant-exposure ceiling (reliable win →
F3 rises toward Medium/High; fair race → Low stands).

## Verdict (one line)

**The race is real but position-only — it decides MC inclusion, never value, and it is reliably
attacker-winnable via hash grinding + tip anchoring. The value ledger resolves to the victim's
spend regardless. F3's ceiling stays Low; the reliable displacement strengthens the "silent
contest" form but does not demonstrate value theft.**

## 1. What the race actually decides — three distinct contests

The F3 construction produces two 'good' units spending the same private output X: the victim's
spend C and the attacker's ghost A. There are three separate mechanisms that could "decide"
between them, and they must be kept distinct:

### 1a. The conflict-resolution machinery — DOES NOT RUN (decisive)
`handleNonserialUnits` (main_chain.js:1290-1333) processes only units with
`sequence != 'good'` at a stabilized MCI. Units are marked temp-bad at validation
(`checkSerialAddressUse`, validation.js:1322-1333) only when the unit-level double-spend checks
FIRE. F3's dodge means the ghost is accepted 'good' (the spend-proof check is keyed out of reach)
and is never marked temp-bad. Consequently:
- **Same-branch (A descendant of C):** both units are 'good', both on the MC chain, at different
  MCIs. `handleNonserialUnits` never processes either. No resolution — ever (LR-2 verified: both
  units 'good', MC indices 1 and 2, no final-bad).
- **Fork (A sibling of C at the same MCI):** both are 'good'. `handleNonserialUnits` skips both
  (the `sequence!='good'` filter). The comment in `findStableConflictingUnits`
  (main_chain.js:1390-1392: "the smallest unit wins because it got selected earlier and was
  assigned sequence=good") never fires — no unit is ever marked temp-bad, so no resolution occurs.
- **Consequence:** the victim's unit C can NEVER become 'final-bad' through this machinery. Any
  merchant logic keyed on "wait for final-bad to detect the fraud" never triggers — the fraud is
  silent by construction.

### 1b. The MC-position contest (reorg displacement) — REAL, attacker-winnable
`updateMainChain` (main_chain.js:32+) re-walks the MC from the best-ranked free unit on every new
unit (`readLastUnitProps`, main_chain.js:43-88: `ORDER BY witnessed_level DESC,
level-witnessed_level ASC, unit ASC`). When a better-ranked free unit arrives, `goDownAndUpdateMainChainIndex`
(main_chain.js:200+) resets `main_chain_index > join_point` to NULL for the previously-included
units and re-labels from the new walk. Two constraints bound it:
- **Stable units are protected:** `checkNotRebuildingStableMainChainAndGoDown` (main_chain.js:133-146)
  THROWS if any `is_stable=1` unit would be removed. The displacement window is therefore
  inclusion→stabilization only.
- **Sibling exclusion:** the goUp re-walk includes all ANCESTORS of the new best unit; a sibling
  (not an ancestor) is excluded — its main_chain_index is reset and it falls off the MC.

**Ranking controls the winner.** For two siblings C and A anchored in the same tip region:
- `witnessed_level` — the level of the ancestor where 6 OP authors accumulate
  (`determineWitnessedLevelAndBestParent`, storage.js:691-725). Equal for both (same OP ancestry)
  UNLESS the attacker anchors A on a NEWER OP waypoint → A's witnessed_level ≥ C's. Free to the
  attacker (they control A's parents).
- `level - witnessed_level` — near-equal for tip-anchored siblings; not reliably controllable.
- `unit ASC` — the unit hash. **The attacker can grind A's unit hash below C's** by varying the
  unit content (e.g., a text message payload). C's hash is public once C is posted. Expected
  attempts: ~2 valid unit compositions for a 50% tie-break win (two random 256-bit hashes: P(A<C)
  = 0.5); a handful for near-certainty. Each candidate is a valid unit (a payment unit with a
  random text message validates fine). Trivial cost — no GPU needed.

**Result: the attacker can RELIABLY win the MC-position contest in the unstable window** (tip
anchor for the witnessed-level edge + hash grind for the tie-break). C's `main_chain_index` is
reset to NULL; C stays 'good' (sequence untouched by the reorg) but never stabilizes.

### 1c. The value-resolution — ALWAYS the victim (decisive)
The private output X's value is moved only by the payload that materializes. The ghost's payload
is rejected by the payload-side owner binding: the recomputed spend proof uses
`src_output.address` (the victim's), which never matches the ghost's stored row `(P, attacker)` →
`"incorrect spend proof"` (divisible_asset.js:159). So:
- X's `is_spent` is set by C's spend (the only payload that validates).
- The ghost's outputs never materialize; no value moves to the attacker.
- Even when C is displaced off-MC (1b), its spend of X stands (C is 'good', never 'final-bad').

## 2. Can the attacker reliably win? — the honest answer

| contest | attacker control | reliable? | decides |
|---|---|---|---|
| conflict resolution (1a) | none needed — it never runs | n/a | nothing (both stay 'good') |
| MC position (1b) | tip anchoring (witnessed level) + unit-hash grind (~2 attempts) | **YES — reliable and cheap** | MC inclusion / stability of C |
| value (1c) | none (payload owner binding) | n/a — C wins by default | the money |

## 3. Merchant-exposure ceiling (the escalation question)

The merchant accepting C on INCLUSION (unstable):
- **Same-branch construction (A descendant of C):** no displacement possible (A is C's ancestor's
  child — the MC walk includes C as A's ancestor). Both units 'good', C keeps its position. Exposure:
  ledger pollution only. The merchant is NOT defrauded.
- **Fork construction (A sibling):** the attacker reliably displaces C's MC position in the
  unstable window (1b) — the merchant's inclusion-keyed acceptance sees the payment's
  `main_chain_index` silently reset to NULL, with NO rejection signal ever emitted. The merchant's
  node shows C as 'good' (it is!) while the payment evaporates from the MC.
- **Once C is STABLE, the merchant is safe from displacement** (stable units are protected by the
  throw at main_chain.js:133-146). The exposure window is the standard DAG unstable-inclusion
  window — the same window any DAG merchant must wait out — with the F3 twist that the displacement
  is attacker-controlled, invisible, and never leaves a 'final-bad' trail.

**Marginal-contribution critique applied:** in the public model, a second spend of the same output
is REJECTED at unit level with a visible signal (the merchant's node refuses it; network.js:1146
"the transaction would be non-serial"). In the private model with F3, the second spend is accepted
'good' and can silently displace the first from the MC during the unstable window. The DELTA F3
adds over the public model: (a) no rejection signal exists, and (b) the displacement is
attacker-controlled (deterministic via grinding) rather than a fair race. The world WITHOUT F3:
the second spend is rejected at unit level (the designed behavior of the spend-proof check) — the
merchant is never exposed in the unstable window for a same-proof re-spend.

That is a real marginal contribution — but the money is conserved (1c), the exposure is bounded to
the unstable window, and demonstrating actual merchant loss requires an inclusion-based acceptance
flow that ignores the stability wait. **The ceiling therefore stays Low** (consistent with the
round-2 kill-pair and LR-2 adjudication), with the Medium ceiling remaining triple-contingent.

## 4. What this adds to the F3 finding

1. **The displacement is deterministic, not probabilistic** — the hash grind (~2 valid unit
  compositions) + tip anchoring make the MC-position win reliable. The "silent contest of a
  settled-looking payment" (KP-F3-establish §3) is therefore a *controlled* contest, which
  strengthens the ledger-integrity and merchant-exposure claims.
2. **The conflict machinery never fires on 'good' units** — this is the root of the "permanent
  unresolved duplicate" property: the resolution premise (doublespenders are temp-bad) is broken by
  the F3 dodge in BOTH the same-branch and fork variants. The victim's unit can never be marked
  final-bad, so fraud-detection flows keyed on final-bad never trigger.
3. **Severity: unchanged (Low).** No value theft; value resolves to C; stable-C is protected. The
  reliable displacement is an escalation NOTE, not a severity lift — it strengthens the mechanism
  description, not the impact class.

## 6. Residual risks / open items

- **Timing sensitivity:** the displacement requires the attacker to post A after C's inclusion and
  before C's stabilization. C's stabilization latency on the live network is not measured here
  (no multi-node lab); the window is at least one OP waypoint cycle. The grind itself takes
  seconds.
- **The reorg corner (E1-15's lane)** is adjacent: if a reorg could place a temp-bad unit at a
  balled MCI, the crash-family throws would become reachable — separate lane, not affected by this
  analysis.
- **No live multi-node demonstration** of the displacement (the lab cannot construct the witness
  state); the mechanics are source-verified with the same evidence grade as KP-F2-link.
