# E1-4 — F1 sibling sweep: all prover-supplied verification primitives (formula + definition languages)

**Hunter:** E1-4 · **Pinned:** ocore `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44` · **Date:** 2026-08-11
**Brief:** sweep every verification primitive whose inputs are prover-supplied; for each, is the
root/commitment bound to an ANCHORED value or prover-chosen? Verify each is sound or find another
unsound one (escalation move 7 — one-off → class).

## Verdict

**F1 (is_valid_merkle_proof) is a genuine ONE-OFF — the only verification primitive whose
truth-anchor is structurally inside the prover's input.** The "prover-supplied-commitment" class
does NOT extend to any other opcode or definition predicate. Every other primitive either (a)
anchors to on-chain state (feeds, definitions, the aa_addresses table), (b) takes the anchor as an
explicit separate argument the AA author controls, or (c) is a pure computation. **Escalation
verdict: capped** — the finding does not become a family; the sweep sharpens its framing (internal
inconsistency with the two sound anchored constructs) and surfaces two author-manageable caveats
for the hardening notes.

## The escalation analysis

1. **The class does not extend (cap proven).** Every verification primitive except
   `is_valid_merkle_proof` either anchors to on-chain state (#4, #6, #12, #13, #14, #15, #18), takes
   an explicit author-controlled anchor (#2, #3, #11), or is pure (#5, #7, #8, #16). There is no
   second opcode whose commitment is hidden inside the prover's input. **F1 remains a one-off
   opcode flaw; the finding's severity ceiling is unchanged (Medium, usage-capped).**

2. **The framing sharpens (amplifier for the report, not the severity).** The definition language
   has TWO sound anchored constructs (`in merkle` #13, `in data feed` #12) and the formula language
   has ONE unsound one. The fix pattern the codebase already uses elsewhere (bind the root to a
   posted feed) is proven in-tree — so F1's "missing anchoring step" reads as an implementation
   omission in the formula opcode, not a deliberate design. The e01ba3e sibling-cap never mitigated
   the vacuous case (0 siblings suffice; the cap only bounds sibling counts).

3. **Two hardening-note candidates (HN-12, author-manageable, NOT opcode flaws):**
   - `is_valid_sig`/`vrf_verify` with prover-supplied keys: an AA that keys on trigger-supplied
     pubkeys gets no authenticity (measured: any self-chosen key+sig pair verifies). The AA author
     must pin the key (e.g., from its own definition or a signed feed). The opcode makes no identity
     claim — sound as stated.
   - `is_valid_signed_package` replay: `last_ball_unit` is optional (evaluation.js:1666); a package
     without it is valid indefinitely. An AA using the opcode for authorization must require
     freshness/nonce itself.
