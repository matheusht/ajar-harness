## Tests (all real-path)

### TEST-A1 — text-only unit, declared tps_fee = 1e14, NO base payment message
- Result: `ifUnitError "no base payment message"` (validation.js:1521). **BLOCKED.**
- Meaning: a unit with no inline base payment is rejected before anything else; the "text-only
  bypass" hypothesis dies here.

### TEST-A2 — base payment, input 2e8, output 5e7, declared tps_fee = 1e14 (unfunded)
- Result: `ifUnitError "inputs and outputs do not balance: 200000000 !== 50000000 + 468 + 258 + 0 +
  100000000000000 + 0 + 0"` (validation.js:2654-2656). **BLOCKED.**
- Meaning: the declared fee MUST be funded from the unit's inputs (the closure). The unfunded-
  declaration vector is closed by construction.

### TEST-A3 — funded payment (declared 1e6, input 2e8): settlement = refund only
- Validation: `ifOk`. Settlement (real `updateTpsFees([mci])`, normal window, final fee 0):
  balance after = **1,000,000 = declared − final** — the credit equals the refund; the declared
  1e6 was burned from the inputs at save (closure), so net cost = final. **CONSERVATION CONFIRMED.**

### TEST-C — double-call of updateTpsFees([mci])
- Result: balance 1,000,000 → 2,000,000 — **the delta applies again on a direct second call**
  (`REPLACE INTO` upserts; the SELECT reads the already-updated balance). The single-application
  invariant rests entirely on caller discipline (matches ER-4's static finding).

### TEST-D — stale watermark → updateMissingTpsFees reprocess (the ER-4 MySQL scenario, sqlite-equivalent)
- Setup: funded unit saved as a STABLE DB unit at mci 1 (last_stable_mci=1); a newer-rowid
  tps_fees_balances row at mci=0 makes `getLastTpsFeesMci` return the STALE watermark 0 (in MySQL
  the same stale state arises from a same-second `creation_date` tie-break in
  `ORDER BY creation_date DESC`).
- Result: `updateMissingTpsFees` reprocesses mci 1 → balance 2,000,000 → **3,000,000** — the delta
  applied again. **DOUBLE-APPLICATION CONFIRMED through the real reprocess path.**
- sqlite is immune in the normal case (rowid is insertion-monotonic); the stale state is the
  MySQL-only trigger. Impact: double-credit (refund inflation) or double-debit (fee overcharge)
  for the reprocessed window across a restart. Not directly attacker-triggerable (needs a node
  restart + same-second multi-mci settlement + the MySQL backend) → **hardening note (HN-15)**.

## The estimation-asymmetry refund (brief item 3)

The estimation applies `tps_fee_multiplier` (10) while settlement does not
(storage.js:1334-1339 vs :1228-1234). TEST-A3 demonstrates the refund mechanics: an author who
declares high (at a high estimate) and settles low receives exactly `(declared − final)` back —
**a refund, not a profit** — because the declared was burned from the inputs at save. Net cost is
always `final`. No sequence found where the balance increases without a matching input burn (the
funding gate + closure prevent it).

## Brief item 4 — any balance increase without a matching input burn

None found. Every valid unit burns its declared fee from inputs (closure); every balance credit is
a refund bounded by `(declared − final) ≤ declared`; the recipients are author-constrained
(storage.js:1458-1465). The only balance growth without a CURRENT unit's burn would be the
double-application (TEST-C/D), which requires the stale-watermark condition.
