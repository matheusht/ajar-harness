# E2-12 — Light-vendor handshake: does anything the vendor serves cross the trust boundary?

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation hunter report (round E2).
Scope: `light.js` (prepareHistory vendor-side + processHistory client-side), the `light/get_*`
command surface in network.js, `light_wallet.js`, `aa_addresses.js` (light definition fetch).
All line refs against the pinned commit.

## Verdict (one line)

**`capped` — the light-vendor surface is trust-model-bound: no fund-impact candidate crosses the
documented hub-trust boundary.** The light client's cryptographic checks (witness-signed
proofchains, ball-hash recomputation, unit-hash validation, witness proof against the client's OWN
witness list) constrain a malicious vendor to serve REAL cryptographic material; everything a
malicious vendor could do through the gaps (stale-branch confirmation, forged AA responses, voided
payments, fabricated pending units, position-lock) is achievable with equal-or-greater effect
through the vendor's inherently-trusted channels (get_balances, history omission). Marginal
contribution of each gap ≈ 0. Three hardening notes confirmed (LR-1 H-L1/H-L2/H-L3, sharpened with
the exact commented-out code), two observations verified (E1-14 O1/O2).

## The crossing candidates examined (each with the marginal-contribution critique)

### C1 — stale-branch confirmation (LR-1 H-L3, confirmed + sharpened)
- **Mechanism:** `processLinkProofs` (light.js:789-866) verifies reference-closure (each chain
  element's parents/balls must be known from prior elements), unit hashes, and ball-hash
  recomputation — but NOT that the chain reflects the real MC's ancestry. A vendor can assemble a
  reference-closed chain of REAL units + REAL witness-signed balls from a stale branch and present
  it as the confirmation for a payment; the client accepts it and emits stability (the unit reaches
  `is_stable=1`, `is_unique=1`, `emitStability`).
- **Marginal contribution:** a fully malicious vendor can already (a) omit the payment from history
  entirely, (b) serve a forged `get_balances` number, or (c) serve the same stale-branch story via
  `get_history` — all invisible to the client. The gap adds no capability the trusted vendor lacks.
  A NON-vendor attacker cannot inject into the vendor's response (single configured wss hub;
  impersonation = DNS/TLS compromise = the attacker becomes the vendor = same trust model).
- **Bound:** the chain must be built from REAL witness-signed balls (the anchor holds) — the vendor
  cannot fabricate a confirmation for a unit that never appeared on any witnessed chain.
- **Verdict: capped (trust-model-bound).**

### C2 — AA-response trust
- **Mechanism:** "AA responses are trusted without proof" (light.js:295) — structure-only
  validation (light.js:295-323); the response's authenticity (real AA's response) is not verified.
  A vendor can serve a forged AA balance/response → the user's AA-conditional decisions (e.g.,
  withdraw threshold) act on wrong state.
- **Marginal contribution:** the vendor can equally serve a forged `get_aa_balances`/`get_aa_state_vars`
  number or a wrong `get_history` — the AA response is one of many equally-trusted channels. No
  crossing.
- **Verdict: capped.**

### C3 — the void path (vendor marks a real payment final-bad)
- **Mechanism:** processHistory voids units the vendor serves with a proofchain entry marking
  `is_nonserial=true` (light.js:312-322, `archiving.generateQueriesToArchiveJoint 'voided'`) —
  the client deletes the outputs client-side.
- **Bound:** the proofchain entry must be a REAL witness-signed ball with `is_nonserial=true` —
  which requires the real network to have marked the unit final-bad. The vendor cannot void a unit
  that is really serial (no real is_nonserial ball exists). The anchor holds.
- **Marginal contribution:** for units that ARE final-bad, voiding is correct behavior; for a
  malicious vendor wanting to hide a payment, history omission achieves the same. No crossing.
- **Verdict: capped.**

### C4 — fabricated pending units
- **Mechanism:** unproven units are saved as unstable 'good' (the disabled proofchain rejection) —
  a vendor can serve the user a cryptographically-valid unit (attacker-signed, valid hash) that is
  NOT on the real DAG; the client displays it as pending.
- **Marginal contribution:** same effect via a forged `get_balances` pending number; and a
  sound merchant waits for confirmation (which the anchor protects). No crossing.
- **Verdict: capped.**

### C5 — position-lock (vendor serves old parents → never-stabilizing payment)
- **Mechanism:** `light/get_parents_and_last_ball_and_witness_list_unit` (network.js:3541) serves
  the position; the light client composes against it unverified (f15-T2). A malicious vendor can
  serve OLD parents → the user's payment attaches to an old DAG part → never stabilizes (KP-F2-link
  proved old-attached units cannot stabilize) → the user's inputs are locked in a pending unit until
  archiving voids it.
- **Marginal contribution:** the vendor can equally refuse to broadcast the user's unit (censorship
  is inherent to the hub model) — the freeze is a delayed-availability variant of inherent
  censorship, and it self-heals at archive. No theft (the vendor cannot sign for the user).
- **Verdict: capped (trust-model-bound; delayed availability only).**

## Confirmed hardening notes (sharpened from LR-1, with the exact lines)

- **H-L1 (confirmed):** unconfirmed-state unit authenticity is NOT verified — the proofchain
  REJECTION is commented out (light.js:256-258, :292-293); unproven units are saved as unstable
  'good'. The anchor (confirmed-state requires proofchain membership) holds, but the disabled
  checks are dead defense-in-depth. **Fix:** restore the rejections (unstable-only saving of
  unproven units).
- **H-L2 (confirmed):** light AA definitions fetched from the vendor are chash-verified but NOT
  `validateAADefinition`'d, inserted at mci=0 (aa_addresses.js:92-95); malformed definitions cause
  wallet-side bounce-fee miscalculation / possible getter throw (wallet-side, vendor-trust).
- **H-L3 (confirmed + sharpened):** `processLinkProofs` (light.js:789-866) verifies
  reference-closure + hashes but not real-MC ancestry — a vendor can serve a stale-branch
  confirmation. **Fix:** the client cannot distinguish stale from current without more data; a
  stronger design anchors the proofchain start to a witness-verified current last-ball.

## Observations verified (E1-14 O-notes)

- **O1 (verified):** wallet-side fee-estimation runs against the vendor-served position — timing

- **O2 (verified):** `cacheOfNewAddresses[address] = Date.now()` (aa_addresses.js:74-83) grows for

## Why "no crossing" is the honest result

The light client's checks exist to make the vendor's data CRYPTOGRAPHICALLY HARD to fake (witness
signatures, ball hashes, unit hashes). They succeed: every candidate gap still requires REAL
witness-signed material, and the client's confirmed-state anchor holds. Everything beyond that
(which units to serve, which balances to report, which parents to hand out) is inherently
trusted-vendor state with no independent client verifier — by design (a light client has no graph).
Forcing a "crossing" claim here would violate the marginal-contribution critique.
