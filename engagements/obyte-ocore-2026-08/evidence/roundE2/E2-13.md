## Verdict (one line)

**Capped / no finding.** The archiving edge is sound for double-claim and theft: every unspend is
guarded by a competing-spender `NOT EXISTS`, the void deletes outputs (spends referencing them are
cleanly rejected), re-arrival of purged units is equivalent to fresh authoring, and the private
input-type surface is constrained. Residuals are hardening notes (HN-2 family crash-window; light
trust model), none attacker-exploitable for value.

## The double-claim question — each scenario, with the decisive control

### S1 — legitimate reorg-void (unspend after void) — CORRECT
Unit A spends X; A goes final-bad and is voided (storage.js:~1700): `generateQueriesToUnspend...`
unspends X (`UPDATE outputs SET is_spent=0`, archiving.js:150) **only if no other transfer input
spends X** (the `NOT EXISTS` at :114-120). X becomes reusable by design — the void cancels A's
spend. **Decisive control:** archiving.js:111-121.

### S2 — void with a live competitor — CORRECT (no double-claim)
A (final-bad) and B (good) both spend X. A's void: the NOT EXISTS sees B's transfer input row →
X NOT unspent → X stays spent by B. **Decisive control:** archiving.js:114-120 (alt_inputs
existence check).

### S3 — both voided in one batch (double-spend where both lose to a third unit C) — CORRECT
The unspend SELECTs run at query-collection time (before any DELETE executes), so A's SELECT sees
B's row and vice versa → neither unspends. And the both-lose case implies a third winner C spends
X → C's row blocks both unspends → X stays spent by C. **Decisive control:** collection-then-
execution ordering in joint_storage.js:265/archiving.js + the winner-implies-spender invariant.
No lock: both A and B losing to no one is unreachable (final-bad is assigned by the conflict
resolution which always has a winner).

### S4 — private-payment competitor — CORRECT
Private payments create `type='transfer'` input rows (divisible_asset.js:39
`type = input.type || "transfer"`; indivisible_asset.js:256/263). The competing-spender check
(`alt_inputs.type='transfer'`) covers them. **Type-injection residual closed:** the private-chain
validation constrains input types to `issue` (divisible_asset.js:96-111) or absent=transfer
(`else` branch :113-139); any other type → `"unknown input type"` (divisible_asset.js:141-143);
the payment-message path validates issue/transfer fields strictly (validation.js:2300-2360).
So the `type` written to the inputs table is always `issue` or `transfer` — the unspend's
`type='transfer'` filter cannot be diverged from the doublespend's `type=?` filter.

### S5 — spend of a voided unit's output — CORRECT (clean rejection)
The void deletes the unit's outputs (archiving.js:63). A later spend referencing a deleted output
fails: `"output being spent ... not found"` (validation.js:2458-2460); a spend referencing a
stable final-bad output is rejected `"spending a stable final-bad output"` (validation.js:2451-2452).
**Decisive control:** validation.js:2451-2460.

### S6 — re-arrival of a purged 'uncovered' unit — NO ESCALATION
The 'uncovered' purge removes only units that are `sequence IN ('final-bad','temp-bad')` AND
`content_hash IS NULL` AND no ball AND no dependencies (joint_storage.js:229-236) — i.e.,
NEVER-resolved nonserial units. Their spends were never settled. Re-arrival (the code comment:
"the purged units can arrive again, no problem") re-validates the unit; its spends either conflict
with a surviving competitor (temp-bad again) or are the only spend (legitimate). Since the purged
unit's author authored it (only its own key can sign its spends), re-posting is equivalent to
authoring a fresh spend — no new capability, no double-claim. **Decisive control:**
joint_storage.js:229-236 (purge predicate) + the ownership invariant (spends require the author's
key).

### S7 — the void's stripped-joint re-delivery — CONSISTENT
The void replaces the kvstore joint with a STRIPPED copy (storage.js:1725-1732, content_hash only,
no messages). Re-delivery of the full unit reads the stripped copy (readJointJsonFromStorage →
kvstore first, storage.js:87-92) → re-validated as a nonserial unit → rejected as "unit is final
nonserial" (initPrivatePaymentValidationState/validation flow). Idempotent; no resurrection of the
full content.

## Residuals (hardening notes, not findings)

- **R1 — kvstore-del-after-SQL crash-window (HN-2 family):** the archive deletes the sql rows
  first, the kvstore `j\n` copy second (joint_storage.js:278-281; storage.js:1840). A node crash
  between COMMIT and the kvstore del leaves a kvstore joint with no sql row → a later re-delivery
  of that unit hits storage.js:92 `throw Error("unit found in kv but not in sql")` → uncaught →
  crash-loop on every re-delivery after restart. **Not attacker-triggerable directly** (requires a
  coincident mid-archive crash), but the crash-loop-persistence shape matches HN-2's
  warning (any future reachable throw becomes network-wide). Fix: kvstore del before/with the SQL,
  or a tolerant read.
- **R2 — light-client unspend divergence:** the light-client voided archive (light.js:348) runs
  the same unspend queries against the light client's INCOMPLETE inputs table — a competitor row
  the full node sees may be absent locally → the light view of `is_spent` can diverge. Trust-model
  (light trusts the vendor); not consensus-relevant. Note only.
- **R3 — purge re-arrival window:** a purged temp-bad unit's source outputs are unspent; an output
  the honest owner wanted to spend was blocked during the unit's temp-bad lifetime (>10s purge
  delay) — a liveness delay only, by design.
