# E2-14 — Governance vote economics (op_list + fee parameters)

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation-hunter report.
Scope: economic/governance attacks are **out of scope** per the program — this report exists for
the economics (feeds F4's parameter dependence) and for any code-level flaw in the vote machinery
that is NOT pure governance.

## Verdict: **capped** — no escalation lane survives; 2 hardening notes; F4's parameter-dependence confirmed but bounded.

## The vote machinery (source-verified)

- **Votes** (`system_vote` messages): per-address, balance-weighted. Written to
  `system_votes` / `numerical_votes` / `op_votes` **only at stabilization** —
  `saveSystemVote` (main_chain.js:1585-1620) requires `storage.assocStableUnits[unit]`
  (`if (!objStableUnit) throw Error("no stable unit")`); a vote's unit must be on the MC and
  stable or the vote never counts. Unstable votes enter only the emergency path
  (`getUnstableVotes`, main_chain.js:1896-1903, subject op_list only, `>=1h` old,
  `EMERGENCY_COUNT_MIN_VOTE_AGE=3600`).
- **Counting** (`countVotes`, main_chain.js:1705-1894): voter weight = `SUM(outputs.amount)` of
  stable-good, unspent base outputs (NOT EXISTS stable-good spender — main_chain.js:1722-1738).
  Quorum: the vote window expands backward year-by-year until voters in the window hold
  `>= SYSTEM_VOTE_MIN_SHARE (0.1) * TOTAL_WHITEBYTES (1e15)` — i.e., **>= 100,000 GBYTE must have
  voted** (main_chain.js:1770-1785).
  - `op_list`: top-12 by weighted balance (`op_votes` CROSS JOIN voter_balances, LIMIT 12).
  - `threshold_size` / `base_tps_fee` / `tps_interval` / `tps_fee_multiplier`: **weighted median**
    (accumulated balance >= half of total voted balance, ORDER BY value; main_chain.js:1815-1830).
- **Emergency op_list change** (`system_vote_count`, main_chain.js:1904-1919): any address pays
  `SYSTEM_VOTE_COUNT_FEE = 1e9` base (1000 GBYTE) to trigger a count of the previous MCI's votes
  PLUS unstable op_list votes >=1h old; gated by `EMERGENCY_OP_LIST_CHANGE_TIMEOUT = 3 days`
  (too-early → no-op `return cb()`). op_list only — fee parameters are NOT emergency-changeable.

## Escalation lanes

### L1 — vote a fee parameter to a breaking value (tps_interval=0 -> Infinity fees): REFUTED
- Vote-time validation (validation.js:1895-1905): `tps_interval >= 0.1`, `base_tps_fee <= 1e8`,
  `tps_fee_multiplier in [1,1000]`, `threshold_size >= 1000`, `op_list` = 12 valid known
  non-AA witnesses (sorted, no definition references). No countable vote can carry a
  division-by-zero or Infinity-producing value.
- **The S1 disjunct on the bounds** (`last_ball_mci >= pemCurvesFixMci || !hasBall &&
  minRetrievableMci >= fix`) is bypassable by an old-DAG-attached vote carrying an out-of-range
  value — **but dead by stabilization**: `saveSystemVote` requires MC stability, and old-DAG units
  cannot stabilize (KP-F2-link: witnessed level is ancestry-derived; best-parent sorts by it; MC
  walk starts from the tip). The out-of-range vote is accepted at validation and never counted.
  Same class as the whole S1 family — latent hardening item, not exploitable.

### L2 — minority capture of the median (cheap fee-curve control): CAPPED (expensive)
- Median control needs >50% of the voted balance in a window where >= 10% of supply has voted →
  **>5% of the total supply (50,000 GBYTE) voted the attacker's way**. The window expansion is
  turnout-driven (cannot be shrunk by the attacker). Votes are balance-weighted — splitting funds
  across addresses does not multiply weight.
- The vote-count fee is tiny (normal unit fee); the BALANCE is the cost. 50,000 GBYTE is a
  5%-of-supply position — not a cheap attack; and the outcome is a legitimate governance change
  (or a whale's capture — out of scope per the program).

### L3 — emergency op_list subversion: CAPPED
- Cost: 1000 GBYTE per attempt + a >=1h-old op_list vote + a balance competitive with the
  incumbent OPs' 12th-place support. The emergency count is op_list-only, 3-day-gated, and
  deterministic. Displacing an incumbent requires beating their balance-weighted support — the
  same >5%-of-supply class. No cheap path.

### L4 — vote-weight inflation (spend kept unstable at count time): BOUNDED (note only)
- The balance query excludes outputs with a **stable-good** spender; an output spent by an
  **unstable** unit still counts toward the voter's weight at count time (main_chain.js:1730-1737).
  An attacker can spend their output and keep the spend unstable at the count MCI to retain the
  weight. Bounded by the attacker's own outputs (cannot exceed what they hold); timing-dependent;
  no leverage over the >5%-of-supply capture threshold. Note for the record.

### L5 — network freeze by a governance fee raise (the F4 connection): BY-DESIGN (governance)
- Within the validated bounds, governance can set `base_tps_fee = 1e8` (10Mx the current 10) or
  `tps_fee_multiplier = 1000` (1000x) — at tps=2 the estimation fee goes from ~64 base to
  ~6.4e8 base per unit: a network-wide fee wall. This is the community's legitimate governance
  power (or a captured majority's), NOT a code bug. Marginal-contribution: the governance system
  is by-design; the fee curve's parameter range is the community's choice.
- **For F4 (obyte-2026-08-004):** the settlement-poisoning finding is parameter-dependent — a
  higher `base_tps_fee` makes a given flood window's settlement fees larger for the same count.
  F4's own cap (funding bound: count <= ~32) is independent of the fee curve; the severity framing
  "10.7% of supply at count=30" uses the current params and would scale with a governance raise.
  This does not change F4's verdict (the cap is proven); it records the parameter-dependence.

## Hardening notes

- **HN-16 — S1 disjunct inconsistency on the vote-value bounds (latent):** the bounds use the
  `last_ball_mci || !hasBall && minRetrievableMci` form, so an old-DAG-attached vote with an
  out-of-range value passes validation (never counts). Align with the migration pattern
  (unconditional bounds) for defense-in-depth.
- **HN-17 — governance fee ceiling is 10Mx the current base:** `base_tps_fee <= 1e8` with the
  current 10 allows a legitimate (or captured) majority to raise the fee wall by 7 orders of
  magnitude. Consider tighter bounds or a per-vote rate-of-change limit if the community wants a
  softer ceiling. Governance-design consideration, not a defect.
