# E2-15 — EXCHANGE-INTEGRATION SURFACE

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation hunter report.
Focus: the APIs an exchange integration would use (balances, history, receiving, withdrawals) and
integration-level flaws (balance misread, display-vs-settlement races, F4 poisoning hitting hot
wallets).

## Verdict (one line)

**Capped — no new mechanism on the exchange-integration surface.** The three relevant
integration-level consequences are all downstream of already-confirmed findings (F4 fee poisoning,
F3 ghost records, LR-1 light-vendor trust): (1) the F4 freeze of a hot wallet's
`tps_fees_balance` is **invisible to the balance API** — `light/get_balances` shows the
outputs-based balance while withdrawals fail; (2) a temp-bad unit's outputs vanish from the served
balance (sequence='good' filter) and reappear on resolution — a false balance dip; (3) the
declared-fee/settlement delta (F4) makes the true cost of a withdrawal unbounded from the
integration's perspective. None is a new bug; each is the exchange-facing consequence of an
existing one.

## Findings

### F15-1 — The F4 hot-wallet freeze is INVISIBLE to the balance API (integration note, F4 consequence)

- `light/get_balances` (network.js:3724-3726) computes balances from the OUTPUTS table only
  (`SELECT ... FROM outputs JOIN units USING(unit) WHERE is_spent=0 AND address IN(?) AND
  sequence='good'`). The `tps_fees_balance` (the account the min-fee gate checks,
  validation.js:1087) is a **separate ledger** (`tps_fees_balances` table) never surfaced by any
  balance API.
- Consequence: after the F4 flood debits the hot wallet's `tps_fees_balance` by the exponential
  settlement delta (storage.js:1246-1261), the exchange's balance API shows the full output-based
  balance while **every withdrawal fails** with the min-fee error ("tps_fee ... + tps fees balance
  ... less than required"). The failure is invisible until the withdrawal is attempted, and the
  recovery cost (paying the negative balance) is invisible too.
- This is F4's mechanism (already confirmed, obyte-2026-08-004) — the exchange framing adds: the
  freeze is API-invisible, so an exchange monitoring balances cannot detect it. Recommend adding
  `tps_fees_balance` exposure to the integration API and F4's report documenting the exchange
  impact. No new mechanism, no severity change (F4 stays Low; the freeze is the same per-author
  scatter).

### F15-2 — Temp-bad balance dip (integration note)

- The balance query filters `sequence='good'` (network.js:3724). A unit that is temp-bad (pending
  MC conflict resolution, main_chain.js:1322-1333) has its outputs EXCLUDED from the served
  balance; when it resolves 'good', the outputs reappear.
- An exchange monitoring balances sees a deposit or hot-wallet balance DIP during the temp-bad
  window and recover after resolution. The window is bounded (resolution is atomic with
  stabilization) and the value is never lost — a monitoring/alerting false-positive, not a
  misread. Integration note only.

### F15-3 — Withdrawal cost unbounded from the integration's perspective (F4 consequence)

- The declared tps_fee is based on the local estimate (validation.js:1070-1092,
  `getLocalTpsFee`); the settlement debits the difference (declared - final) from the
  author's `tps_fees_balance` (storage.js:1246-1261). In a flood window the final fee is the
  exponential value (F4: 10.7% of supply at count=30), so the true cost of a withdrawal composed
  in the calm just before the flood is unbounded relative to the declared fee.
- Exchange integration: a withdrawal "succeeds" (unit accepted) and the settlement debit lands
  later — the exchange's fee accounting is silently wrong in a flood window. Same F4 mechanism.
  Recommend F4's report note this integration consequence.

### F15-4 — Balance-query precision: SAFE (verified, negative)

- `SUM(CAST(amount AS DOUBLE))` (network.js:3724; storage.js:947 same shape) is precision-exact
  because every amount ≤ MAX_CAP = 9e15 (validation.js:2153/2190) and every asset's total supply ≤
  `payload.cap ≤ MAX_CAP` (validation.js:2721) — the base supply is 1e15 (constants.js:15). All
  sums stay below 2^53 = 9.007e15. No double-precision misread. (Consistent with f1-T5/f6-T2.)

### F15-5 — Ghost footprint in balances: NONE (verified, negative)

- The F3 ghost's claimed outputs do NOT materialize: verified against the F3 lab DBs
  (evidence/lab/r1/.r1data + evidence/lab/kp-f3/.kp-f3-data) — the outputs table holds only the
  genesis outputs, the private output X (is_spent=1), and the victim's change; the ghost leaves
  only `spend_proofs` + `inputs` rows. The ghost's public payment message produces no balance
  effect (the payload-side owner binding rejects its payload; private asset outputs only
  materialize from the payload). No exchange balance is affected by F3's records.

### F15-6 — Deposit confirmation: stable flag is sound (verified, negative)

- The stable/pending split (network.js:3733-3739) is computed from the units' `is_stable`
  (main_chain_index ≤ last_stable_mci). Crediting deposits on 'stable' is the standard
  confirmation rule; the pending amount is the vendor's view for light clients (trust model —
  LR-1 covered the forged-unconfirmed-view risk). A full-node exchange integration uses its own
  node's real ledger — no vendor trust. No new flaw.

## Held observations (decisive control)

- **H1 — get_balances has no auth on addresses:** any inbound light client can query any address's
  balance — by design (the DAG is public); balances are public data. No privacy issue.
- **H2 — light/get_history (3478-3541)** caps history at 2000 units (LR-1/H3 verified param caps);
  an exchange reconciling long histories paginates. No truncation flaw found.
- **H3 — compose-side input picking** (wallet.js → pickDivisibleCoinsForAmount/pickCoins) reads the
  outputs table; a conflict making a picked input final-bad later fails the withdrawal cleanly at
  validation (standard). No balance-vs-settlement race beyond the F4 fee delta.

## Impact assessment (marginal contribution)

- World without the confirmed findings: balances and withdrawals behave as displayed.
- Delta: the F4 fee delta (already confirmed) makes withdrawal costs unbounded and hot-wallet
  freezes API-invisible; the temp-bad dip is a monitoring artifact; F3's records don't affect
  balances at all.
- **Verdict: capped** — the exchange-integration surface contributes no new mechanism, no new
  finding, and no severity change. It documents three integration-level consequences of existing
  findings (F15-1/2/3) for the report-writing phase.
