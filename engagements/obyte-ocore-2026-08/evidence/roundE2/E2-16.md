# E2-16 — Q-1 crash-loop persistence: remote zero-cost wallet crash via hub/deliver to an unknown device key

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation-hunter report. **Quarantine-level**
(device/wallet layer — outside the declared DLT surfaces; the operator decides whether to widen
scope). The maximum-impact PoC is now built, runnable, and empirically verified.

## Claim tuple

- **target/version:** ocore `a7eb776`, device.js `decryptPackage` else-branch (scheduled
  uncaught throw) + network.js `hub/deliver` bToMe path.
- **entrypoint:** an inbound ws peer connecting to a victim's OWN hub (`bServeAsHub`, the
  documented "I'm my own hub" deployment) sends `["request", {command: "hub/deliver", params:
  <crafted device message>}]`.
- **preconditions:** (1) the victim runs `bServeAsHub: true` (their own hub — an opt-in but real
  deployment mode for power users/businesses); (2) the attacker knows the victim's hub URL and
  device address (both semi-public — the device address is the contact identifier; hub URLs are
  advertised); (3) the crafted message is encrypted to a recipient ephemeral key the victim does
  NOT hold (any random key suffices).
- **mechanism:** `hub/deliver` (network.js:3370-3440): the `bToMe` branch (message addressed to
  the hub's own device) **skips the recipient-key validation** (the `keys.includes(...)` check at
  network.js:3424-3426 runs only in the non-bToMe branch) and emits `message_from_hub` →
  device.js `handleJustsaying('hub/message')` (device.js:148-177) → checks pass (the attacker
  signs with their own key — any valid signature passes) → `decryptPackage(encrypted_package)`
  (device.js:404-445) → the `recipient_ephemeral_pubkey` matches none of
  {current temp, prev temp, permanent} → **else branch (device.js:431-432)**:
  `setTimeout(() => { throw Error("message encrypted to unknown key, device ...") }, 100)`.
  The throw fires 100 ms later in the event loop — OUTSIDE the try/catch that wraps
  `decryptPackage` (device.js:170-173) — → `uncaughtException` → process death.
- **observable effect (measured):** the victim sends a clean `error: "failed to decrypt"`
  response, then **crashes 100 ms later** (`UNCAUGHT-EXCEPTION: Error: message encrypted to
  unknown key, device <addr>, len=88. The error might be caused by restoring from an old backup
  or using the same keys on another device.`). Process exit.
- **negative control:** the same delivery with the recipient key equal to the victim's PERMANENT
  pubkey decrypts normally (the permanent branch) — no crash. The attacker cannot hit the else
  branch via a PUBLIC hub in the normal flow (the hub validates the recipient key against the
  registered set: network.js:3424-3426) — the crash is specific to the self-hub bToMe path and to
  stale-key edge cases (backup-restore/multi-device).
- **claimed impact/severity:** remote, zero-cost, repeatable crash of the victim's wallet process
  (the device layer runs in the wallet/hub process) — availability; crash-loop persistence
  (restart → re-deliver → re-crash). Node-side fix (restore the commented-out
  `eventBus.emit('nonfatal_error', ...)`, remove the throw) → out-of-scope class per the
  DoS-coordination rule. The operator decides scope (the 2018 wallet chat XSS→RCE precedent shows
  Obyte treats wallet-layer remote crashes as critical).

## Crash-loop persistence (measured, 3 independent cycles)

|---|---|---|---|---|
| 1 | 037CDE6K3BYY6SNBEQY5SVR6P7JUWBJE2 | `hub/deliver` → accepted | YES (UNCAUGHT-EXCEPTION, len=88) | 0 |
| 4 | 0DIKVMZLR7SI... | accepted | YES | 0 |
| 5 | 0KPQLQZM26DZ... | accepted | YES | 0 |

Each cycle: fresh victim (own hub + device identity) → single hub/deliver → clean error response →
scheduled uncaught throw → process death. The attacker repeats this against any restarted victim —
a permanent crash-loop with zero cost per cycle.

## Impact analysis (marginal contribution)

- World without the bug: the else-branch emits the nonfatal_error event (the commented-out line
  device.js:433) and returns null → the victim responds "failed to decrypt" and continues.
- Delta this bug adds: the wallet/hub process dies on attacker input. Remote (any peer can connect
  to the victim's hub), zero-cost, repeatable (crash-loop). Availability class; the device layer
  handles the fund-holding wallet, so a crashed wallet blocks the victim's funds access until
  restart.
- **Cap (proven):** the population is victims running their own hub (opt-in config,
  `bServeAsHub`); the public-hub normal flow is closed by the recipient-key check. Fix is
  node-side (no network coordination) → out-of-scope class per the program rule.
