# E2-3 — AA issueAsset cap-precision (retry of E1-6): can an AA issue MORE than its cap?

**Pinned:** ocore `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation hunter report.
**Question (f11-R1-A, open since round 0):** can an AA issue more of its own asset than the cap via
JS Number precision at the 2^53 boundary?

## Verdict

**REFUTED for the cap-exceedance question; CAPPED at "composer-side availability / AA-accounting
drift for whale AAs".** The cap cannot be exceeded — structurally and empirically. The 2^53
precision window is closed on the validation path by the total caps. The only residue is
composer-side float rounding for intended sums > 2^53, which produces either a bounce (availability)
or a sub-unit accounting drift in the AA's own state (self-inflicted, no attacker leverage).

## The mechanism under test

`aa_composer.js:1178-1209` `issueAsset`:
```js
var issue_amount = objAsset.cap || (target_amount - total_amount);
```
- **Capped assets:** `issue_amount = objAsset.cap` (the full cap, exactly once — `serial_number 1`,
  "already issued" guard at :1197-1200).
- **Uncapped assets:** `issue_amount = target_amount - total_amount` (issue exactly the gap).

## Why the cap cannot be exceeded (the decisive controls)

1. **The cap is an exact JS Number by construction.** `validateAssetDefinition`
   (validation.js:2728-2729): `if ("cap" in payload && !(isPositiveInteger(payload.cap) &&
   payload.cap <= constants.MAX_CAP)) return callback("invalid cap")`. `MAX_CAP = 9e15`
   (constants.js:57) < `2^53 - 1 = 9,007,199,254,740,991` — every valid cap is exactly
   representable (verified: `MAX_CAP < 2^53: true`).
2. **The issue amount is validated to EXACTLY equal the cap.** `validateIndivisibleIssue`
   (validation.js:2198-2225): for a capped denomination, `input.amount !== denomination *
   denomInfo.count_coins → reject`. `denomination * count_coins = cap <= 9e15` — exact product
   (verified: the max-cap product is exact). An AA emitting any other amount is rejected.
3. **The cap is the sum of the denomination products, checked exactly.**
   (validation.js:2752-2762): `payload.cap !== total_cap_from_denominations → reject` — and the sum
   is bounded by the cap ≤ 9e15 → exact accumulation.
4. **Only ONE issue per capped asset.** Composer guard (:1197-1200) + the ledger-side doublespend
   query keyed on `(type='issue', asset, denomination, serial_number[, address])` (validation.js:
   2358-2368) blocks any second issue network-wide.
5. **The precision window is closed by the total caps.** `total_output > MAX_CAP → reject`
   (validation.js:2190); `total_input > MAX_CAP → reject` (validation.js:2597-2598). Both totals
   are therefore bounded by 9e15 < 2^53 → **every float accumulation in the validation path is
   exact**. The balance closure `total_input !== total_output (+ fees)` (validation.js:2600-2601,
   2653-2656) compares exact values — no rounding-window leak exists.
6. **Capped-issue change math is exact.** `change = total_amount - target_amount` with
   `total_amount = cap` (exact) and `target_amount <= cap` (else the unit bounces on
   `total_output > MAX_CAP`) → both exact.

## The honest residue (the cap)

**Composer-side rounding for whale AAs.** The composer accumulates `net_target_amount`
(payload.outputs.reduce, aa_composer.js:1082) and `total_amount` (existing inputs) as JS floats
BEFORE validation. For an AA whose intended payment or held balance involves sums > 2^53 (many
outputs each near 9e15 — an AA holding > 9e15 base units across multiple outputs), the float sum
rounds (measured: [9e15, 9e15, 1] → 1.8e16, losing the 1). Consequences:
- (a) the composed unit's declared amounts don't truly balance → validation's exact check rejects
  → **the AA's payment bounces** (availability/liveness for whale AA operations — no value theft,
  the unit is never accepted);
- (b) if the rounded declared amounts coincidentally balance, the ledger accepts the declared split
  — a sub-unit drift from the AA's intent — the AA's OWN accounting tracks its own declared
  amounts, so the drift is self-contained (the AA controls its formulas). No cross-party impact, no
  consensus divergence (the rejection/acceptance is deterministic — every node computes the same
  floats).
- The capped-issue case is immune (issue = cap exactly, change = exact).

**Impact class:** availability/AA-accounting at extreme whale scale. No fund loss/freeze above the
program's USD 1,000 floor, no cap violation, no money creation. `real-but-capped` — the cap is
proven by the total-cap controls above.

## Negative control

rejected ("already issued" + the ledger doublespend key); an attempted issue of 9e15+1 is rejected
by `input.amount !== denomination * count_coins`. The boundary is exact at every step.
