# E2-5 — Issue spend proof reuse / duplicate serial issuance across addresses

**Hunter:** E2-5 · **Pinned:** `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`
**Verdict: capped (mechanism confirmed empirically; no value impact demonstrated — the reachable
case is economically inert and the value-bearing cases are contained by layered controls).**

## Claim tuple

- **Mechanism under test:** the issue-type spend proof
  `hash({asset, amount, address, serial_number})` (divisible_asset.js:101-107) has **no
  unit/message_index/output_index binding** (f6-T4). Combined with the address-scoped duplicate
  key, a second issuance of the same serial with a DIFFERENT author address is invisible to both
  the doublespend query and the schema UNIQUE constraint.
- **Empirical (real validation path):** with asset A (uncapped, `issued_by_definer_only=false`)
  and U1 = A1 issuing serial 1, the unit U2 = **A2 issuing serial 1 again**
  `validation.validate` → **`VALIDATION OK sequence=good`** (reproduced in every run of
  `evidence/lab/e2-5/e2-5-issue-reuse.js`). The input-level doublespend query
  (`type='issue' AND denomination=? AND serial_number=? AND address=?`, validation.js:2353-2370)
  keys on the author address — A2's query does not match A1's row.
- **The schema confirms the same gap:** `inputs` has
  `UNIQUE (asset, denomination, serial_number, address, is_unique)` — "UNIQUE guarantees there'll
  be no double issue" (initial-db/byteball-sqlite.sql) — but **`address` is inside the key**, so
  the constraint (like the query) misses the cross-address duplicate.

## Why this is CAPPED (no value impact)

| case | duplicate serial reachable? | value impact |
|---|---|---|
| Capped asset | **NO** — capped forces `serial_number=1` (validation.js:2314-2316) + `issued_by_definer_only` (validation.js:2788) → the doublespend query omits the address (`!objAsset.issued_by_definer_only` guard, validation.js:2366-2369) → caught; the UNIQUE key is then (asset, denom, 1, definer) → caught | n/a |
| Uncapped, same author | **NO** — query catches (address matches) and the UNIQUE key matches → the INSERT fails | n/a |
| Uncapped, different authors | **YES** (empirically: U2 VALIDATION OK) | **NONE** — for an uncapped asset the serial is an arbitrary coin identifier; the issuer can already issue any number of serials, so a duplicate serial neither inflates supply beyond intent nor breaks any value invariant. Coins remain distinct by (unit, message_index, output_index). |
| Private asset reuse | **CONTAINED** — the per-unit payload-side recomputation binds the proof to the claimed issue address (divisible_asset.js:152-162: rows keyed `WHERE unit=? AND message_index=?`; mismatch → "incorrect spend proof"); the unit-level `(spend_proof, address)` check (validation.js:1640-1654) catches same-address reuse | none |

## The marginal-contribution critique

- World without the address-in-the-key quirk: the same serial could not be issued twice by any
  author. The DELTA this quirk adds: a duplicate serial on an uncapped asset — which has no
  economic consequence (the asset's supply is what was issued; serials are cosmetic for uncapped
  assets). No theft, no inflation-beyond-intent, no freeze, no consensus divergence.

## Empirical evidence (real path)

`evidence/lab/e2-5/e2-5-issue-reuse.js` (real `validation.validate` + `writer.saveJoint` for the
attack units; asset definition + U1 seeded schema-exact per the p2-lab convention):

```
E2-5 GENESIS VALIDATION OK sequence=good
E2-5 SEEDED asset=z9HezH2rmaYTcrEZlCCgu5jJ26pNA5jiAADMlb9tkrs= u1=... (A1 issue serial 1)
E2-5 U2-A2-issue-serial1 VALIDATION OK sequence=good      <- THE GAP: A2 re-issues serial 1, accepted
```

The U3 (same-author) control and the full save-path DB state were not observed: the single-node
harness's `writer.saveJoint → updateMainChain` reorg path (main_chain.js:197-198) requires the
ball/hash-tree records a seeded unit does not carry — a documented harness limitation, not a
finding. The same-author containment is statically certain (query + UNIQUE key both include the
address; a constraint violation fails the INSERT and the save).

## Residual risks / follow-up

1. **Full save-path confirmation** (U2 saved + U3 UNIQUE-rejected) needs the E1-7 two-node lab
   (working MC machinery): post the asset + U1 through real stabilization, then U2/U3.
2. **AA/marketplace sensitivity:** an AA that keys coins by `serial_number` alone (rather than by
   (unit, serial)) could conflate duplicate-serial coins — but that is AA-specific logic (out of
   scope) and the duplicate requires the issuer's own second key.
3. **Recommendation:** align the doublespend key and the UNIQUE constraint with the query — omit
   `address` from both for issue rows (like the `issued_by_definer_only` branch) so the "no double
   issue" comment is true. Hardening note (HN-16 candidate), not a bounty finding.
