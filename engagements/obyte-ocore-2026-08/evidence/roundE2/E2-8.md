# E2-8 — HN-5 → parent-composer chain: empirical verdict

Pinned ocore `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation hunter report.

## Verdict (one line)

**The hypothesized HN-5 → parent-composer chain is REFUTED as a direct link** (future-timestamp
units inflate the recent-TPS window but NOT the parent filter's rate source); **the parent-composer
crash itself is CONFIRMED end-to-end on the real path** — its rate-rise trigger is the flood
(recent units), not future-dating. Crash class = E1-5/HN-14 (node-side-fixable, out-of-scope
availability; hardening note).

## What the chain hypothesis claimed

future-timestamp units (valid, cheap, timestamp now+1..+5) → `getRecentTps` inflation →
`getMinAcceptableTpsFeeMultiplier` = 5 → local fee estimate rises →
`filterParentsByTpsFeeAndReplace` excludes all parents → `throw "all potential parents underpay
the tps fee"` (parent_composer.js:461) → composition crash.

## Test A — the HN-5 link (REFUTED empirically + in source)

Lab: 901 future-dated units (timestamp now+5, valid-shaped per validation's +5 bound,
validation.js:280-285) seeded into the unstable cache (the p2/e15 lab convention) on a real-boot
node (synthetic genesis through real validation+writer).

| measurement | before | after 901 future units |
|---|---|---|
| recent-window count (getRecentTps predicate: `ts - timestamp <= 60`, storage.js:1447) | 0 | **901** (all future-dated counted) |
| future-dated units in cache | 0 | 901 |
| `getMinAcceptableTpsFeeMultiplier()` | 1.5 | 1.5 (cache refreshes only every 60s; the threshold is count/period > 15, i.e. > 900 in the 60s window) |
| **`getCurrentTpsFee()` — the parent filter's rate source (parent_composer.js:427)** | **0** | **0 (UNCHANGED — getCurrentTps skips `timestamp > now`, storage.js:1360)** |
| min_parentable (current_fee × 3) | 0 | 0 |

**Conclusion:** the future-dated units inflate the recent window (901 counted) but leave the parent
filter's rate untouched. The filter computes `min_parentable = storage.getCurrentTpsFee() ×
(conf.min_parentable_tps_fee_multiplier || 3)` (parent_composer.js:427-429) — and getCurrentTps
explicitly skips future-timestamped units (storage.js:1360). The 5× multiplier HN-5 targets applies
to the NEW-UNIT fee gate (validation.js:1075-1076 `min_acceptable_tps_fee = current_tps_fee ×
multiplier × count_units`), not to the parent filter.

Additional cap: the multiplier threshold (>15) needs count > 900 in the 60s window, and the
multiplier cache refreshes only every 60s. A future-dating-only flood contributes at most ~75 units
(15/s × 5s future window) — the bulk must be normal recent units anyway. HN-5's practical effect is
negligible even where it applies.

## Test B — the real chain (CONFIRMED end-to-end)

Fresh boot (fast elapsed so the rate math is live). 16 flood units composed through the real path
(`composer.composeJoint → validation.validate → writer.saveJoint`) — each declared the minimum fee
at its (rising but still low) composition rate. Raw log (`evidence/lab/e28/e28b-run.raw.log`):

```
B-RATE-AFTER-FLOOD+POOL {"currentFee":7,"minParentable":21}     <- the flood raised the rate
current tps with shift 0 33
skipping potential parent <flood-unit> as its paid tps fee per unit 1 < min parentable tps fee 21   (×16)
replacement_parents [ <genesis> ]
added replacement parent <genesis>
skipping potential parent <genesis> as its paid tps fee per unit 0 < min parentable tps fee 21
replacement_parents []
E2-8-UNHANDLED-REJECTION: Error: all potential parents underpay the tps fee
E2-8-PROPAGATION: unhandled rejection (Node15+ default: process crash)
```

The full chain fires: flood units (fee 1, paid at their low-rate composition time) raise the rate
(current tps 33 → min_parentable = 7×3 = 21) → a fresh victim's composition (no own free units)
excludes the ENTIRE pool → the genesis replacement is excluded too (fee 0) → no replacements →
**throw → unhandled rejection → process crash**. This is E1-5's mechanism re-verified end-to-end
with the rate math measured (matches E1-5's raw log "current tps 33 → min parentable 21 = 7×3").

## Escalation doctrine application (marginal-contribution critique)

- World without the bug: parent selection returns `onDone(err)` (the sibling branches do), the
  composition fails gracefully, the wallet shows an error.
- Delta this bug adds: **process death** (unhandled rejection) or **permanent hang** (the callback
  is bypassed — composer.js:361/621 never settle). Crash-loop if the victim retries.
- Cap (proven): node-side fix resolves it without network coordination → **out of scope** per the
  DoS-coordination rule (like HN-2/HN-13). No fund-loss path.
- The chain trigger is the FLOOD (recent units raising the window rate), not future-dating — the
  HN-5 mechanism does not reach this crash.
