# E3-11 — Light-vendor fund path (terminal escalation lane)

**Hunter:** E3-11 · **Target:** ocore pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`
**Predecessor:** E2-12 (capped — trust-model-bound). This lane chases the open fund-path items:
the light-client RECEIVE path, the vendor `prepareHistory`, and the light AA-definition fetch (H-L2).

## Verdict (one line)

**CAPPED — the light-vendor fund path is trust-model-bound; no fund-impact candidate crosses the
documented hub-trust boundary, and no honest-vendor divergence with fund impact exists.** The
light client's weaker validation (signatures/balances/doublespends not verified in light mode)
cannot be exploited against an honest vendor, and every fabrication a malicious vendor can inject
through it is equal-effect with the vendor's inherently-trusted channels (get_balances, history
omission, broadcast censorship). H-L2's chash-preimage constraint makes the AA-definition angle
strictly weaker than the trust-model channels.

## Claim tuple

- **target/version:** ocore `a7eb776`, light-client path (`light.js`, `light_wallet.js`,
  `aa_addresses.js`, `validation.js` light mode)
- **entrypoint:** a light wallet receiving history/definitions from its configured vendor
- **precondition:** attacker = the light vendor (or a compromised/rogue vendor)
- **mechanism:** the light client accepts units without signature/balance/doublespend verification
  (validation.js:340-344 light short-circuit) and accepts stable-but-unproven units
  (`validateLight` swallows `lightStableErrorMessage`, validation.js:108-110; the proofchain
  membership rejections are commented out, light.js:254-258, 269-272)
- **observable effect:** a malicious vendor can serve fabricated payment units that the light
  wallet accepts and displays as (unconfirmed) credits; serve malformed-but-chash-valid AA
  definitions (aa_addresses.js:60-115); serve stale branches and omitted proofchains
- **negative control:** an HONEST vendor: the light client's view is correct (structural checks +
  unit-hash validation + witness-anchored proofchain for confirmed state, light.js:203-260); the
  outbound path is structurally safe (the victim's signed units are enforced by full nodes)
- **claimed impact/severity:** none crossing the trust boundary — capped; hardening notes only

## Analysis

### A — The receive/credit path (why no fund impact even with a malicious vendor)

`processHistory` (light.js:177-320) accepts joints on `validation.validateLight` alone. The
commented-out rejections (`stable but no ball`, `stable but not proven`, `proofchain doesn't prove
unit`) mean the vendor can serve units outside the witness-anchored proofchain, and
`validateLight`'s `ifJointError` handler ignores the "stable unit without proof" error
(validation.js:108-110). The units are inserted into the light DB; outputs from them become
(displayed) balance.

**Why this does not cross the trust boundary (marginal contribution ≈ 0):**
1. The vendor can display the same fake credit by answering `light/get_balances` (or omitting the
   real balance) with zero fabrication — an inherently-trusted channel with equal or greater
   effect. The fabrication adds cryptography (a self-consistent unit hash) but no new capability.
2. The fabrication is durable in the light DB but that is a LIABILITY for the attacker: restoring
   the wallet on a full node re-validates every unit (signatures checked) and the fabricated
   credit evaporates — the fraud is then visible. The victim cannot lose real funds on a
   fabricated credit (outbound spends are enforced by full nodes against the REAL balance).
3. The unconfirmed/unproven view matches the full node's own unconfirmed view (a full node also
   shows unconfirmed credits before stabilization); the light client simply cannot verify the
   confirmation state itself — which is the documented light design (the vendor is the
   confirmation oracle).

### B — The honest-vendor divergence question (my lane's sharpest addition)

Is there a fund path where the light client's OWN code diverges from a full node in a way that
matters even with an HONEST vendor? Checked:
- `fixIsSpentFlag`/`fixInputAddress` (light.js:448-500): the light client maintains its own
  is_spent/inputs tables from served units. With an honest vendor the inputs are real; the light
  client cannot verify doublespends (no graph), but neither can a full node's UNCONFIRMED view —
  the full node resolves doublespends at stabilization, and the light client's `processProvenUnits`
  marks proven units stable + `is_unique=1` on the same witness anchor. No divergence that matters.
- Balance computation: light wallets read balances from the local outputs table (built from
  served units) or the vendor. Outbound spends (composed + signed by the victim, broadcast to a
  full node) are enforced against the REAL ledger. No fund-movement path bypasses a full node.
- `validateLight` structural checks (unit hash, payload hashes, well-formedness) are the same as a
  full node's early checks (validation.js:130-160) — the LIGHT divergence is only the
  non-cryptographic verifications, which are the documented trade.

### C — H-L2 (light AA definitions) — strictly weaker than the trust-model channels

`readAADefinitions` (aa_addresses.js:60-115): light fetches unknown definitions from the vendor;
`objectHash.getChash160(arrDefinition)` MUST equal the address. Because the address IS the
chash160 of the definition, a malicious vendor cannot serve a different definition for a KNOWN AA
address (preimage resistance) — it can only invent NEW addresses whose definitions self-consistently
hash to them, and the wallet queries addresses only when it encounters them. Effects of an invented
malformed definition:
1. bounce-fee miscalculation → failed transactions (full node rejects) — availability only;
2. `determineGetterProps` with `validation_mci=0` throwing (aa_validation.js:792) → wallet compose
   crash — availability only;
3. no fund movement (the invented AA's outputs are synthetic; the wallet cannot be made to send
   real funds to a definition it trusts without the user's own action).
A malicious vendor achieves (1) and (2) with equal or greater effect through trusted channels
(serving garbage definitions, blocking get_definition). Marginal contribution ≈ 0.

### D — Outbound path (verified structurally safe)

The victim's own spends are composed and signed locally and broadcast to a full node, which
enforces the real balance, signatures, and doublespend state. The light client's weak validation
applies only to INBOUND served data, never to the enforcement of the victim's outbound units.

## Negative control (why the cap is proven, not asserted)

- Honest vendor: the confirmed-state anchor holds (witness-verified proofchains, ball-hash
  recomputation, the client's own witness list — light.js:203-260); the victim's balance and
  outbound spends are correct.
- The three fabrication classes (fake payments, stale branches, invented AA definitions) are each
  achievable with equal or greater effect through the vendor's inherently-trusted channels
  (get_balances, history omission, broadcast censorship, get_definition) — named per class above.
- No candidate enables fund movement the vendor could not already cause; no candidate changes the
  victim's ability to recover (restore-on-full-node reveals every fabrication).

## Residual risks / notes

1. The proofchain-membership rejections being commented out (light.js:254-258, 269-272) is a
   defense-in-depth regression: an honest-but-partial vendor (e.g., a syncing hub with an
   incomplete proofchain) can cause the light client to display unproven credits as if confirmed.
   Availability/UX only. Recommended hardening: restore the rejections for confirmed-state units.
2. H-L2's `insertAADefinitions(..., mci=0)` without `validateAADefinition` is a wallet-side
   hardening item (bounce-fee miscalculation / getter throw on invented definitions). Capped by
   the chash constraint.
3. No live multi-node light-vendor test was run (the lab does not include a light client + vendor
   pair); the analysis is source-verified against the pinned tree, consistent with E2-12/LR-1's
   same-grade conclusions.
