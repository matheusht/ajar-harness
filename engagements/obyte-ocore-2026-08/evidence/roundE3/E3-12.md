# E3-12 — RECIPIENT SPEND RACE: can the tps_fees_balance credit be spent in the same block/transaction it lands?

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation-hunter report. All anchors verified
against the pinned tree.

## Verdict (one line)

**CAPPED — no same-block/transaction race exists (all settlement paths are serialized under the
handleJoint/write locks, and a unit can only reference a stabilized MCI's ball after its fee
settlement has committed). The credit is usable deterministically from the next MCI. The one real
mechanism is a cross-node divergence window: the balance-sufficiency gate is a PERMANENT rejection
(ifUnitError) gated on node-local settlement state, so nodes at different settlement heights can
permanently accept/reject the same unit — amplified by the F4 poisoning (hugely negative balances
on ahead nodes) — but capped: the OPs' nodes are the ahead nodes, so the divergent branch never
stabilizes on the witness-anchored MC, confining the divergence to behind-node junk pollution and a
temporary DAG-content mismatch (no consensus impact).**

## Q1 — Can the credit be spent in the SAME block/transaction it lands? NO.

### Q1a — all settlement write paths are serialized under the handleJoint/write locks

| path | lock | evidence |
|---|---|---|
| `stabilizeMci` (the 1-MCI-at-a-time path) | `mutex.lock(["handleJoint"])` acquired at main_chain.js:1201, held across markMcIndexStable → AA triggers → `updateTpsFees(conn,[mci])` (main_chain.js:1257-1259, own conn, BEGIN/COMMIT) | main_chain.js:1199-1260 |
| `saveJoint` stabilization loop | under `['write']` (acquired inside the handleJoint flow via ifOk → saveJoint); fee updates at writer.js:727-729 and 759-761 (own conns, BEGIN/COMMIT) | writer.js:715-765 |
| `updateMissingTpsFees` (startup) | network.js:4290 under `handleJoint`+`initial`, before any unit processing | ER-4 e5 verified |

All four write the balance via `REPLACE INTO tps_fees_balances (address, mci, ...)` —
storage.js:1261 — the ONLY writer (ER-4 e1 verified; composer/light/validation read-only).

### Q1b — the next unit's validation cannot interleave

The validation of any unit whose `last_ball_mci = X` (i.e., that references MCI X's ball) also runs
under the `handleJoint` lock and reads the balance at `mci <= last_ball_mci`
(validation.js:1085-1086). Because stabilizeMci(X) holds the lock until X's fee settlement COMMITs,
the dependent validation necessarily observes the credited balance. There is no interleaving point
between the ball creation for X (addBalls, inside markMcIndexStable) and the X fee settlement —
both are in the same lock hold. **Same-block credit-and-spend is impossible within a node.**

### Q1c — "spend the credit" is not a per-unit debit anyway

The balance is a cumulative prepaid-fee account, NOT consumed per unit at validation. Posting a
unit only requires the balance to cover the DECLARED fee (`tps_fees_balance + tps_fee*share >=
min_tps_fee*share`, validation.js:1087-1089); the balance is adjusted only by the settlement deltas
(`declared - final`, storage.js:1246-1261). The declared fees were already burned from the author's
INPUTS at save (balance closure, validation.js:2654-2656), so a positive delta (credit) is a
REFUND of an overpaid declaration — the accounting is conserved (ER-4/E2-1 verified). A credit
cannot be spent more than once: it funds declarations, and every declaration is settled to its
final fee.

## Q2 — The real mechanism: permanent-gate × node-local settlement state = cross-node divergence window

### Q2a — the balance-sufficiency rejection is PERMANENT and node-local

- `validateTpsFee` (validation.js:1087-1089) returns a PLAIN `callback(...)` string on
  insufficiency, which routes to `callbacks.ifUnitError(err)` in the validate() error dispatcher
  (validation.js:464-470: non-object err → `ifUnitError`). `ifUnitError` rejects the unit (not
  saved; network.js:1083-1092 region; the re-arrival re-validates and is re-rejected while the
  balance stays insufficient).
- Contrast: the min-acceptable-fee branch explicitly wraps in `createTransientError`
  (validation.js:1094-1096) — transient. The balance-sufficiency gate is NOT transient.
- The balance is node-local until the node settles the same MCIs (deterministic deltas per MCI,
  storage.js:1246-1261).

### Q2b — the divergence

Node A (settlement height < X) and node B (>= X) validate the same unit U authored by an address
whose balance changes at X:
- **Credit direction (declared > final):** A (no credit yet) rejects U; B (credit landed) accepts.
  When A catches up, U re-arrives → re-validation now passes → U enters A's DAG late →
  **temporary** divergence, converges.
- **Debit direction (declared < final — the F4 poisoning shape):** A (not yet debited) accepts U;
  B (debited, balance hugely negative) permanently rejects U and every descendant referencing it.
  A keeps U and the branch (saved units are not re-validated on re-arrival). **Permanent DAG-content
  divergence** between the two nodes for that branch.

### Q2c — the cap (why this is not a consensus split)

- The MC is witness-anchored: units stabilize only when the OPs' waypoints witness them. The OPs'
  nodes are the network's fast (ahead) nodes — they have settled the flood MCI and therefore
  PERMANENTLY REJECT the divergent branch (balance gate). The branch can never get balls on the
  consensus layer.
- Behind nodes that accepted the branch hold non-stabilizing junk: `main_chain_index` never
  assigned, never balled, eventually archived — no MC impact.
- The merchant-fraud escalation (a behind-node merchant accepting a payment the consensus rejects)
  requires (a) a merchant node behind at the exact window, (b) the payment's output in the
  divergent branch, (c) the OPs not witnessing it — the merchant's own full node would show the
  payment unconfirmed; speculative, no demonstrated flow.
- The F4 poisoning amplifies the window (balances differ by ~10.7% of supply between settled and
  unsettled nodes), but the amplification is of a capped mechanism.

### Q2d — the reportable residue

This is the F4 finding's cross-node divergence note: the permanent balance gate makes the F4
poisoning not only a per-author freeze but a temporary cross-node acceptance divergence, with the
durable effect confined to behind-node junk pollution. It does not lift F4's severity (the
consensus layer converges) and it does not create a new finding (no value movement, no consensus
impact, node-side-fixable). Recorded as a hardening note (HN-16) + a note in the F4 package.

## Q3 — Lock ordering summary (the brief's explicit question)

```
handleJoint lock (validation + saveJoint entry)
 ├─ validation of U (reads balance @ mci <= last_ball_mci)
 ├─ ifOk → writer.saveJoint(U) → ['write'] lock → stabilization loop + updateTpsFees (own conns)
 └─ determineIfStableInLaterUnits... → handleJoint lock → stabilizeMci(X) → markMcIndexStable
     (balls) → AA triggers → updateTpsFees(X) → COMMIT → unlock
next unit's validation: waits on handleJoint → sees committed X settlement. Serialized. No race.
```

## Negative controls (verified)

1. A unit referencing MCI X's ball validates only after X's stabilization holds release — the ball
   exists (addBalls) but the lock is held until the X fee settlement COMMITs; the validation queue
   waits. No interleaving.
2. The credit is not withdrawable: the balance is a fee-only account; the only consumers are the
   min-fee gate and the settlement deltas (E2-10 verified: no withdrawal path; net cost = final).
3. `updateMissingTpsFees`'s watermark (getLastTpsFeesMci) is monotonic on sqlite (rowid) — a
   startup re-run cannot re-apply already-settled MCIs (ER-4 e5; the MySQL tie-break exception is
   HN-15, sqlite immune).
