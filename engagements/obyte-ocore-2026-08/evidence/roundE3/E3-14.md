# E3-14 — AA SELF-REDEFINITION (definition-change path in AA context)

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation-hunter report (terminal round).

## Verdict

**CAPPED** — an AA cannot redefine itself, cannot overwrite another AA's definition, and cannot
re-wire its getters or state. AA-emitted definitions (the AA-defines-AA path) are fully validated
at execution. Churn vectors are bounded. Residuals: 2 hardening notes (the defensive-throw pattern
in the AA-response validation path — HN-2 family; the 128-bit effective chash — informational).

## Claim tuple

- **claim:** "AA self-redefinition (definition messages changing an existing AA's code, state, or
  getters) is possible via the AA response message path."
- **verdict:** REFUTED — structurally impossible + empirically demonstrated.
- **decisive controls (file:line):**
  1. Address = chash160(definition); the AA response composer DERIVES the address from the
     definition (`aa_composer.js:1295` `message.payload.address = objectHash.getChash160(...)`) —
     a new definition yields a NEW address; a same-address redefinition requires a chash160
     second-preimage (128-bit effective: `chash.js` `getChash` drops 4 bytes of ripemd160,
     `hash.slice(4)` + 32-bit checksum → 2^64 birthday — infeasible).
  2. `aa_addresses.address` is PRIMARY KEY (initial-db/byteball-sqlite.sql) and
     `insertAADefinitions` uses `INSERT OR IGNORE` (`storage.js:921`) — **the first definition
     wins; repeated definitions are ignored** ("ignoring repeated definition of AA ...").
  3. AA response units run the FULL `validation.validate` (`aa_composer.js:1789`
     `validateAndSaveUnit` → `validation.validate({aa:true, aa_mci})`); definition messages hit
     the `validation.js:1740-1790` 'definition' case (chash check :1744-1748 +
     `aa_validation.validateAADefinition` :1765). No lighter path.
  4. Definition-path validation errors are plain callbacks → `ifUnitError` → `cb(err)` → `bounce`
     (`aa_composer.js:1801-1803` ifUnitError is the ONLY clean-return handler; the caller at :1402
     `if (err) return bounce(err)`).

## Churn vectors — bounded

| vector | outcome | control |
|---|---|---|
| AA redefines ITSELF (same address, new code) | impossible | chash binding (1295) + PK + OR IGNORE; 2^64 birthday infeasible |
| AA overwrites another AA/user address | impossible | same (would need a chash preimage of that address) |
| AA defines a NEW AA (nested/template) | intended; bounded | response count ≤ MAX_RESPONSES_PER_PRIMARY_TRIGGER=10; full validateAADefinition at execution; fresh address + fresh state; new AA inert until triggered |
| Getter re-wiring | impossible | getters computed once at definition insert (determineGetterProps, storage.js:917-920); definition immutable |
| State reset | no reset exists | the only repeat case (bAlreadyPostedByUnconfirmedAA, same unit — storage.js:932-946) RECALCULATES aa_balances via a REPLACE of an idempotent SUM over outputs (not additive — no double-count) |
| definition_template churn | shape-checked only (validation.js; aa_validation.js:424-426) | no execution path found that changes an existing AA |

## Residuals (hardening notes — NOT findings)

1. **HN-A (HN-2 family):** `validateAndSaveUnit` (aa_composer.js:1789-1830) THROWS on
   `ifJointError`/`ifTransientError`/`ifNeedHashTree`/`ifNeedParentUnits`/`ifOkUnsigned` — the
   uncaught-throw pattern (network.js:4367 re-throw → process death). Today the definition path
   routes errors to `ifUnitError` (clean bounce), so these throws are defensive-only; a future
   validation change that routes an attacker-influenced AA response to a joint/transient error
   would make them reachable → network-wide crash-loop. Fix: convert the throws to `bounce(err)`.
2. **HN-B (informational):** the effective AA-address space is 128 bits (ripemd160 minus 4 bytes +
   32-bit checksum, chash.js). 2^64 birthday collision is infeasible today; noted for long-horizon
   awareness, not a finding.

## Marginal-contribution note

The world without this property would allow AA code changes post-deployment — a fund-impact class
(tampering with live AA logic). The property is enforced by the address-binding design, so the
delta an attacker could add is ZERO. No severity claim arises.
