## Verdict (one line)

**CAPPED / negative — the per-tuple uniqueness is SOUND.** The f8 "last gap" closes: cross-asset
proof reuse is cryptographically impossible (the proof embeds the asset), same-asset double-claims
within one unit are rejected by the shared-state spend-proof dedup (empirically verified), and
cross-asset references of one output are blocked by the src-output asset filter. No new
multi-asset-specific surface. The only private-payment uniqueness gap remains the already-filed F3
(address-keyed check), which is per-proof and unaffected by the multi-asset feature.

## The three defense layers (source-verified + empirically tested)

### Q1 — Cross-asset proof reuse: IMPOSSIBLE (cryptographic)
- The transfer spend proof is `hash({asset, unit, message_index, output_index, address, amount,
  blinding})` (divisible_asset.js:125-136) — the **asset is a hash input**.
- Measured: P_A ≠ P_B for the same output with only the asset swapped (both runs, different keys);
  P_A deterministic across computations.
- Reuse requires a SHA-256 collision on differing inputs → impossible.

### Q3a — Same-asset double-claim in ONE unit: REJECTED (shared-state dedup, empirical)
- `objValidationState` is created ONCE per unit (validation.js:322) and shared across all messages
  (validateMessages → validateMessage per message).
- validation.js:1571-1573: `if (arrInputKeys.indexOf(spend_proof) >= 0) return cb("spend proof ...
  already used"); arrInputKeys.push(spend_proof)` — the same spend proof in two messages of one
  unit is rejected.
- **Empirical (real path):** CONTROL (one message, one proof) → `VALIDATION OK` (accepted);
  DUP (two messages, the SAME proof P) → **REJECTED: "spend proof ... already used"**.

### Q3b — Cross-asset reference of one output: BLOCKED (src-output asset filter, empirical)
- The src-output lookup binds the payload's asset: `SELECT ... FROM outputs WHERE unit=? AND
  message_index=? AND output_index=? AND asset=?` (divisible_asset.js:118-122) — an output created
  as asset A cannot be referenced by a payload claiming asset B ("not 1 row" rejection).
- **Empirical:** the exact query against X (an asset-A output): asset=A → 1 row; asset=B → 0 rows.

### Q2 — The uniqueness key (source-verified)
- Unit-level check (validation.js:1644): `(spend_proof, address)` — the proof embeds the asset →
  effectively per-asset; cross-asset rows never collide.
- Input-level check (validation.js:2255-2262): `AND asset=?` added generically for issue and
  transfer → per (asset, type, src_unit, src_message_index, src_output_index) tuples.
- Issue input-key (validation.js:2345): `(asset, denomination, address, serial_number)` — per-asset.
- Measured: zero duplicate-key rows in the inputs table (per-tuple keys).

## Why this closes the f8 gap

f8 deferred: "the uniqueness interaction across two private assets in one unit (per-tuple
uniqueness) was not verified." Verified now: the dd29823 multi-payload path keeps each payload's
uniqueness in its own per-(asset, proof) tuple; no cross-tuple confusion, no reuse, no collision.
Two assets with the same serial/denomination issue in one unit is legitimate (per-asset keys);
the same output cannot be claimed twice (Q3a) or cross-asset (Q3b).

## The F3 interaction (already filed, unchanged)

The F3 dodge (same proof, different address → the unit-level check keys on the unit's author, not
the output owner) applies per-proof regardless of the asset or the multi-asset feature. No new
surface added by multi-asset payments; F3 remains the single private-payment uniqueness gap.
