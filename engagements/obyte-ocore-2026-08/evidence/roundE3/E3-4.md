# E3-4 — DOUBLE-APPLICATION ATTACK ANGLE (the HN-15 question)

Pinned `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44`. Escalation hunter, terminal round. The question:
can an ATTACKER trigger the MySQL stale-watermark double-application of tps-fee deltas?

## Verdict

**CAPPED — the full chain is real in every link but requires a specific non-default deployment
(MySQL backend + bServeAsHub + supervisor restart + a nondeterministic tie-break), the value
consequence is bounded (non-withdrawable fee-credit or one-window over-debit), and no fund-loss
class is demonstrated. HN-15 is upgraded from "latent" to "attacker-triggerable under a
documented-unsupported deployment"; two adjacent robustness notes are added (HN-16 AA-trigger
re-run; the parent-composer crash is NOT a full-node vector).**

## The chain under test

```
attacker flood (valid units, rising rates)
  -> same-second multi-MCI settlement on MySQL (creation_date tie)
  -> attacker device-crash: hub/deliver bToMe to the victim's own hub (bServeAsHub)
     [E2-16 confirmed: the bToMe branch SKIPS the recipient-key validation]
  -> supervisor restarts the node (systemd/pm2/docker)
  -> startup re-enters updateMissingTpsFees (network.js:4290)
  -> getLastTpsFeesMci returns a stale tied row (nondeterministic ORDER BY creation_date DESC)
  -> reprocesses [stale+1 .. last_stable_mci] -> deltas re-applied (ER2-1 TEST-D confirmed)
```

## Q1 — Attacker-triggerable restart: YES, via the device-crash (bServeAsHub); the parent-composer crash is NOT a full-node vector

- **The device-crash (E2-16, 3/3 crash-loop) reaches a FULL NODE's own process when it serves as
  its own hub.** `hub/deliver` (network.js:3370-3440): the `bToMe` branch (message addressed to
  the hub's own device — the "I'm my own hub" deployment, `bServeAsHub`) **skips the
  recipient-key validation** (`keys.includes(...)`, network.js:3385-3393 is bypassed) and emits
  `message_from_hub` (network.js:3375) → `device.js handleJustsaying` (:136) →
  `decryptPackage` (:177) → the else branch (device.js:431-432) schedules an uncaught throw 100 ms
  later → `network.js:4377-4379` uncaughtException re-throw → process death. The attacker needs
  only the victim's hub URL + device address (semi-public) and a crafted message encrypted to any
  key the victim does not hold. The crash is REMOTE and REPEATABLE.
- **Restart re-entry:** `startRelay` (network.js:4256) runs `aa_composer.handleAATriggers()`
  (:4289) then `storage.updateMissingTpsFees()` (:4290) on EVERY start. Standard supervision
  (systemd/pm2/docker) restarts the process after the crash.
- **The parent-composer crash (E1-5/E2-8) is NOT a full-node vector:** `pickParentUnitsAndLastBall`
  callers are composer.js:361/621/862 (wallet composition) and light.js:606 (light wallet). The
  AA-response composition path uses a LOCAL `pickParents` (aa_composer.js:1374) — no
  `filterParentsByTpsFeeAndReplace` — so a full node composing AA responses does not hit the
  parent-filter throw. Only a wallet+node in ONE process (exchange wallet node) would restart via
  this vector.

## Q2 — Same-second multi-MCI settlement: PLAUSIBLE (and guaranteed on any offline catch-up)

- The attacker flood drives rapid stabilization: each `stabilizeMci` (main_chain.js:1239) →
  `updateTpsFees(conn, [mci])` (main_chain.js:1258) writes the mci's rows with
  `creation_date = CURRENT_TIMESTAMP` (second granularity). Several mcis settling within one
  wall-clock second tie their rows' creation_date.
- **Guaranteed tie by construction:** `updateMissingTpsFees` (storage.js:1267-1286) wraps the
  ENTIRE range `[last_tps_fees_mci+1 .. last_stable_mci]` in ONE `BEGIN`/`COMMIT` — every mci in
  the range gets its rows written in the same transaction and (on a fast run) the same second.
  Any node that was offline and catches up creates the tie without an attacker.
- The tie alone is harmless; it becomes stale only if the nondeterministic `ORDER BY
  creation_date DESC LIMIT 1` returns a row whose mci is below the max processed mci.

## Q3 — sqlite rowid immunity: CONFIRMED

- `getLastTpsFeesMci` (storage.js:1287-1289): `ORDER BY ${sqlite ? 'rowid' : 'creation_date'} DESC
  LIMIT 1`. sqlite rowids are insertion-monotonic; `REPLACE INTO` (PK `(address, mci DESC)`,
  byteball-sqlite.sql) assigns a fresh larger rowid; settlement writes mcis ascending. The
  max-rowid row is always the max processed mci → the watermark is correct → no reprocess of
  processed mcis. The stale state in sqlite requires an out-of-order rowid insert, which the
  normal flow cannot produce. **Immune (default backend).**

## Q4 — Other reprocess triggers: NONE (startup only); the re-stabilization edge is closed; NEW robustness note (AA-trigger re-run)

- `updateMissingTpsFees` has exactly ONE caller (network.js:4290, startup). The re-stabilization
  edge (ER2-1 residual #2) is closed: main_chain.js:1215-1217 prevents re-stabilizing an
  already-stable mci; writer.js:718-719 throws on >1 mci per save.
- **NEW (found this lane) — the startup AA-trigger re-run (HN-16):** `network.js:4289`
  `aa_composer.handleAATriggers()` "in case anything's left from the previous run". The trigger-row
  DELETE (aa_composer.js:102, inside the SQL BEGIN/COMMIT at :94/:119) and the AA-state kvstore
  `batch.write({sync:true})` (:117) are **separate stores, not atomic**. A crash between the
  kvstore write and the SQL COMMIT leaves the trigger row present (DELETE rolled back) with the
  state already updated → the restart re-executes the trigger against post-first-run state →
  **AA state vars can double-apply**. Fund impact is bounded: the response unit is saved only
  after the COMMIT via the `new_aa_unit` event (arrPostedUnits → eventBus → onNewAA → writer), so
  a crash before the COMMIT loses the first response entirely; the re-run composes ONE new
  response. The double-application hits non-fund state vars (counters, flags) — AA state
  integrity, not double payment. This is the team's own "in case anything's left" handling
  (network.js:4289) — the residual is the non-atomicity of the two stores. Robustness note.

## Value consequences of the primary chain (double-application of fee deltas)

- **Double-credit (refunds):** authors with positive deltas (over-declared, settled low) get the
  refund re-credited. The tps_fees_balance is **non-withdrawable** (ER2-1 claim (d), verified: the
  only writer is storage.js:1261; the balance only offsets future declared fees via
  composer.js:384-390/628-630). The attacker's profit = their own future fees at half price,
  bounded by the reprocessed window's deltas.
- **Double-debit (fee overcharge):** negative-delta authors (under-declared; the F4-poisoned
  window) get debited twice → deeper freeze. Chained with F4: the double-debit doubles the
  poisoning depth of one window. Not targetable (the reprocessed range is window-wide).
- Both directions are bounded by one window's deltas; no fund-loss class (no withdrawal; no
  cross-address transfer).

## Deployment prerequisites (why it is CAPPED, not a finding)

1. **MySQL backend:** conf.js:66-68 — the maintainer's own line: `// mysql is not currently
   supported; exports.storage = 'sqlite'` (added 2026-07-11). The code path + DDL exist
   (mysql_pool.js, byteball-mysql.sql) but the supported configuration is sqlite.
2. **bServeAsHub:** opt-in ("I'm my own hub" — real for power users/businesses/exchange nodes,
   but not the default relay/full-node deployment).
3. **Supervisor restart:** standard ops (systemd/pm2/docker).
4. **Nondeterministic stale tie:** the tie-break may return the max mci (no reprocess) or a stale
   one (reprocess) — a race, not a guaranteed condition.
5. **Program bar:** no fund-loss/freeze class demonstrated (non-withdrawable credits; one-window
   over-debits below the USD 1,000 floor for realistic windows).

## Fix directions

- HN-15: `getLastTpsFeesMci` → `SELECT MAX(mci)` or a dedicated watermark column (removes the
  tie-break entirely).
- HN-16: make the AA-trigger DELETE and the state write atomic (delete the row in the kvstore
  batch, or write a started/finished marker in the same store as the state).
- E2-16/Q-1: restore the commented-out `eventBus.emit('nonfatal_error', ...)` and remove the
  scheduled throw (defense for the bToMe path).
