### The count=1 inference — REFUTED by E2-9's own raw log and by source

E3-10's M1 states: *"Each unit therefore settles when the stability point reaches its mci, with
the previous unit as its last ball — getFinalTps's window walk counts units with
main_chain_index > last_ball_mci, i.e. count=1 … the pinned stabilization never creates it."*

Source says otherwise:

1. `last_ball_unit` is a **fixed field of the unit, chosen at authoring time** (the composer reads
   the last balled unit; validation only requires it to exist, be on MC, and be included in the
   parents — `validation.js:715-740`; no timestamp relation to the last ball, no "must be the
   newest ball" check). The 1-MCI-at-a-time stability advance changes *when* a unit settles, not
   *which* ball it references.
2. `getFinalTps` (`storage.js:1173-1218`) counts **all** units in the window
   `(last_ball_mci, mci]` via `assocStableUnitsByMci` (`countAll` loop, `storage.js:1207-1217`),
   not just ancestors. In a flood, all burst units share the same old `last_ball_unit`, so the
   window count at MCI k = k − last_ball_mci. The count>=30 window shape **is** what a flood
   produces.
3. **E2-9's own raw log (`/tmp/e29-hub.log`) — the same run E3-10 cites as corroboration —
   disproves count=1.** Per-MCI settlement (lines 3240-4308) shows tps = count/elapsed with the
   last ball fixed at MCI 0:

   | mci | final tps | decoded |
   |---|---|---|
   | 6 | 1.2 | count=6, elapsed=5 |
   | 17 | 2.8333333333333335 | count=17, elapsed=6 |
   | 18 | 2.5714285714285716 | count=18, elapsed=7 |
   | 21 | 3.0 | count=21, elapsed=7 |
   | 22 | 3.142857142857143 | count=22, elapsed=7 |

   count reached 22 — the exact r2 lag shape (last ball at mci 0, tip advancing, count = mci).
   E2-9's own report states it: *"The count reached ~20–22 (all units in the window)."*
4. E3-10's S1 experiment (`e310-exp.js`) seeds each unit's `last_ball_unit` = the **previous**
   unit — the drip shape (each unit authored after the previous one was balled). Its
   fee=17-at-every-step is correct **for that seeding** but does not represent the flood; the
   "30-unit chain settling under the 1-at-a-time advance" in the S1 measurement is a drip chain,
   not a burst chain. The E3-10 sentence *"the pinned stabilization never creates it [the
   count>=30 state]"* and residual note #1 (*"a lag state the code cannot produce"*) are wrong:
   E2-9's pinned code produced count=22.

So M1's *ordering* facts are right, but M1's *conclusion* ("count>=30 unreachable") is wrong. The
count>=30 window is reachable (it is the flood shape); what is **not** reachable is elapsed=1 for
an honest author (see M2).

## (2) M2 — wall-clock elapsed dilution: VERIFIED, and it is the actual protection

- Honest units get wall-clock timestamps: `composer.js:353/360`
  `objUnit.timestamp = Math.round(Date.now() / 1000)`. ✓
- The equal-timestamp trick is valid only for attacker-authored units: `validation.js:280-285`
  bounds only the future (`≤ now+5`), `validation.js:692` allows `ts == parent_ts` (equality), and
  `validation.js:722-740` imposes no timestamp relation to the last-ball unit. An honest author
  cannot be forced to set ts; the exchange's composer sets wall-clock. ✓
- S3 independently re-run (this review, real storage path): honest unit ts=T+5 in the lag window
  (count=31) → tps=6.2 → **fee=4,917 base** — byte-identical to E3-10's raw log. ✓

  actual fees 0–1 base for the burst units; final `TPS_FEES_BALANCES` (line 4344): user +181 at
  mci 21, witness +9/+18, **no negative balance anywhere**. ✓
- Structural reason the honest unit's elapsed can't be 1: the ball the honest unit references is
  *already balled* (stabilized) at authoring time, so its timestamp is ≥ the balling latency

## Why the demotion is nevertheless CORRECT (the honest-author-freeze is dead)

The finding's core impact claim: "a 30-unit 1-second window charges every settling author ~10.7%
of the supply; small authors are permanently frozen". Decomposing what a real flood does:

1. **Honest units in the flood window:** count grows to the flood size (real, E2-9 count=22), but
   elapsed ≥ balling latency (measured 4–7 s) dilutes tps to ~3–6 → fees of 0–1 base (E2-9) to
   4,917 base (S3, elapsed=5) — 10 orders of magnitude below the 10.7% figure, and the 10×
   estimation multiplier (storage.js:1329-1349 applies `tps_fee_multiplier`; `getFinalTpsFee`
   storage.js:1228-1235 does not) *credits* the balance when declared > final (E2-9: +181). No
   freeze.
2. **The attacker's own chain:** elapsed=1 is fully reachable (equal timestamps are valid), so
   the attacker's k-th flood unit settles at fee=round(10·(e^k−1)) — at k=30, 10.7% of supply,
   debited from the **attacker's own** `tps_fees_balance` (delta = declared−final,
   storage.js:1254). The funding bound (validation.js:2654-2655: inputs must cover the *declared*
   fee) caps what the attacker must pre-fund, but the settlement debit lands on the attacker's
   own address → **self-frosting, griefing-against-self, zero collateral**.
3. **Cross-author collateral:** requires an honest unit authored within ~1 s of a just-balled
   unit — not observed (lab: 4–7 s) and structurally gated by balling latency; the equal-timestamp
   lever is not usable on someone else's unit.
4. **Infinity variant (count≥709):** dead — funding bound caps count ≲ 32 (validation.js:1087
   gate + 2654-2655), and exp overflow needs k≥710 (measured in round-1).
5. **Permanence:** repayable debt, not irreversible (r2 Link 3; storage.js:1288-1306 gap-fill is
   idempotent, restart no-op — consistent).

The marginal-contribution critique (engine/escalation.md §1) also holds: even if a flood *could*
hit an honest author, the honest author's exposure is the delta the settlement formula adds on top
of the flood itself — and the measured delta is trivial for every non-attacker unit.
