## 1. Findings recommended for submission (2)

### 1a. obyte-2026-08-001 — Formula `is_valid_merkle_proof` vacuously satisfiable (MEDIUM)

- **One-sentence why it is real:** the formula engine's merkle-membership predicate verifies
  against a proof root the caller supplies from the proof itself — `proof = "0-" +
  base64(sha256(X))` evaluates `true` for any X with no tree membership — so any AA that gates on
  it is bypassable.
- **Mechanism:** `formula/evaluation.js:1763-1810` (`case 'is_valid_merkle_proof'`) →
  `merkle.js:84-101` (`verifyMerkleProof` reduces to `hash(element) === proof.root` with
  `index=0, siblings=[]`); root never bound to a committed/anchored value. Contrast: the sound
  sibling `in merkle` (`definition.js:1004-1031`) binds the root to an on-chain posted feed.
- **Reachability:** any AA formula (init/response/condition/getter) can call the opcode with an
  attacker-chosen element + proof; no prior validation restricts the proof beyond the 1024-char cap.
- **Empirical evidence (real path, 3 independent runs):**
  - Builder (p9): 4/4 arbitrary elements `true`; positive control (real tree) `true`; negative
    control (wrong root) `false`; `in merkle` contrast `false` without a posted feed.
  - Independent reviewer (IR-F1, fresh context): reproduced all rows + cross-constructed proofs.
  - **Fund-impact demonstration (E3-1, real two-node network):** a whitelist-gated AA
    (withdrawal only for merkle members) — attack run `BYPASS-CONFIRMED` (withdrawal output
    amount=1000) vs control run bounce (`'neither case is true'`). The E3-1 lab: definition →
    stabilization → trigger → formula → response on the real network.
- **Impact (marginal contribution):** the delta is "membership/authz gates in AAs are broken" —
  any AA trusting the construct is bypassable. **Cap:** which deployed AAs use the construct is
  not enumerable from ocore (individual AA repos out of scope) — usage-capped.
- **Severity:** Medium. The fund-impact class is now demonstrated (E3-1); the engine defect is
  in-scope (SF-9/SF-10); the usage dependence caps it below High.
- **PoC (max-impact + independent run — standing gate honored):**
  `evidence/lab/p9/p9-poc.js` (opcode-level) + `evidence/lab/e31-aa-demo.js` (fund-impact);
  independent runs in `reviews/claim_adjudication.json` (IR-F1) + E3-1's two-node run.
- **CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N = 5.3** (gates pass).
- **Lifecycle:** 6/6 gates CLEAR, promoted `findings/obyte-2026-08-001`.

### 1b. obyte-2026-08-003 — Spend-proof uniqueness keyed on a party-chosen address (LOW)

- **One-sentence why it is real:** the only network-wide private-payment double-spend detection
  (`validateSpendProofs`) keys its conflict match on the unit's claimed author address rather than
  the output owner the proof commits to — a sender who retains the bearer proof places a second
  `'good'` unit with the same proof under a different address, no conflict, no resolution.
- **Mechanism:** `validation.js:1637-1654` (conflict key `(spend_proof, claimed-address)`) vs
  `validation.js:1557-1568` (claimed address = unit author, never the output owner) vs
  `inputs.js:73-80` (the proof commits to the owner). The input-level check cannot run
  network-wide for private payments (`bPrivate` is payload-flow-only, `validation.js:2695`).
- **Reachability:** the sender retains the blinding (`composer.js:839`); empirically: victim's
  spend saved with its `(P, victim)` row; attacker's re-spend with the same P under the attacker's
  address ACCEPTED + SAVED as `'good'` on the MC path (direct descendant) — verified by 3
  independent runs + direct DB reads (r1 exp, IR-F3, LR-2).
- **Empirical evidence:** IR-F3 raw log + DB read (two `spend_proofs` rows, identical P; both
  units `'good'`, MC indices 1+2); contrast (same P + same address) cleanly rejected. E1-8:
  merchant exposure in its strongest form (direct-descendant ghost, unbounded window, no signal).
  E1-2/E4-3: the MC-position contest is attacker-influenceable (unit-hash grind, `main_chain.js:46-48`),
  but the value ledger always resolves to the victim (ghost payload rejected by the owner binding,
  `divisible_asset.js:159`).
- **Impact (marginal contribution):** the designed early-detection (unit-level rejection of a
  duplicate spend proof) is defeated; a merchant whose acceptance logic keys on "unit accepted +
  included" (sound for public bytes) is exposed for private bytes. **Bounds (proven):** no direct
  theft (payload owner binding); no voiding of the victim's unit in the same-branch case;
  merchant exposure is triple-contingent (acceptance flow + race win + timing). Ledger-integrity:
  permanent unresolved duplicate-spend records.
- **Severity:** Low (payment-race / ledger-integrity). Medium ceiling only if the merchant-
  acceptance link is demonstrated in a real deployment — out of the core library's control.
- **PoC (max-impact + independent run):** `evidence/lab/r1/p1-refute.js` + `evidence/lab/kp-f3/kp-f3-ghost-exp.js`;
  independent runs in `reviews/claim_adjudication.json` (IR-F3) + LR-2 + E1-8.
- **CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N = 3.7** (gates pass).
- **Lifecycle:** 6/6 gates CLEAR, promoted `findings/obyte-2026-08-003`.

## 2. Demoted finding with refutation trail (do NOT submit as-is)

### 2a. obyte-2026-08-004 — Settlement tps-fee exponential/unbounded (DEMOTED)

- **Original claim:** a 30-unit 1-second window charges every settling author ~10.7% of the
  supply (fee = 106,864,745,815,235 base at count=30/elapsed=1) → authors frozen.
- **Refutation trail (the escalation phase corrected the engagement's own record):**
  1. E3-10 (real-path experiment, `evidence/lab/e310-exp.js`): under the actual 1-MCI-at-a-time
     stabilization (`main_chain.js:540-543` "not trying next any more"; `writer.js:718/740`
     throw if >1), **every unit settles with count=1** — fee = 17 at every step of a 30-unit
     chain (S1). The count>=30 state seeded by the round-1 r2 drive is unreachable.
  2. **Orchestrator source verification:** `stabilizeMci` orders `markMcIndexStable` → `addBalls`
     → `updateTpsFees`; each unit's settlement runs after its OWN mci is balled, with the previous
     mci's ball as `last_ball_mci` → the `getFinalTps` parent-walk
     (`main_chain_index > last_ball_mci` skip, `storage.js:1178-1218`) counts 1.
  3. E3-10 M2: even in a lag state, honest units settle with wall-clock elapsed (S3: 4,917 base
     — six orders below the claimed poisoning); the equal-timestamp trick only frosts the
     attacker's OWN chain (self-frosting, ~10.7% of the attacker's supply-equivalent — griefing
     against self, economically pointless).
  4. E2-9 (real two-node network): 20-unit burst — fees 0-190, balances monotonically increasing
     (+181, the 10x estimation multiplier credits), no negative balances anywhere.
  5. The r2 drive that "confirmed" the honest-author freeze seeded the honest unit with the
     attacker's equal timestamps — the same synthesized-state error class as the round-1 p2
     crash PoC (a crash on a seeded state is not a reachable crash; a freeze on a seeded state is
     not a reachable freeze).
- **Residual truth (worth a hardening submission, not a bounty finding):** the settlement fee
  curve is unbounded relative to author balances (a future stabilization change could re-open the
  window); HN-15 (MySQL watermark double-application, conditional, sqlite immune); HN-5
  (future-timestamp multiplier inflation — below the $1k floor); the estimation/settlement
  multiplier asymmetry is a fair refund mechanism (no withdrawal path).
- **Status:** demoted to `unproven/obyte-2026-08-004` (impact claim refuted; mechanism retained
  as a design note). Lifecycle: demote recorded with the full reason.

## 4. Quarantine candidates (operator scope decision required)

### Q-1 — Remote zero-cost wallet crash via device-message decryption (device.js:431-432)
- **Mechanism (verified 3/3 crash-loop on the real path, E2-16/ER2-3):** any peer can deliver a
  device message encrypted to an unknown key via the hub mailbox; the wallet's `decryptPackage`
  schedules `setTimeout(() => { throw Error(...) }, 100)` → uncaught → crash; re-delivery
  re-crashes (crash-loop persistence, 3/3 cycles). The commented-out `eventBus.emit('nonfatal_error')`
  shows the intended pattern.
- **Scope:** wallet/device layer — OUTSIDE the declared DLT surfaces (SF-1..SF-10); program is
  Blockchain/DLT only; node-side fix class (out-of-scope DoS per the coordination rule).
- **Historical note:** Obyte's 2018 wallet chat XSS→RCE was treated as critical by the vendor —
  wallet-layer robustness is historically material to them. The operator may choose to surface it.
- **PoC:** crash-loop delivery loop script (E3-6 partial / E2-16); maximum-impact PoC ready if
  scope widens.

### Q-2 — Permanent silent DoS on multisig wallet creation via `extended_pubkeys` injection
- **Mechanism (verified against the real schema, E1-12 W1):** `my_xpubkey` accepted from
  non-correspondents; `addDeviceXPubKey` inserts the sender as a member with an approval_date; the
  wallet never finalizes; no removal path; same-xpubkey recreation reproduces the poisoning —
  remote, unauthenticated, permanent, silent.
- **Scope:** wallet layer — quarantine; fix direction: membership/correspondence check + FK.
