## 2. Finding obyte-2026-08-001 (formula `is_valid_merkle_proof` vacuously satisfiable) — **CONFIRMED at Medium**

### Marginal-contribution critique
- **World without the bug:** the construct would bind `proof.root` to an anchored/committed value
  (the sound sibling `in merkle` does exactly this — root must equal a posted data feed) or would
  not exist in the formula language. AA authors reaching for "merkle membership" would get a
  sound check.
- **The delta the bug adds:** any AA whose logic trusts the construct for membership
  (whitelists, airdrop claims, proof-of-publication, authorization predicates) is bypassable with
  a self-consistent proof. **The delta is now DEMONSTRATED on real code**: E3-1's withdrawal-gated
  AA moved 1000 units to an attacker who is in no merkle tree, on the real two-node network,
  through the real AA trigger path (definition → stabilization → `aa_triggers` → `handleAATriggers`
  → formula evaluation → response committed `sequence=good`). The control run bounced cleanly.
  The attacker's cost is zero (no keys, no membership, no preconditions beyond supplying the
  proof argument).

### Does the fund-impact demo raise the severity? **No — it CONFIRMS the impact class and
strengthens the exploitability evidence; Medium remains correct.**

Arguments for raising (considered, rejected):
- The fund impact is real (withdrawal executed) — but it is conditional on an AA *choosing* the
  construct. The impact is on a subset of the ecosystem (AAs that use the opcode), not on the
  consensus/ledger itself. Integrity impact for affected AAs: the current vector
  `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N` (5.3) already encodes conditional integrity.
- I:L → I:H would raise the score to 6.5 (still Medium band) — the honest reason NOT to: the
  opcode is a footgun whose reach depends on adoption; the finding's value is that the ENGINE
  ships an unsound primitive, and the fix (bind the root or remove the opcode) is engine-level.
  Severity should reflect what the engine defect is worth to fix + the demonstrated impact class,
  capped by the usage-dependence. Medium is the defensible ceiling.
- The opcode is first-class and tested in the suite (test/formula.test.js:3123-3145), so use is
  plausible — this argues the LIKELIHOOD is non-trivial, which Medium already assumes.

Arguments for lowering (considered, rejected):
- "Individual AAs are out of scope" does NOT cap this: the engine-level defect is in scope
  (SF-9/SF-10), it is confirmed at two levels (function + AA execution), and the fix is
  engine-level. The usage-cap is a real limiter but not a demotion — the construct is a supported
  opcode, and its unsoundness is a defect in the engine itself.

**Verdict: 001 = Medium (unchanged). CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N = 5.3
(unchanged). The E3-1 demo is added to the package as exploitability evidence (E4-5's revision
action).**

## 3. Finding obyte-2026-08-003 (spend-proof uniqueness keyed on a party-chosen address) — **CONFIRMED at Low**

### Marginal-contribution critique
- **World without the bug:** the uniqueness check would key on the output owner (the value the
  spend proof commits to — the payload-side recomputation, divisible_asset.js:120-136, already
  does this per-node). A sender's re-spend of the recipient's private output would be rejected at
  unit level on every node — the designed early-detection protection.
- **The delta the bug adds:** the sender's re-spend enters the DAG as `'good'` with no rejection
  signal; a merchant whose acceptance keys on unit inclusion + stability receives no warning; the
  re-spend races for the MC position. **The escalation phase bounded this delta precisely:**
  - The value ledger ALWAYS resolves to the victim (E1-2's decisive control): the ghost's payload
    is rejected by the owner binding ("incorrect spend proof", divisible_asset.js:159) — the ghost
    never materializes its claimed outputs; the victim's unit is not voided in the same-branch
    case (LR-2: victim stays 'good', MC indices 1+2).
  - The MC-position contest IS attacker-winnable (E1-2: tip anchoring + unit-hash grind, ~2
    attempts) — but position ≠ value: even a displaced victim unit's VALUE still resolves to the
    victim's spend (the ghost has no materialized outputs to compete with).
  - The merchant exposure (E1-8) is real but triple-contingent: private-payment merchant + an
    acceptance flow keyed on inclusion-without-uniqueness + race timing. The "silent contest"
    (no rejection signal) is the strongest empirical form; the direct financial loss requires
    the acceptance-flow link, which is outside the core library and not demonstrated.

### Does the displacement evidence raise the severity? **No — the ceiling stays Low.**

Arguments for raising (considered, rejected):
- E1-2's "reliably attacker-winnable" MC position — rejected as a lift because the value outcome
  is position-independent (the victim's value is never lost; the ghost's claim never materializes).
  A severity lift needs value loss or a demonstrated acceptance-flow exploit; neither is present.
- The E4-3 displacement empirical (still pending, timed out twice) would refine the exposure
  WINDOW timing, not the impact CEILING — the ceiling is set by the value-resolution + the
  acceptance-flow contingency.

Arguments for lowering (considered, rejected):
- The ledger-integrity defect (permanent unresolved duplicate 'good' units) is real but
  informational in impact; the payment-race vector is the Low rationale and it is confirmed
  empirically. Informational would understate the demonstrated race + the absence of any
  rejection signal (a real operational hazard for private-payment adopters).

**Verdict: 003 = Low (unchanged). CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N = 3.7
(unchanged). The E1-2/E1-8 evidence is already in the package's adjudication trail; the E4-3
result, when it lands, refines the exposure window only.**
