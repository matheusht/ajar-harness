## Claim (c) — double-application: direct double-call AND stale-watermark reprocess path — **VERIFIED** (incl. reprocess-path proof, sqlite immunity, MySQL-only condition)

TEST-C (direct double-call): raw log shows a second explicit `storage.updateTpsFees(conn, [1])` → balance 1,000,000 → 2,000,000 ("delta applied again: true"). The single-application invariant rests on caller discipline: direct callers are main_chain.js:451/1258 and writer.js:728/760 (stabilized-mci ranges); a duplicate mci across calls re-applies the delta because the SELECT (:1259) reads the already-updated balance.

TEST-D (reprocess path) — **the key item. Verified the raw evidence actually shows the reprocess path executing:**
- E2-1.js TEST-D section calls **only** `await storage.updateMissingTpsFees()` — no direct `updateTpsFees` call in that section (read of E2-1.js confirms).
- The raw log shows a third `updateTpsFees [ 1 ]` (line 89) **between** the TEST-C summary (line 88) and the TEST-D summary (line 92) — this is the internal `updateTpsFees(conn, [1])` invoked from `updateMissingTpsFees` (storage.js:1280, inside BEGIN/COMMIT at :1278-1283) after `readLastStableMcUnitProps` → `last_stable_mci = 1` and `getLastTpsFeesMci` → stale watermark `0`.
- Result (raw log line 92): `watermark= 0 | balance before reprocess= 2000000 -> after= 3000000 | double-application: YES (reprocessed mci 1 with the delta applied again)`. ✓
- The stale state is set up faithfully: a newer-rowid `tps_fees_balances` row at mci=0 makes `ORDER BY rowid DESC` return mci 0 while the mci=1 delta is already applied — the same *state* the MySQL tie-break produces.

sqlite immunity — **confirmed from source**: `getLastTpsFeesMci` (storage.js:1287-1289) orders by `rowid` on sqlite, `creation_date` otherwise. sqlite rowids are insertion-monotonic; REPLACE INTO assigns a fresh, larger rowid; normal settlement writes mcis in ascending order (updateTpsFees iterates the range ascending; updateMissingTpsFees builds `last_tps_fees_mci+1 .. last_stable_mci` ascending). Therefore the max-rowid row is always the max processed mci → watermark correct → no reprocess of processed mcis. The stale state in sqlite requires an out-of-order rowid insert, which the normal flow cannot produce. Immune.

MySQL-only condition — **confirmed**: the ternary at storage.js:1288; the MySQL table (`initial-db/byteball-mysql.sql:981-986`) has `creation_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` — second granularity — with `PRIMARY KEY (address, mci DESC)`. REPLACE INTO refreshes creation_date; a same-second multi-mci settlement (a burst within one `updateMissingTpsFees`/stabilization transaction) ties all rows on creation_date, and `ORDER BY creation_date DESC LIMIT 1` then returns an unspecified row among the ties — if it returns an mci below last_stable_mci, the next startup (`network.js:4290` runs `updateMissingTpsFees`) reprocesses already-settled mcis and re-applies their deltas. MySQL is a real supported backend (db.js:5-19, mysql_pool.js, conf.js:123-129), though non-default (conf.js:68 `exports.storage = 'sqlite'`). The tie-break is nondeterministic (not a guaranteed stale), so the hazard is a race — the write-up's hedged "can arise" is accurate. The `last_tps_fees_mci > last_stable_mci` throw guard (storage.js:1273-1275) covers the opposite stale direction.

Reachability assessment is sound: needs (1) the MySQL backend, (2) a same-second multi-mci settlement to create the tie, (3) a node restart to re-run `updateMissingTpsFees`. Not directly attacker-triggerable. Consequence: double-credit (refund inflation → balance offsets future declared fees, composer.js:384-390/628-630) or double-debit (fee overcharge). HN-15 rating is right.

## Claim (d) — no withdrawal path for the balance credit — **VERIFIED** (with one evidence-artifact defect)

Independent full-tree grep for `tps_fees_balances` (all *.js + DDL, excluding node_modules): the **only writer** is storage.js:1261 (`REPLACE INTO`); every other reference is a SELECT read — composer.js:384/628 (offset the *declared* fee), light.js:637, validation.js:1085 (min-fee gate), storage.js:1259 (settlement read), :1288 (watermark), :1424; DDL only in sqlite_migrations.js:560 and initial-db/*.sql. Non-withdrawable credit ledger — confirmed.

**Evidence-artifact defect (low):** E2-10.md prints `E2-10-WRITERS: []` and annotates it "no code path writes the balance except the settlement delta". I reproduced the script's grep verbatim against the pinned tree — it does return `[]`, but **by construction**: `matchAll(/tps_fees_balance[^\n]*/g)` starts the match at the identifier, so the leading `REPLACE INTO` keyword on storage.js:1261 falls outside the matched substring and the `/INSERT|REPLACE|UPDATE|DELETE|INTO/` filter never fires. The grep is systematically blind to the canonical write form and would report `[]` even for a tree whose only writer it was meant to catch. The qualitative claim survives only because my independent keyword-anchored grep found exactly one writer. The artifact overstates its own evidential power — the conclusion is verified by other means, but the cited empirical line does not actually demonstrate it. Fix: anchor the regex on the line (`/.*tps_fees_balance.*/` per line) or search for `INTO tps_fees_balances` / `UPDATE tps_fees_balances` / `DELETE FROM tps_fees_balances`.

## Residual risks

1. **HN-15 (unchanged):** MySQL stale-watermark double-application — real; conditional on MySQL backend + same-second multi-mci settlement (creation_date second-granularity tie, `initial-db/byteball-mysql.sql:981-986` + `storage.js:1288`) + node restart (network.js:4290). Bounded by the reprocessed window's deltas; not directly attacker-triggerable. sqlite (default) immune.
2. **Caller discipline:** the single-application invariant for `updateTpsFees` (storage.js:1237) rests on main_chain.js:451/1258 and writer.js:728/760 never passing an already-settled mci; a re-stabilization edge (reorg/rollback) would double-apply without any watermark involvement. Static finding territory (ER-4); not empirically exercised here.
3. **Parked balance:** an author can park arbitrarily large fee-credit (their own value); usable only to offset future declared fees — also acts as an F4-flood shield. Robustness, not value.
4. **Rounding dust:** `Math.ceil` at compose (composer.js:387) vs `Math.floor` at settlement (storage.js:1258) — per-unit dust direction is E2-11's lane; not re-adjudicated here.
