## Claim (a) — composition throughput caps the natural-burst rate at ~6/s — **verified** (mechanism real; measured rate ≈ 6.7/s)

- **Measured number.** Raw hub log line 3108: `[hub] burst of 20 posted, end second=1786457411 (window 3s)`.
  20 units in a 3-second window → ~6.7/s ≈ the claimed "~6/s". Unit timestamps corroborate
  (hub-final dump: mci 2-6 at ts 1786457409, mci 7-17 at 1786457410, mci 18-21 at 1786457411).
- **Mechanism (serialized parent selection).** Each burst unit's `parent_units` = `[previous unit]`
  (e.g., WP-TAIL-0 xp6ejW's parent = RL7YkC, the mci-22 unit; log line 3395 area). Composition is
  inherently serial: unit N+1 cannot be hashed until unit N is composed, validated and saved
  (per-unit log: "validation ok took 23-35ms", "committed unit … write took 24-50ms"). The cap is
  a practical honest-pipeline rate, not a protocol-enforced limit — the E2-9 report states this
  correctly ("optimized tooling … = the F4 attack lane").
- Minor table error in E2-9 (does not change the claim): the mci→tps table mislabels two entries —
  mci 10 is 1.667 (not 2.166; 2.166 is mci 13) and mci 15 is 2.5 (not 2.857; 2.857 is mci 20).
  The values themselves all exist in the raw log (24 "final tps at" lines, paired with
  `getFinalTps <unit> <mci>`).

## Claim (d) — E2-11: floor dust destroys; half-up can create but is OP-only or ~50x below cost — **verified** (ratio is actually ~100x, i.e., even more dead)

- **Settlement floor destroys, never routes.** `storage.js:1258`
  `Math.floor(total_tps_fees_delta * share / 100)` (E2-11 cites :1255 — 3 lines off, same code).
  `Math.floor(x) ≤ x` for every recipient ⇒ dust is destroyed, never credited anywhere.
  Routing impossible; verified numerically (`floor(-1*33/100) = -1` etc.).
- **Routing to a chosen address is blocked anyway**: `getTpsFeeRecipients`
  (`storage.js:1460-1470`) — if any recipient is external, override to author-only
  (`recipients = { [author_addresses[0]]: 100 }`). ✓
- **Sign bias real**: negative deltas (the F4 direction) over-debit up to 3x for |D|=1 at 33/33/34
  (three × `floor(-1*33/100) = -1` ⇒ -3 vs true -1); positive deltas under-credit. Verified numerically.
- **Paid-witnessing half-up**: `paid_witnessing.js:162`
  `Math.round(objUnit.payload_commission / countPaidWitnesses[v.unit])` ✓; SQL `ROUND(1.0*…)` :173 ✓;
  RAM-vs-DB cross-check :185 ✓. Creation examples verified (`round(5/2)=3` ⇒ 2 witnesses pay 6 for 5,
  +1; `round(12/8)=2` ⇒ 16 for 12, +4; `round(3/12)=0` ⇒ -3; `round(5/10)=1` ⇒ +5). Recipients are
  the MC-designated witnesses = OP list (`readMcUnitWitnesses` → `storage.getOpList` for v4+,
  `paid_witnessing.js:205-207`) — governance-selected, not attacker-selectable. Not exploitable ✓.
- **Headers-commission half-up**: `Math.round(full_amount * share / 100.0)`
  (`headers_commission.js:183` RAM / :199 SQL; E2-11 cites :202 — off by a few lines). External
  recipients ARE allowed — `validateHeadersCommissionRecipients` (`validation.js:1100-1126`) has no
  author constraint (only positive-int shares, sorted valid addresses, sum 100) ✓. Winner = lowest
  `sha1(child_unit + next_mc_unit)` (`getWinnerInfo`, `headers_commission.js:249-257`) ✓;
  `payload_commission === payloadSize` reconciliation (`validation.js:258-260`) ✓; exponential
  oversize fee (`storage.js:1137-1155`) ✓.
- **Economics**: with N recipients, unit size ≈ 50N and payload commission ≈ size ⇒ commission ≈ 50N
  vs max half-up creation ≈ N/2 ⇒ the commission is **~100x** the max gain (E2-11's "~50x" is
  conservative; net ≈ −49.5 per recipient, "dead by two orders of magnitude" holds). Verified
  numerically: hc A=5 50/50 → 3+3=6 (+1); A=1 50/50 → 1+1=2 (+100%).

## Findings

### F1 (medium) — E2-9 did not actually run at tps_interval=1; the getSystemVar cache held the lab default 60
- The run claims `tps_interval=1 (mainnet value)`, but the fee arithmetic in the raw log proves the
  in-memory cache used **60** throughout:
  - `getSystemVar` reads the in-memory `systemVars` cache (`storage.js:1122-1127`), populated by
    `initSystemVars` (`storage.js:2463`, invoked from `initCaches` at `storage.js:2526`) during boot
    from DB rows that `e17b-boot.js` inserted as `tps_interval=60`.
  - `e29-run.js` `setTpsInterval` then issues a **DB-only** `UPDATE system_vars SET value='1'`
    (e29-run.js, after `boot()` returns) — the cache is never refreshed. The script's own SYSVARS
    dump (log line 144) shows the DB = 1, but all computations use the cache = 60.
  - Decisive raw-log arithmetic (interval=60 reproduces every value; interval=1 does not):
    - WP-TAIL-0 (local tps 5.5): `validation { min_tps_fee: 10 }` — interval=60 → round(100·(e^0.0917−1)) = 10 ✓; interval=1 → 24,369.
    - BURST-1 (local tps 0.4): declared 1 — interval=60 → round(100·(e^0.0067−1)) = 1 ✓; interval=1 → 49.
    - mci 23 settlement (final tps 5.5): actual 1 — interval=60 → round(10·(e^0.0917−1)) = 1 ✓; interval=1 → 2,437.
- Impact: "actual fees 0-1 base" and "+10/unit credit" are interval-60 magnitudes. At true mainnet
  interval=1, fees at the measured tps reach ~2.4k base ≈ 2.4e-6 GBYTE (peak) — still trivial, deltas
  still positive, and the poisoning threshold (0.0033 GBYTE = 3.3e6 base ⇒ tps ≈ 12.7, not 15 as
  stated) remains unreachable at ~6/s honest composition. **The verdict direction survives; the
  "measured at mainnet values" framing is overstated.** A re-run with the cache updated (or
  boot-time tps_interval=1) is the correct evidence for the mainnet-magnitude claim.
- Note: E2-9's own arithmetic asides carry 10x slips in both directions ("10*(e^5.5−1) ≈ 24k base" —
  actual 2,437; "fee ≈ 3.3e6 base at tps≥15" — actual 3.27e7). None affects the conclusion.

## Verdict

- (a) **verified** — composition cap ~6/s (measured 6.7/s; 20 units/3 s), serial-parent mechanism real.
- (b) **verified** — settlement window 4-7 s vs 1 s burst; tps diluted to 2.86-5.5; reproduced exactly
  (20/7, 21/7, 22/4) from raw unit timestamps; `storage.js:1174`.
- (c) **verified (direction)** — multiplier-10 estimate vs no-multiplier settlement credits the balance
  (`storage.js:1337` vs `:1234`, delta `:1249`, credit `:1258-1264`); empirical balances +181, no negatives.
  Magnitude caveat per F1 (the run used tps_interval=60, not 1).
- (d) **verified** — floor dust destroys and cannot route (author-only override `storage.js:1460-1470`);
  half-up creation real but recipients OP-only (witnessing) or the site is ~100x cost-dominated (hc);
  all arithmetic spot-checks pass.
- E2-9's refutation stands in mechanism and direction; its "mainnet parameters" framing is overstated (F1).
  E2-11's capping is fully verified.

## Residual risks
- Mainnet-magnitude fee/balance figures in E2-9 are unproven (tps_interval=60 cache flaw, F1) — re-run
  with cache-correct interval before quoting magnitudes externally.
- The 0.0033 GBYTE poisoning threshold is reached at tps ≈ 12.7 (not 15); still unreachable by honest
  composition, but the F4-attack-lane margin is ~2x thinner than E2-9 states.
- No direct post-settlement compose test survived (F2) — only the +181-balance inference.
- `tps_interval` is a governance variable; a future vote lowering it would shrink the dilution margin
  (already noted as E2-14 lane in E2-9).
