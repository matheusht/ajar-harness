## E2-16 — Q-1 crash-loop

### Claim (a) — the device-layer scheduled throw crash-loops on re-delivery (3/3 cycles)

**Verdict: verified** (precisely: crash + repeatability across 3 independent restart cycles; the
"re-delivery → re-crash" property is demonstrated across cycles, each being a fresh victim process
crashed by one delivery)

Decisive source:

- `device.js:431-432` — `decryptPackage` else-branch:
  `setTimeout(function(){ throw Error("message encrypted to unknown key, device "+my_device_address+", len="+...); }, 100);`
  The throw fires 100 ms later, after the `try { decryptPackage(...) } catch` at `device.js:170-173`
  has returned — i.e., uncaught. The nonfatal-error alternative is commented out at `device.js:434`.
- `network.js:4377-4379` — ocore's own `uncaughtException` handler ends with
  `throw err; // crash the process to avoid ending up in an inconsistent state` → process death is
  ocore behavior, not harness artifact.

Decisive raw logs (3/3 cycles, `/tmp/e2-16-victim.log`, `-4`, `-5`), identical pattern each:

| cycle | raw log | delivery accepted | failed-to-decrypt | UNCAUGHT throw (device) | process death |
|---|---|---|---|---|---|
| 1 | `/tmp/e2-16-victim.log` L297-320 | L298 `response":"accepted"` (to `037CDE6K3BYY6SNBEQY5SVR6P7JUWBJE2`) | L300 `justsaying error failed to decrypt` | L305 `[victim] UNCAUGHT-EXCEPTION: Error: message encrypted to unknown key, device 037CDE6K3BYY6SNBEQY5SVR6P7JUWBJE2, len=88...`; L307 `Uncaught exception: ... at Timeout._onTimeout (.../device.js:432:10)` | L320-325: `network.js:4379 throw err` + `Node.js v25.9.0` fatal footer |
| 4 | `/tmp/e2-16-victim-4.log` L242-265 | L243 `accepted` (`0DIKVMZLR7SI4LA2T5TV3SOOB3MSTUVCA`) | L245 | L250-252 (`device.js:432:10`) | L265 `Node.js v25.9.0` |
| 5 | `/tmp/e2-16-victim-5.log` L239-262 | L240 `accepted` (`0KPQLQZM26DZEDJY7BZ6ZB5LEOOUJSAQC`) | L242 | L247-249 (`device.js:432:10`) | L262 `Node.js v25.9.0` |

Every cycle: `hub/deliver` → `accepted` → `message encrypted to unknown key` (L299/244/241) →
`failed to decrypt` justsaying → scheduled throw at `device.js:432:10` → re-throw at
`network.js:4379` → process death. Victim device addresses and `len=88` in the report table match
the logs exactly. **3/3 verified.**

Precision note on "re-delivery": each log file is ONE victim process — there is no
crash-then-auto-restart-then-re-crash inside a single log (the victim has no auto-restart). The
crash-loop is the persistence property across restart cycles: the attacker re-delivers after each
restart and the victim re-crashes — demonstrated by the 3 independent cycles, each crashing on a
single delivery (including two deliveries in victim.log: the first rejected at validation
L244-245 "invalid to address" — malformed `to` field — the second accepted L297-300 → crash).
The 3/3 claim as written ("fresh victim → single hub/deliver → crash; attacker repeats against any
restarted victim") is exactly what the raw logs show.

### Claim (b) — the delivery path (hub/deliver mailbox → wallet processing) is real and remote

**Verdict: verified** (remoteness: by protocol — any inbound ws peer; the empirical run was
loopback)

Decisive source:

- `network.js:3347` `case 'hub/deliver'`; `network.js:3360` `bToMe` computed;
  `network.js:3373-3378` — the `bToMe` branch replies `accepted` and emits
  `message_from_hub` **without** the recipient-key check; the `keys.includes(...)` check at
  `network.js:3390-3391` ("wrong recipient ephemeral pubkey") runs **only** in the non-bToMe
  registered-device branch (`network.js:3381-3391`).
- `device.js:147-177` — `handleJustsaying('hub/message')`: field checks, hash check, signature
  check (attacker signs with their own key → passes), then `decryptPackage` (L177) inside try/catch.
- `device.js:404-445` — `decryptPackage`: recipient-ephemeral-key matching against
  {temp, prev-temp, permanent} (L417-429); else-branch L430-434 (the throw).

Raw-log confirmation that the real path executed: the victim is the ocore process itself, running
its own listener ("WSS running at port 6611", `/tmp/e2-16-victim.log` L25 — `network.js:4240`,
auto-started because `conf.explicitStart` is unset, `network.js:4347`), and the delivery walks
network.js `hub/deliver` → device.js `hub/message` → `decryptPackage`:
`RECEIVED ... "command":"hub/deliver"` → `accepted` → `message encrypted to unknown key` →
`failed to decrypt` → crash. The attacker script signs the device message with its own fresh key
(`e2-16-attacker.js`: `attacker_priv = crypto.randomBytes(32)`), which is all the hub-side checks
require.

Remoteness nuance: the empirical run connects from `127.0.0.1` to the victim's hub port
(`VICTIM_URL = ws://127.0.0.1:6611`). Nothing in the mechanism requires local access — it is a
plain inbound ws `request` to the victim's listener, so any peer that can reach the hub port is
equivalent. The "remote" qualifier holds by protocol construction; the demo itself was loopback.

Population-scope nuance (strengthens, does not weaken): `network.js:3361`
`if (!conf.bServeAsHub && !bToMe) return ... "I'm not a hub"` — the `bToMe` branch is reachable
even when the victim does **not** set `bServeAsHub`; the actual precondition is "victim runs a
listening full node (conf.port set) with a device identity, and the message `to` equals the
victim's own device address". The report's precondition "(1) bServeAsHub: true" is therefore
conservative — the population is every listening full node, not only self-hubbers. Cap direction
(public-hub normal flow closed by the key check) is unaffected.

Citation drift: the report cites the keys check at `network.js:3424-3426`; the actual check is at
`network.js:3390-3391`. Substance identical; the cited range 3370-3440 covers the handler.

Negative control: `/tmp/e2-16-negctl.log` L240-242 — delivery with `recipient_ephemeral_pubkey` =
victim's permanent pubkey → `accepted` → `message encrypted to permanent key` → `failed to
decrypt: Error: Public Key could not be parsed` → **no crash** (no UNCAUGHT lines in the file).
The else-branch is not reachable with a key the victim holds. Verified.

## Residual risks / notes

- E2-16 severity/scope remains the operator's decision (quarantine-level; device/wallet layer
  outside the declared DLT surfaces). The DoS-coordination rule (node-side fix without network
  coordination → out of scope) applies as the report says, but the 2018 wallet-chat XSS→RCE
  precedent shows Obyte treats wallet-layer remote crashes seriously; also note the population
  nuance above (all listening full nodes, not only `bServeAsHub`) and that the empirical demo was
  loopback-only (host-to-host reachability of the hub port not exercised).
- E2-6 is infrastructure/deliverable evidence, not a finding; the response unit's stabilization
  (witness waypoints referencing it) was not exercised in this run.
- No secrets in any reviewed artifact (synthetic lab keys only).
