## Claim (a) — e32 flood: "the flood experiment at mainnet parameters demonstrates NO impact of any kind"

### a1. VERIFIED — the flood chain settles with trivial fees (the raw log core)

`/tmp/e32-hub.log:5980` `[hub-final] UNITS(36)` — parsed: 30 flood units (mci 2–31), all
`ts=1786461853` (equal timestamps), `st=1, seq=good`; `actual_tps_fee` = 0 (mci 2–17) / 1 (mci

`[hub-final] TPS_FEES_BALANCES` — attacker (TXJ6JUSE) balance monotonically increasing +1 → +421,

actual 1, mci 32 (WP-2) 1, mci 33 2. The exp(30)-class fee (1.07e14) never fires in this run.

### a2. WRONG — "at mainnet parameters" (tps_interval=1): the settlement used tps_interval=60

The run's settlement arithmetic proves the fee was computed with **tps_interval=60**, not the
mainnet value 1 that E4-2 claims ("verified in the hub DB").

- The raw log prints one `final tps at <unit> <tps>` per settled unit (34 lines); the fee formula
  is `Math.round(base_tps_fee * (exp(tps / tps_interval) - 1))` (storage.js:1231-1235).
- Cross-checking every one of the 34 printed tps values against the DB `actual_tps_fee`:
  **34/34 match with tps_interval=60; 34/34 mismatch with tps_interval=1** (e.g. F1 tps=0.3333 →
  round(10·(e^0.3333−1))=4 at interval 1, but DB=0; at interval 60 → 0 ✓; F30 tps=5.1667 → 1743 at
  interval 1, DB=1; at 60 → 1 ✓).
- Why: `getSystemVar` (storage.js:1123) reads the in-memory `systemVars` cache populated once at
  boot by `initSystemVars` (storage.js:2464-2473, `ORDER BY vote_count_mci DESC`). The boot module
  inserted `tps_interval=60` (e17b-boot.js sysrows); e32's `setTpsInterval` did a raw SQL
  `UPDATE system_vars` (so the raw table — and the `SYSVARS` log line 144 — shows 1), but never
  refreshed the in-memory cache, so settlement kept using 60.
- Consequence: the measured 0/1 fees are the product of a **60x dilution**, not a mainnet
  parameter. At true mainnet tps_interval=1 with the same count/elapsed the run's own data would
  have produced fees 2 → 1,743 (and 429,007 for the WP-TAIL-0 witness unit, tps=10.67) — still far
  below the F4 blowup, but not "0/1 at mainnet parameters".

### a3. WRONG — the stated mechanism ("count=1 per unit", "elapsed=1", "count≥30 unreachable") is contradicted by the run's own prints

The run's own `final tps at` lines show count **reaching 31** and **elapsed=6**:

- F1 tps=0.3333 = 2/6, F2 = 3/6, … F30 tps=5.1667 = 31/6 (unit at mci 31, count=31, elapsed=6).
- The flood units' `last_ball_unit` field is the **genesis** (`1IYMt5Z…`, ts 1786461847) — the
  units were composed in a 0.2 s burst before WP-1 was balled, so the pre-burst ball (the genesis)
  is what `getFinalTps` uses (storage.js:1174: `elapsed = mc_ts − last_ball_ts`; the ancestry walk
  skips only `main_chain_index <= last_ball_mci`, storage.js:1191).
- So: the count≥30 half of the F4 trigger state **was empirically reached** (31); the elapsed was 6,
  not 1. The trivial fees came from elapsed=6 + tps_interval=60 — not from E4-2's "count=1,
  elapsed=1, round(10·(e−1))-class". (Note E4-2's own prose "round(10·(exp(1)−1))-class" = 17 is
  also not what the run measured, 0/1.)

### a4. OVERSTATED — "there is NO expensive construction… the attack is fully inert"

Not established by the evidence:

1. The count=31 state is empirically reachable (a3).
2. The elapsed=1 half is a **stamp choice the run intended but did not achieve**: the script
   stamped the flood at T0 (1853) expecting WP-1's ball (ts 1852) to be the last ball (elapsed=1),
   but WP-1 was not yet balled at burst composition, so the last ball was the genesis (1847) →
   elapsed=6. The construction "stamp the burst at `last_ball_ts + 1`" was never tested.
3. Nothing in the code blocks that construction: validation rejects only **future** timestamps
   (validation.js:284-285 `timestamp > current_ts + max_seconds_into_the_future_to_accept`); there
   is no old-timestamp or parent-ts-ordering rejection. The e32 `stamp()` re-signs and re-hashes,
   so a backdated-stamp chain is valid.
4. E3-10's own seeded measurement of the joint state (count=30, elapsed=1, mainnet vars) through
   the real `getFinalTpsFee` produced exactly the F4 number:
   `raw-e310-exp.log` → `E310-SUMMARY {"s1_last_fee":{"mci":30,"fee":17},"s2_lag_fee":106864745815235,"s3_exchange_fee":4917}`.
   And E3-10.md's residual note #3 states: *"The attacker self-frosting is real: an attacker CAN
   burn ~10.7% of its own supply-equivalent in declared/settled fees by equal-timestamping its own
   chain — a griefing-against-self only."* — E4-2 ("attacker does NOT burn ~10.7%… fully inert")
   directly contradicts E3-10's own recorded residual.
5. Scope check: even if the self-frosting construction is real, it is a self-grief (attacker pays
   its own fees) — out-of-scope impact per the program ("direct financial damage ≤ 200% of the
   attacker's own expense" is excluded). So **the 004 demotion (victim-side honest-author freeze
   unreachable, E3-10 M1/M2 + funding bound) remains correct**; what E4-2 overstates is the
   attacker-cost narrative and the "mainnet parameters" framing.

### a5. MINOR numeric errors in E4-2's table

- Net effect on the verdict: none — the attacker cost is trivial either way (14 or 15 base units).

### a6. Lab-quality caveats (affect the "real two-node" framing)

  claims (a) need correction (below).
- **Note (E4-2 must be corrected)** — (1) "mainnet parameters" is false for the decisive variable:
  the settlement used tps_interval=60 (boot cache), so the measured 0/1 fees are 60x-diluted; a
  re-run must set system vars through the cache (`storage.systemVars`), not a raw UPDATE.
  (2) E4-2's mechanism (count=1, elapsed=1, count≥30 unreachable) is contradicted by its own raw
  log: count=31 measured, elapsed=6. (3) "No expensive construction / fully inert" is not
  established: the count≥30 half is reachable, the elapsed=1 half is a valid untested stamp

  attacker self-frosting as real. The open question is attacker self-grief only (out-of-scope
  impact class), so the 004 demotion stands — but the "no impact of any kind" sentence should be
  rewritten as "no victim impact; attacker self-frosting construction remains open (self-grief,
  out of scope)".
- **Note (lab quality)** — node and hub booted with different genii (no LAB_GENESIS_TS in the e32
  run) → the node never integrated the flood chain; the node log is truncated (no node-final, no
