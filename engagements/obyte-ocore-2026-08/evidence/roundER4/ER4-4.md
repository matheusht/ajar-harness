**The overstatement — the F4 "mainnet parameters" real-network magnitudes:**
1. **E2-9's fees/balances were computed with tps_interval=60, not 1.** ER2-2 (the E2 verification
   round) F1 established this decisively: the in-memory `systemVars` cache (storage.js:1122-1127,
   initSystemVars at :2463) is populated at boot from DB rows e17b-boot.js seeded with
   `tps_interval=60`; `e29-run.js`'s `setTpsInterval` issues a **DB-only** UPDATE that never
   refreshes the cache. ER2-2 reproduced every logged fee with interval=60 and none with interval=1
   (e.g., the mci-23 settlement, local tps 5.5: interval=60 → round(10·(e^0.0917−1))=1 ✓;
   interval=1 → 2,437). E4-15's citation "real-network (E2-9: fees 0-190, balances +181, no
   negatives)" therefore repeats the interval-60 magnitudes as if mainnet.
2. **E4-2 repeated the same flaw.** `e32-flood.js`'s `setTpsInterval` (evidence/lab/e32-flood.js
   :18-21) is the same DB-only UPDATE; the e32 boot log dump shows the cache initialized at
   `tps_interval: 60` (line 40-44) while the DB shows `1` (line 144, "[hub] SYSVARS"). Its claim
   "System vars: mainnet values ... (verified in the hub DB)" is exactly the DB-vs-cache confusion
   ER2-2 flagged. Re-derivation from the e32 raw log: settlement tps grows 0.2 → 5.1667
   (count≈31/elapsed≈6, last ball at genesis) — at interval=1 the settlement fee per flood unit is
   `round(10·(e^tps−1))` ≈ **2 → 1,736 base**, not the measured 0-1. So "the flood costs 15 base
   units ... fully inert, no impact of any kind" does **not** transfer to mainnet parameters: with
   declared fees of 1-10, the deltas are negative and the author's `tps_fees_balance` goes
   negative — the attacker **self-frosts**, and an honest unit settling inside the same window is
   transiently debited (micro-GBYTE scale, e.g. 10·(e^4−1)≈545 base at tps 4).
3. **E4-2's mechanism claim "count=1 per unit" is contradicted by its own raw log** (tps 5.1667 at
   mci 32 ≈ count 31 / elapsed 6) — the count-lag state it says is impossible is the state its own
   run produced. The record already knows this from E4-1's correction ("E2-9 produced count=22 — a
   real lag state exists; the true protections are M2 + funding bound + self-frosting"), so the
   correction is on record; E4-2's count=1 phrasing regressed from it.
4. **E3-10's "real-path" framing is over-strong.** e310-exp.js drives the real
   `storage.getFinalTpsFee` functions against a **seeded in-process cache of fabricated unit/ball
   objects** (evidence/lab/e310-exp.js :42-58, resetCaches pattern); E3-10.md discloses this
   ("seeded cache (the r2 pattern)") but rounds.md/E4-15's "real-path (fee=17 every step)" reads
   stronger than the method. The arithmetic itself is interval=1-correct (raw-e310-exp.log:
   S1 fee=17 = round(10·(e^1−1)); S2 1.0686e14 = 10·(e^30−1); S3 4,917 at count=31/elapsed=5).

**Why the covered-dry verdict still stands despite (1)-(4):** the demotion's *direction* survives
independent re-derivation. In the worst real state measured (e32: count≈31, elapsed≈6), true
interval=1 settlement fees are ~1.7e3 base (≈1.7e-6 GBYTE) per unit — five orders of magnitude
below the 10.7%-of-supply figure (which needed elapsed=1, i.e. the attacker-only equal-timestamp
lever); honest units are elapsed-diluted (measured 4-7 s in both real runs); the debit lands on
the settling author (self-frosting for the attacker; transient micro-debits for honest authors in
the window); the funding bound (validation.js:2654-2655) caps the attacker's pre-funding; the
freeze is repayable debt. No in-scope finding results and no promoted severity changes. The named
gap is **evidence-quality**: E2-9's and E4-2's mainnet-magnitude numbers must be re-measured with
the cache corrected (ER2-2's F1 was already filed; it was not carried into E4-2) before any
external quoting, and E4-15 §5's citation of them as decisive is overconfident.
