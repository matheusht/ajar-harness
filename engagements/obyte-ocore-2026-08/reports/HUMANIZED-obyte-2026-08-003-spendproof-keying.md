# [LOW] Private-payment spend-proof uniqueness check is keyed on a party-chosen address, so a sender can place a second `good` unit with the same spend proof

**Target:** ocore core library (Obyte Foundation, Immunefi)
**Pinned:** `a7eb776afc68ed4bed05ba554f7f1e95f5d49b44` (2026-08-10)
**Severity:** Low (CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N = 3.7)

## Summary

Hi Obyte team,

The unit-level spend-proof uniqueness check for private payments keys its conflict match on `(spend_proof, claimed-address)`, where the claimed address is the unit's own author. It is never compared to the output owner the spend proof actually commits to. A private-payment sender who retains the bearer spend proof can publish a second unit carrying the same proof under their own address, and every node accepts it as `good`. No conflict is detected, no rejection is emitted, and nothing ever resolves the pair.

I confirmed this on the real path: both units land on the main chain as `good`, and the `spend_proofs` table ends up holding two rows with the identical proof, one under each address.

## Root cause

Three facts.

1. The spend proof commits to the output owner. The transfer proof is a hash of `{asset, unit, message_index, output_index, address, amount, blinding}` (inputs.js:73-80), where `address` is the source output's owner. The payload-side validation recomputes it from the outputs table and compares against the stored row (divisible_asset.js:120-136).
2. The unit-level uniqueness check (validation.js:1637-1654) looks the proof up under the unit's claimed address. For a single-authored unit that is the author's own address; for a multi-authored unit it must be one of the authors (validation.js:1557-1568). Nothing in that path compares the claimed address to the owner.
3. The sender keeps everything needed to recompute the proof. The blinding is generated by the sender at compose time (composer.js:839), stored in their own outputs row, and carried in the private payload. The sender can recompute the proof for the recipient's output at any time.

The result: the recipient's spend created row `(P, recipient)`. The sender's re-spend is checked under `(P, sender)`. No row matches. Accepted.

I should be precise about the scope of the check's role here. For private payments the payload is not in the unit, and the input-level double-spend check only runs where the payload arrives (`bPrivate` is set only in the payload flow, validation.js:2695). So the unit-level spend-proof check is the only network-wide double-spend detection for private payments, and its key is dodgeable.

## Steps to reproduce

I verified this with a scripted experiment on a local node (real composer, real validation, real writer).

1. Create a private divisible asset locally, send a private payment creating output X for a recipient.
2. The recipient spends X. The node stores row `(P, recipient_address)` in `spend_proofs`.
3. The sender authors a new unit spending X with the same proof P, under the sender's own address, and sends it.

Observed: the sender's unit validates as `good` and is saved. The `spend_proofs` table now has two rows with the identical P, one under the recipient's address and one under the sender's. Both units sit on the main chain with no conflict state and no resolution.

The contrast that shows intent: repeat step 3 but reuse an address that matches an existing row (the sender's own earlier spend). The check fires and the unit is cleanly rejected with "conflicting spend proof in inner unit". So the check rejects duplicates only within an address; the key is the bug, not the intent.

## Impact

The ledger ends up with two permanent `good` units carrying the same spend proof, and no resolution mechanism ever fires. The sender can also silently contest a merchant's accepted private payment: the merchant's node shows both units as `good`, with no rejection signal. In the public-asset model the same act produces a clean unit-level rejection.

The honest ceiling: I did not demonstrate direct theft. The ghost unit's competing payload is rejected by the payload-side owner binding, so the double-spent value does not move twice. The merchant exposure is real but conditional on acceptance flows that trust unit inclusion, and on the sender winning the main-chain race. That is why I rate this Low rather than Medium. The ledger-integrity effect (two unresolved `good` units with one proof) stands on its own.

## Severity

Low, and I would defend that. The mechanism is confirmed, the fix is small, but the value impact needs a merchant acceptance flow plus a race win, neither of which I could demonstrate in scope. If you know of private-payment acceptance flows that trust inclusion without uniqueness checks, this deserves a second look at Medium.

## Remediation

Bind the uniqueness key to the output owner. The payload-side validation already computes the owner's address (divisible_asset.js:120-136); the unit-level check should resolve the same address from the output and key on `(spend_proof, owner)` instead of `(spend_proof, claimed-author)`. Storing the owner's address with the `spend_proofs` row would make this a one-line query change.

Happy to retest once you've had a look.
