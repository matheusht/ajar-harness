# Comparison protocol — draft, not executed

**Decision:** compare real defect discovery during a bounded run. A finding
requires an independent effect, a relevant control, and clean reproduction.
The raw material is each frozen source archive, the ordinary application,
host-captured execution, provider usage, and the observer's hidden reference.
Counting each harness's finding labels would reward different definitions of
`confirmed`, so a common external grader is necessary. This draft cannot be
preregistered for scoring until the open model, target-route, and budget choices
are fixed. A difference in model, target access, authority, budget, or grader
input invalidates a matched comparison.

## Order of work

1. **Preparation only, current state.** Recheck the [candidate pins](README.md)
   and the [scope proposal](scope.md). Record a clean source manifest for each
   harness and target. Keep the observer answer out of both researcher contexts.
   No target or model execution belongs to this stage.
2. **Native E2E qualification, future separate action.** Before scored work,
   prove one genuine native model turn on the owned local target. Require the
   researcher's command, host effect capture, saved result, clean original replay,
   relevant fixed or denial control, fresh review, spent allowance, stop, and
   verified cleanup. Exercise an interrupted turn and an uncertain-effect path.
   Preserve a repeatable command, inputs, environment, receipts, and expected
   result. Use the [existing T04 acceptance contract](../native-qualification/T04-UNHINTED-PREFLIGHT.md).
   A synthetic executor check or observer-only replay does not pass.
3. **0 route and parity preflight, future separate action.** Use the white-box
   live-scan route, `0 scan --target <local URL> --repo <vulnerable source>`.
   Freeze its command, enabled scope policy, model endpoint, tool permissions,
   target setup, output path, and cleanup. Verify that both arms can see the
   same ordinary app entry paths and actor capabilities from the same initial
   state. If the native protected route has no equivalent for 0, exclude it
   from both arms or stop the comparison. An installed CLI or successful build
   is not a completed investigation.
4. **Method pilot, future separate action.** Use the Kanboard case to check
   setup, route parity, metering, evidence capture, adjudication, and cleanup.
   Keep its outcomes, including no-finding or blocked runs, but do not use this
   public case alone to rank research quality.
5. **Scored comparison, future separate action.** Select and freeze an
   independent multi-target roster first. Start each arm in a clean context
   with an independent target copy and the same neutral brief. Randomize arm
   order per case. Repeat cases only by a rule fixed before scoring, not in
   response to a favorable or poor result. Preserve setup failures and
   zero-finding runs. Do not tune an arm on a scored case.
6. **Blind adjudication.** Remove harness names from claim packets. A separate
   reviewer checks the exact source, effect, control, clean replay, and observer
   state. Reconcile all claims and duplicate roots before calculating totals.

Steps 2–6 are not authorized by the current scaffold instruction. Each actual
target run still requires its own signed target-local scope and route approval.

## Matched conditions to freeze before scoring

| Dimension | Required match or recorded difference |
| --- | --- |
| Target | Same archive bytes, version, ordinary setup, synthetic identities, initial database, reachable interfaces, and allowed effects. Separate disposable copies. A common running app may be prepared for both arms; any setup help is recorded. |
| Model | Same exact provider route, model identity and effective revision, account entitlement, decoding settings, context limit, and fallback policy. Record actual provider receipts. No silent substitute. |
| Prompt | Same neutral task objective, source access, and disclosure of target facts. Harness-specific instructions and tools remain native to each product and are inventoried. No advisory, fix, answer, or seeded lead enters either context. |
| Pilot budget | Proposed 45 minutes of host-enforced wall time per arm, measured from start through stop. This is a feasibility limit only. Record requests, tokens, tunnels, bytes, and cost; do not infer request counts from tunnel limits. |
| Scored budget | Before scoring, freeze one hard wall-time limit and a common, independently enforced provider usage or spend limit that covers research, delegates, review, and resume for both arms. Numeric values and the common meter remain **unselected**. Each arm's own limits may be stricter but do not establish shared enforcement. |
| Money | Record billed provider cost and all unpriced usage. Do not call a nominal free tier zero cost without a complete receipt. Cost-normalized results are unavailable if billing is incomplete. |
| Reviewer | Same independent review allowance and common external scoring rule. A required review is counted as human work, not a research hint. |
| Recovery | A resume continues the same budget. It does not reset time, requests, target state, or human-help counters. |

The native runner admits keyless `opencode/deepseek-v4.1-flash-free` and keyed

## Failure checks fixed before implementation

| Failure | Required observation |
| --- | --- |
| An arm receives the advisory, fix, observer answer, or other arm's output. | Mark the run contaminated. Do not score it. |
| The model, source hash, initial state, or effective permission differs. | Stop the paired case. Record the mismatch and repair before a fresh start. |
| A target action has an unknown result. | Stop new effects until authorized readback or reset establishes state. Charge prior usage. |
| An arm exceeds a shared ceiling or its meter fails. | Stop the run and mark the paired case invalid. Preserve actual spend and partial findings. |
| A setup error prevents a valid target test. | Record blocked setup. It is neither a target negative nor a false finding. |
| A model calls a held path proof of safety or submits a label without an effect. | Keep the claim unsupported. Record the overclaim separately. |
| A reviewer cannot reproduce an asserted effect. | Record inconclusive until conditions and contrary evidence settle it. Do not automatically call it false. |
| A reviewer proves the reported effect is ordinary behavior, a wrong actor, or a changed target. | Mark the specific claim false with the decisive control and evidence. |
| Cleanup leaves an owned resource or uncertain effect. | Keep the case unfinished and record the exact resource. |

## Common scoring

- **True finding:** a distinct defect on the exact original source with a
  relevant effect, a causal control, clean replay, and independent review.
  Group duplicate reports by root cause and effective fix. Report supported
  partials at their supported depth; do not count them as true findings.
- **False finding:** a submitted defect claim contradicted by a decisive
  independent test or shown to depend on altered source, injected private
  state, extra privilege, or ordinary behavior. A mere failed retry is not
  enough. Preserve the claim and disproof.
- **Unresolved claim:** a plausible or asserted issue without enough proof or
  disproof. It counts neither as true nor false. Report it separately.
- **Missed reference:** a prevalidated defect in the hidden answer that the
  arm did not establish by its deadline. A new valid defect outside the answer
  is still eligible after independent review.
- **Human help:** log each setup action, research hint, rescue, prompt edit,
  target reset, review, and adjudication with actor, elapsed minutes, and
  effect on the run. Report research hints separately from necessary setup
  and independent review. Do not hide help inside a coordinator prompt.

Report per case and per arm: true findings, false findings, unresolved claims,
missed references, time to first true finding, total wall time, actual provider
requests and cost, setup failures, human interventions and minutes, and cleanup
state. Show the raw counts before any ratio. Precision is true divided by true
plus false when the denominator is nonzero. A one-case pilot can validate the
method; it cannot establish which harness wins across domains.
