# Domain Pack: Authentication, OAuth, Delegation, and Cryptography

Load this pack only when `skill_mode=domain` on authentication middleware, JWT/PASETO/session verifiers, OAuth2/OIDC providers and clients, capability tokens, or cryptographic primitives.

**Step-2 Divergence Exit Rule:** Inspect the exact verifier configuration (algorithm pinning, key resolver, claim checks, DB transaction atomicity) first. If a concrete guard blocks the vector, close the task immediately with `ajar task dry <task_id> --worker <id> --locus <file:line> --control "<reason>"`.

## Contrastive Pattern Matrix

| Pattern | Defect Pattern & Sinks | Compensating Control That Makes It Safe | 4-Arm Verification Recipe |
| --- | --- | --- | --- |
| **1. JWT Algorithm, `kid` / `jku`, & `decode`-vs-`verify` Bypass** | Middleware calls `jwt.decode(..., options={"verify_signature": False})` (or JS `jwt.decode` instead of `jwt.verify`), accepts `"alg": "none"`, allows asymmetric-to-HMAC (`RS256 -> HS256`) public-key confusion, trusts attacker-supplied `jku`/`x5u`/`jwk` headers, or uses hardcoded/fallback empty secret (`jwt-authentication-bypass`). | Verifier pins explicit algorithm allowlist (`algorithms=["RS256"]`), resolves keys exclusively from trusted server JWKS/keystore by validated `kid`, and rejects unsigned or empty-secret tokens. | Arm 1: Forged `alg: none`, `HS256`-signed-with-pubkey, or unverified token authenticates as target user and accesses guarded endpoint. Arm 2: Legitimately signed token succeeds. Arm 3: Enforce `jwt.verify` with pinned `algorithms` and trusted keystore. Arm 4: Legitimately signed token passes. |
| **2. JWT Claim Validation Confusion (`aud`, `iss`, `exp`, Tenant)** | Signature is cryptographically valid for the IdP, while the service omits `aud` (accepting tokens minted for sibling/public client apps), omits `iss`, ignores `exp`/`nbf`, or trusts an unverified `email`/`org_id` claim across multi-tenant issuers (`jwt-claim-validation`, `benchmarks/hermetic/targets/api-jwt-claim-validation`). | Verifier enforces exact `issuer`, service-specific `audience`, `exp`/`nbf`, `email_verified == true`, and issuer-to-tenant mapping (note: a valid signature that is still denied access by downstream authz is not a finding). | Arm 1: Wrong-audience, expired, or unverified-tenant token grants guarded privilege. Arm 2: Token with matching `iss`, `aud`, and active `exp` succeeds. Arm 3: Enforce strict `audience`, `issuer`, and tenant-claim checks. Arm 4: Matching valid token succeeds. |
| **3. OAuth Authorization Code Non-Atomic Single-Use (Race)** | Token endpoint reads `auth_code` row (`SELECT`), verifies `used == false`, mints access/refresh tokens, and only afterward marks `used = true` without an atomic compare-and-swap (`oauth-authorization-code-single-use`). | Atomic single-statement `UPDATE oauth_codes SET used = TRUE WHERE code = $1 AND used = FALSE RETURNING *` (or `DELETE ... RETURNING *`) ensures at most one concurrent exchange succeeds, and revokes issued tokens on replay attempt per RFC 6749 §4.1.2. | Arm 1: Concurrent `/oauth/token` exchanges with one authorization code mint multiple independent token sets (`--determinism probabilistic --trials 10`). Arm 2: Single code exchange mints one token set. Arm 3: Replace read-then-write with atomic `UPDATE ... WHERE used = FALSE RETURNING`. Arm 4: Single code exchange passes while replay fails. |
| **4. OAuth Client, `redirect_uri`, PKCE & `state` Binding Bypass** | Authorization code issued to `client_a` (or `redirect_uri_a`) can be exchanged by `client_b` because `/token` omits `client_id` + exact `redirect_uri` + `code_verifier` binding (`oauth-client-binding`), or OAuth login callback omits CSRF `state` / allows open-redirect `redirect_uri` prefix/traversal theft. | Code record binds `(client_id, exact_redirect_uri, code_challenge, code_challenge_method="S256")` at `/authorize` and verifies all four atomically at `/token`, plus exact `redirect_uri` match and session-bound `state`. | Arm 1: Code minted for Client A or mismatched `redirect_uri`/missing `code_verifier` exchanges successfully. Arm 2: Matching client + `redirect_uri` + valid `S256` `code_verifier` succeeds. Arm 3: Bind and verify `(client_id, redirect_uri, PKCE)` on `/token`. Arm 4: Valid exchange passes. |
| **5. Delegated Capability Attenuation Loss** | User or parent service mints a scoped API key, OAuth sub-token, presigned token, or session delegation (`read:repo-x`), while token refresh, impersonation, or child-worker spawn drops the attenuation caveats and restores the parent principal's full privileges (`delegated-capability-attenuation`). | Effective permission check computes `principal_scopes INTERSECT token_scopes` on every request and preserves monotonic scope intersection across token refresh and sub-delegation. | Arm 1: Scoped token (`read-only`) executes `write`/`admin` action (directly or after `/refresh`). Arm 2: Scoped token executes permitted `read` action cleanly. Arm 3: Intersect token scopes on dispatch and refresh. Arm 4: Permitted `read` action still passes. |
| **6. Cryptographic Primitive Misuse & Non-Constant-Time Secret Compare** | Nonce reuse in AES-GCM/ChaCha20-Poly1305/ECDSA, unauthenticated AES-CBC decryption exposing padding oracles, `math/rand` / `random.random()` / `Math.random()` used for reset tokens or keys, malleable signature verification, or `==` / early-exit byte comparison on HMAC/webhook secrets (`cryptographic-weakness`). | CSPRNG (`secrets`, `crypto/rand`, `OsRng`) for all secrets/nonces, AEAD with unique/misuse-resistant nonces, canonical signature verification, and `hmac.compare_digest` / `subtle.ConstantTimeCompare`. | Arm 1: Predictable token recovery, nonce-reuse keystream/key recovery, or forged unauthenticated ciphertext tampering succeeds. Arm 2: Valid authenticated token/ciphertext verifies cleanly. Arm 3: Switch to CSPRNG / AEAD / `compare_digest`. Arm 4: Valid token/ciphertext verifies cleanly. |
| **7. Hardcoded / Default Credentials & Unthrottled Secret Verification** | Service ships default admin credentials, embedded static API/signing keys in source/config, or short numeric OTP login/reset endpoints without per-account attempt caps (`default-creds-brute-force`). | Mandatory unique secret provisioning at startup (refusing insecure defaults), external secret injection, and per-account + per-IP rate/attempt limits on OTP/password endpoints. | Arm 1: Default credential or bounded OTP exhaustion authenticates without secret knowledge in local test environment. Arm 2: Provisioned unique credential authenticates cleanly. Arm 3: Reject default/static secret and enforce attempt limit. Arm 4: Provisioned credential passes. |
